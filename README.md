# J-Novel：面向长文本生成的过程感知型小说创作框架

## 摘要

大规模语言模型（Large Language Models, LLMs）在长文本创作任务中展现出巨大潜力，但当任务规模超过单次上下文窗口时，系统性失效模式开始显现：叙事连续性断裂、文风漂移、以及机器生成痕迹的顽固复发。现有解决方案——无论是上下文窗口扩展、链式推理提示，还是通用型 Agent 框架——均未能从根本上解决这三个问题，因为它们缺乏对**创作过程本身的状态管理**。

本文提出 J-Novel，一个融合了过程层状态管理的端到端小说创作框架。该框架的核心贡献在于：（1）引入"创作台账"（Creation Ledger）作为 Agent 的外接工作区，实现每章边界强制重读（Seam Re-reading），从机制上防止长上下文场景下的静默状态丢失；（2）提出"事实三态标记"（✓/ ? / ✗），将"已落正文"、"仅规划"与"已被否定"的叙事元素物理分离，根除了"我以为写过了"这类逻辑崩坏的源头；（3）建立了三层量化质检体系——句法层九项、分布层七项、作者在场一项，共 **17 项硬指标**，将"人类写作节律"转化为可执行的硬性阈值；（4）设计了**链式流水线**并发协议，明确"并行的单位是工序而非章节"，通过接口契约冻结、锚点滚动与交叉互检保证多代理协作时的叙事一致性；（5）配套了一套 SKILL 自身的发布前 QA 与故障注入机制（`audit_release.py` + `test_guards.py`），把"我改了"变成"机器验证过真的改了"。

我们在两部完整小说的生产过程中验证了该框架的有效性。实证结果表明，J-Novel 产出的文本在句法层与分布层指标上显著趋近人类基线，同时消除了传统 AI 创作中常见的连续性 BUG 与模板化表达。本文旨在为长文本生成领域提供一个具备可复现性的、工程化的研究基线。

**关键词**：AI 辅助创作 · 长文本生成 · 叙事连续性 · 过程管理 · 质量控制 · 多 Agent 协作

## 1. 引言

### 1.1 问题背景

大型语言模型在创意写作任务中的能力已得到广泛验证。给定一个简短的提示或大纲，LLM 能够生成流畅、连贯、甚至具备一定文学性的短篇文本。然而，当任务从"写一个短篇"扩展到"写一部长篇小说"（通常超过 10 万字、数十个章节）时，模型的性能急剧下降。

这种下降并非源于模型"不会写"，而是源于长文本生成任务的三个结构性痛点：

**痛点一：连续性错觉（Continuity Illusion）**。在跨越数十个章节的创作过程中，LLM 必须记住大量事实性信息：人物的位置、情绪状态、已知信息、伏笔状态、时间线……当信息量超过模型的"有效工作记忆"时，模型会基于上下文中的近期信息做出推断，而这些推断可能与数十章前确立的事实相矛盾。这种矛盾不会触发任何错误信号——模型不会"报错"，它只是安静地产生了一个逻辑 BUG。在最坏的情况下，第 5 章登记的伏笔在第 20 章被当作既成事实引用，而该伏笔从未真正被写进正文。

**痛点二：长跑漂移（Long-haul Drift）**。文风不是由单一规则定义的，而是由大量微观决策（词汇选择、句法节奏、叙述者距离、修辞偏好等）共同构成的分布。在长篇创作中，这些微观决策会随着时间推移逐渐偏移。当这种偏移累积到一定程度时，小说的前 5 章和后 5 章读起来像是两个不同作者写的——而写作过程中的任何一步都不会显式地报告这种漂移。

**痛点三：AI 味顽固复发（AI-flavor Recidivism）**。"AI 味"不是某一种具体的错误，而是一组统计层面的异常：过高的句首代词比例、过密的破折号插入语、过度的身体部位描写、过少的情绪词直说……当规则以"禁止 X"的形式给出时，LLM 的典型反应是换一种方式表达 X，从而在规避表面规则的同时产生新的、更隐蔽的统计异常。这就是为什么单纯依赖"去 AI 味提示"往往治标不治本。

### 1.2 现有工作及其局限

现有解决方案大致可分为三类：

**（1）上下文窗口扩展（Context Window Scaling）**。以 GPT-4 128K、Claude 200K 为代表，通过扩大上下文窗口让模型"看到更多"历史内容。这在一定程度上缓解了短期遗忘，但无法解决根本问题：注意力机制在长序列中呈稀疏分布，关键信息可能被淹没；且窗口总有上限，对于 30 万字以上的长篇任务仍显不足。

**（2）通用型 Agent 框架（General-purpose Agent Frameworks）**。如 LangChain、AutoGPT 等，提供了工具调用、记忆存储、任务规划等通用能力。但它们的设计目标是"通用任务执行"，而非"文学创作"。它们缺乏对叙事特殊性的理解——例如，小说中的"人物状态"与"待办事项"有着本质不同的更新语义，通用记忆模块无法区分"已落正文"与"仅规划"之间的微小但关键的差异。

**（3）小说写作辅助工具（Narrative Writing Assistants）**。近年来出现了若干面向小说的 AI 辅助工具，如 Sudowrite、NovelAI 等。它们提供了优质的文本生成与润色能力，但通常以"单次生成"为交互单元，缺乏对"跨章连续性"和"过程状态"的系统化管理。用户仍然是整个创作流程的核心调度者，而非 Agent。

### 1.3 本文贡献

本文提出 J-Novel 框架，从"过程层状态管理"的角度重新审视 AI 长篇创作问题。具体贡献包括：

1. **提出"创作台账"作为 Agent 外接工作区的概念**，将"故事的状态"与"Agent 自身的认知状态"物理分离，并在每章边界强制执行"Seam 重读"机制，从系统层面防止静默状态丢失。

2. **建立"事实三态标记"系统**（✓ / ? / ✗），将叙事事实的认知状态（已确认/待确认/已否定）显式编码到项目管理文件中，消除了"规划"与"执行"之间的语义混淆。

3. **构建三层量化质检体系**：基于三部人类小说全集（合计约 1213 万字）的统计基线，设定了 **17 项硬指标**——句法层九项、分布层七项、作者在场一项——外加一项独立的硬性句式闸门（`不是X，是Y`），将"人味"分解为可自动化验证的数值阈值。其中"分布层"是均值达标后的第二道防线：均值可以过关，但分布形状仍可能不像人。作者在场指数则是全部指标中分离度最高的一项（人类 3.73–7.84 vs AI 0.64–1.89）。

4. **设计链式流水线并发协议**：明确"并行的单位是工序而非章节"，通过**接口契约冻结**、**批内依赖图**、**锚点滚动**与**交叉互检**机制，在保证叙事一致性的前提下实现多代理并行加速，并配套 `check_batch_gate.py` 把"批次验收"从自查清单变成可执行的退出码。

5. **配套 SKILL 自身的工程化自检**：`audit_release.py` 一条命令跑完八项发布前 QA（引用完整性 / 脚本语法 / 阈值一致性 / 调用链闭合 / 结构完整性 / 残留检查 / 跨脚本一致性 / 分离回归），`test_guards.py` 用 8 例故障注入验证"守卫真的会响"。**"加了守卫"和"守卫有效"是两件事。**

6. **以两部完整小说作为实证案例**，展示了该系统在实际生产中的有效性与局限性。

## 2. 系统架构概述

J-Novel 是一个文件化、状态感知的多代理创作框架。其整体架构可以概括为"一条流水线、三本台账、两层质检、一套自检"。

### 2.1 六阶段流水线

J-Novel 将长篇创作分解为六个可验证的阶段：

| 阶段 | 名称 | 核心任务 | 出口条件 |
|------|------|---------|---------|
| Phase 0 | 初始化 | 加载用户偏好、检测未完成项目、状态恢复五步 | 清单全勾 + 入口判定完成 |
| Phase 1 | 深度采访 | 五层挖掘（情绪/动机/期待/想象/盲区），磨出 12 项验收清单 | 验收全过 + 故事速写经用户确认 |
| Phase 2 | 规划与确认 | 生成故事圣经、人物档案、分章大纲、写作计划 JSON、台账、细纲/任务卡 | 清单全勾 + 锚点章定调确认 |
| Phase 3 | 疯狂创作 | 逐章或链式流水线执行"写—审—改—锁"循环 | 全部章节 completed |
| Phase 4 | 自动校验 | 字数/质检痕迹/节律/统计指纹/连续性/台账对账；按重试三出口修复 | 全部章节 PASS + 完成报告 |
| Phase 5 | 完稿润色 | 一致性通读、台账对账、节奏评估、开篇重审、资产沉淀 | 清单全勾 + 全书完成总结 |

每个阶段的入口处设有"执行清单"（Execution Checklist），Agent 必须逐项打勾才能进入下一阶段。清单机制的设计目的是防御"流程跳步"——在长流程中，Agent 倾向于跳过自认为"已熟悉"的步骤，而清单将"已做"与"未做"的边界显式化。

### 2.2 文件化状态管理：三本台账 + 两份规划文件

J-Novel 的核心设计原则是**所有状态必须落盘**。项目目录下的五份文件分别承载不同维度的状态，其中**三份构成"台账体系"**：

| 文件 | 角色 | 管理内容 | 回答的问题 | 更新者 |
|------|------|---------|-----------|--------|
| `00-人物档案.md` | 规划文件 | 角色静态设定 | 这个角色是谁？ | 规划阶段一次性写入 |
| `01-大纲.md` | 规划文件 | 章节规划与摘要 | 每章要发生什么？ | 规划写入，写作后追加摘要 |
| `02-写作计划.json` | **台账** | 项目进度 | 还剩什么没做？ | 每章更新 |
| `03-状态台账.md` | **台账** | 故事内动态状态 | 现在故事里发生了什么？ | 每章写回 |
| `05-创作台账.md` | **台账** | Agent 的认知状态 | 我现在确认了什么/不确定什么？ | 每章 seam 重读与回写 |

`05-创作台账.md` 是本框架最核心的创新。它不记录"故事里发生了什么"（那是 `03-状态台账.md` 的职责），而是记录**"Agent 认为自己知道了什么"**。这个区别至关重要：当上下文窗口滚动、早期信息被压缩时，Agent 仍然可以通过重读 `05-创作台账.md` 来恢复自身的"认知状态"，从而避免"静默丢弃约束"。

**三本台账回答三个不同的问题，谁也替代不了谁**：`02` 管"还剩什么没做"，`03` 管"故事里发生了什么"，`05` 管"我现在知道什么"。混用它们会导致状态机失效——例如把 `05` 写成待办清单（那在 `02` 里），或把 `03` 的推测条目当成 `05` 的既成事实。

`05-创作台账.md` 的五字段结构如下：

```markdown
# 创作台账（每次 seam 重读）
最近重读章号：第X章

## Goal
一句话，本阶段"完成"意味着什么，能判断自己到没到。

## Core
≤2 条。第三条想进来必须先换掉一条，且换的时候要说出声。
- 文风锚点 —— [一句话 + 它为什么重要]
- 本卷张力 —— [一句话 + 它为什么重要]

## Verified
编号追加，永不改写。每条写清依据。
- ✓01 [已落正文的既成事实]（依据：第X章）

## Open
每条带"什么能终结它"。
- ?01 [还不确定什么] —— settled by: [什么能终结它]

## Next
单一动作，永不为空。
```

### 2.3 执行契约（Execution Contract）

为确保 Agent 在长流程中不跳步、不偷懒，J-Novel 内置了一份"执行宪法"，其核心是**九条铁律**。前四条管"产物是否合格"，中间四条（5–8）管"Agent 在长跑中是否还醒着"，第九条管成本纪律：

| 编号 | 铁律 | 核心内容 |
|------|------|---------|
| 1 | 【必须】读流程 | 进入任何 Phase 先读对应流程文件，按执行清单逐项执行 |
| 2 | 【必须】不跳步 | 标注【必须】的步骤不可跳过/合并/简化 |
| 3 | 【必须】读指南 | 关键动作前必读对应 guides 文件 |
| 4 | 【必须】固定排班 | 检查型工具到点必调，自检"没问题"不是跳过理由 |
| 5 | 【必须】三态标记 | 标 `?` 的条目，下游章节不得当作已发生的事实来写 |
| 6 | 【必须】Seam 重读 | 每章边界重读 `05-创作台账.md` 五段后再动笔 |
| 7 | 【必须】置信度绑定 | 读到「晃」禁止原路重走，三选一换路 |
| 8 | 【必须】注册分离 | 正文里不得出现细纲记号、质检字段、未展开的缩写 |
| 9 | 【必须】成本纪律 | 一次跑完全部脚本 / 一次批量改写 / 不重读指南 / 子代理只读速查卡 |

铁律 5–8 是本框架区别于其他系统的关键：它们不直接作用于产物，而是作用于 Agent 在写作过程中的"认知纪律"。铁律 9 处理的是另一类问题：**长篇创作的成本大头不是模型产出，而是上下文重发**。实测基线（《灰烬之契》前 6 章 / 1.24 万汉字）：总消耗 45.4M tokens，其中 97.8% 是 cacheRead（上下文重发），output 只占 0.7%——放大倍数 135 倍。因此铁律 9 的核心不是"少检查"，而是"同样的检查不要做多次"。

## 3. 核心机制详解

### 3.1 事实三态标记系统

**问题**：在长篇创作中，最昂贵的一类 BUG 是"我以为这条已经写过了"。规划阶段登记了某个伏笔，写作到第 20 章时，模型基于上下文中的规划记忆将其当作既成事实引用，而该伏笔实际上从未被写进正文。这种错误不会触发任何异常信号——它只是安静地产生了逻辑断裂。

**解法**：J-Novel 引入"事实三态标记"，强制状态台账与伏笔对照表中的每一条目携带状态位：

| 标记 | 含义 | 约束 |
|------|------|------|
| `✓` | 已在正文中明确写出 | 标注依据章号，可追溯 |
| `?` | 仅规划或推断，尚未落正文 | 下游章节**不得**以此为前提 |
| `✗` | 已被后续剧情否定 | 不删除、不覆盖，保留证据链 |

默认无标记 = `?`。这一设计将"规划"与"执行"在语义层面强制分离。在 Phase 3 的每章收尾步骤中，Agent 必须扫描本章正文，将真正落地的条目从 `?` 更新为 `✓（第X章）`，并在 `05-创作台账.md` 的 Verified 字段中追加编号记录。

**效果**：三态标记不依赖于模型的"记忆"，而是依赖于文件系统的持久化和每章收尾时的强制检查。它从工程层面切断了"记忆混淆导致逻辑 BUG"的因果链。

### 3.2 Seam 重读机制

**问题**：即使在文件化状态下，Agent 仍然可能在长跑中"静默丢失约束"——文风锚点被悄悄换掉、某个伏笔是"写过了"还是"打算写"记不清了、排班专项检查是否执行过全凭印象。这些错误不会报错，它们只会在第 20 章变成"这本书怎么读着不对劲"。

**解法**：J-Novel 在每章创作的入口处（Phase 3 步骤 0.5）强制执行"Seam 重读"：Agent 必须用不超过 30 秒的时间，完整读取 `05-创作台账.md` 的五段全部内容（Goal / Core / Verified / Open / Next）**与 `03-状态台账.md` 本章出场人物的条目**，并在动笔前更新 Next 字段。

**两个台账都要读**：`05` 管认知状态（我已确认什么/待定什么），`03` 管故事内状态（人现在在哪/什么情绪/知道什么）。换会话后只读 `05` 会在本章写出"上个会话已经解决的事"。

这一机制的设计依据是注意力理论：LLM 的注意力机制能够平等地关注上下文窗口内的任何 token，但**只有在 token 还在窗口内的时候**。当上下文滚动、早期信息被压缩或移出窗口时，注意力无法重新触达这些 token。Seam 重读将 `05-创作台账.md` 设计为"注意力锚点"——它是每个 Seam 处都会被重新加载的信息集，因此永远不会被遗忘。

Core 字段的"≤2 条"限制进一步强化了这一机制：超过两条的 Core 会被稀释，每条只能分配到不到二分之一的注意力。第三条想进入 Core 时，Agent 必须**说出口**（"放下 X，拿起 Y"），将离开的那条写入 Verified 或 Open。这一"出声"操作防止了静默丢弃（Silent Drop）——即某个约束在任务中途悄悄停止生效，而 Agent 没有意识到它的消失。

### 3.3 三层量化质检体系

**问题**："读起来像不像人写的"是一个主观判断，Agent 可以用"我觉得没问题"糊弄过去。主观判断不可信，数字可信。

**解法**：J-Novel 构建了一套基于统计基线的三层量化质检体系，核心工具是 `check_human_rhythm.py` 与 `check_aistyle.py`。基线取自三部完整人类小说全集（齐佩甲《超神机械师》、三天两觉《惊悚乐园》、柳岸花又明《我真没想重生啊》，合计约 1213 万字）——取范围而非单一样本，避免被单一作者带偏。

#### 层一：句法层九项（句子怎么组织）

| 指标 | 人类范围 | 硬阈值 | 方向 | 特征描述 |
|------|---------|--------|------|---------|
| 句首代词占比 | 1.5–10.4% | ≤15% | max | 人类很少用"我/他/她"开句 |
| 句首引号占比 | 18.4–30.6% | ≥15% | min | 人类让对话先行 |
| 平均句长 | 22.7–36.6 字（均值 30.8） | ≥18 字 | min | **18 是底线，23–37 才是目标区间** |
| 破折号密度 | 0.05–0.97/千字 | ≤1.5/千字 | max | 破折号是"句子写完再补一刀"的痕迹 |
| 身体部位密度 | 0.31–0.55/千字 | ≤1.0/千字 | max | 过度身体化是 AI 对"禁止情绪词"的补偿 |
| 情绪词密度 | 0.32–0.35/千字 | 0.25–0.5/千字 | range | **区间制：过低或过高均不合格** |
| 明喻密度 | 1.05–1.27/千字 | 0.8–1.5/千字 | range | 区间制：比喻审美需波动 |
| 对话占比 | 20.4–33.5% | ≤40% | max | 护栏，**无下限**（原"≥30%"因逼出注水已废除） |
| 动作短语密度 | 0.106–0.247/千字 | ≤0.4/千字 | max | ACTION_PATTERNS 是违禁品清单，不是素材库 |

#### 层二：分布层七项（均值达标 ≠ 分布像人）

这是 v4.0 新增的一层。前一层只看均值，但**均值可以达标而分布形状仍不像人**——例如人类的句长分布是"短句群 + 长句群"（p90 到 48–74 字），AI 是"挤在 15–40 字之间"，均值接近，形状完全不同。

| 指标 | 人类范围 | 硬阈值 | 方向 | 特征描述 |
|------|---------|--------|------|---------|
| 超长句（≥60字）占比 | 4.7–19.0% | ≥3% | min | **最强指标**：人类把多个信息单元打包进一个复合句 |
| 句长 p90 | 48–74 字 | ≥42 字 | min | 长句能力的上沿——AI 根本没能力写长 |
| 节奏变异系数（500字窗口） | 0.251–0.321 | ≥0.19 | min | 人类"该急则全短句、该缓则长句铺陈" |
| 中文量词密度 | 7.04–8.76/千字 | ≤10.5/千字 | max | **反向指标**：AI 用"一+量词"做泛化指代，是人类 2–3 倍 |
| 长对话（≥30字）占比 | 15.8–27.7% | ≥8% | min | 人类对话里有"一段完整发言"，AI 全是短促信息交换 |
| 数字密度 | 1.16–3.15/千字 | ≥0.8/千字 | min | 人类用具体数字锚定世界，AI 几乎不用 |
| 现实锚定计量 | 0.07–0.72/千字（现实题材） | ≥0.05/千字 | min | 人类技法型指标，19 倍分离；**架空/游戏世界观豁免** |

#### 层三：作者在场（第 17 项，也是分离最干净的一项）

把引号里的对话剥掉，只统计**叙述部分**的叙述者人格痕迹：评价副词（其实/居然/简直/毕竟）×1 + 口语插话（说白了/反正/怎么说呢）×3 + 吐槽贬称（这货/欠揍/要命）×3 + 语气词×1，再加叙述句里 `？` / `！` 的占比×0.5。

| 指标 | 人类 | AI | 判定 |
|------|------|-----|------|
| 作者在场指数 | 3.73 / 6.25 / 7.84 | 0.64 / 1.27 / 1.89 | 区间 2.5–12 |

**根因**：AI 的叙述是**透明的**——只报告事件，不表态。它把所有态度都让角色用对话说出来，叙述者自身没有立场。最极端的两个信号：口语插话在 AI 的十个样本里密度是 **0.00**；AI 把所有的 `？`/`！` 都放进引号里（叙述感叹号差 **252 倍**）。

**⚠️ 这是全部规则里最容易做歪的一条。** 实测教训：第一版把这条写成配额（"≥3 处叙述者评价 + ≥2 处叙述句里的 `？`/`！`"），结果在场指数从 0 涨到 **7.93 完美达标，盲评却 3:0 判负**——三位评委各自独立地从同一个文件里挑出同一组三句（"这种事也值得…？""这算什么规律？""这算什么秋天？"），原话："**模板化的自由间接引语，密度整齐得像刷 KPI**"。**"没有人"不能靠"加几条人的话"来修，要修的是视角：先有人，再有话。**

#### 独立硬闸门：硬性句式

`check_aistyle.py` 的退出码**只由「先否定再肯定」驱动**：「不是X，是Y」（同句）硬线 **0.12/千字**、「不是X。Y是…」（跨句）硬线 **0.40/千字**。

> ⚠️ 原版只匹配「不是…而是…」，结果 **AI 学会了绕开"而是"，改用"是"**——人类 0.087/千字 vs AI 0.011/千字，旧规则完全失效（AI 反而更少）。新口径同时覆盖同句变体与跨句变体。改法：改成直接陈述 Y，或把否定句独立留白。

#### 弱信号（提示，不阻塞）

| 指标 | 人类范围 | 弱阈值 | 方向 |
|------|---------|--------|------|
| 单句成段占比 | 40.8–99.0% | <40% | min |
| 最长句（字） | 86–166（窗口 p10–p90） | <90 | min |
| 对话占比过低 | 20.4–33.5% | <10% | min |
| 通用模板短语密度 | 0.55–1.22/千字 | >1.5/千字 | max |

其中"通用模板短语密度"专门针对"一个人"、"这一刻"、"走廊里"等任何小说都能套用的泛化表达——**人类的高频词是专有名词（人名、地名），AI 的高频词是通用模板词**。"一个人"这个模板出现在至少 5 部 AI 小说里。

#### 脚本测不出来的那一半：独立质检子代理

**v4.4 实测证明：脚本全绿 ≠ 像人写的。** 一轮 A/B 里，加了新规则的那一版所有脚本指标全部通过（在场指数 0→7.93），**但盲评以 3:0 判负**。

所以 J-Novel 在脚本之后加了一道**独立质检子代理**（`guides/review-agent.md`），核心是**独立性铁律**——**只给纯正文**，不给细纲、规则包、改动说明、脚本报告。四项测试：

| 测试 | 人类侧真值 |
|------|-----------|
| **同构测试**（找出像同一个模子的句子，必须引用原句） | 人类表态**离散**，模型**成套**（同构率 0% vs 16.7%） |
| **删除测试**（5 处闲笔，删掉有无影响） | 人类"毫无影响" **1/5**；AI **3–4/5** |
| **作者在场测试**（划掉对话只读叙述，问"这里有一个人吗"） | 人类 3.73–8.40 vs AI 0.64–1.89 |
| **用力过猛测试**（找"像在完成任务"的表态） | 实测："更用力" = "更假" |

**判定原则**：**两个以上独立评委指向同一处 → 必改。** 要求引用原句，**不要打分**（打分会被"总体不错"这类判断污染）。

### 3.4 置信度绑定与重试三出口

**问题**：读完"这章不太行"却继续往下走，是长篇创作中最贵的动作。当检测到质量问题时，Agent 的默认反应是"在原地改一遍"——这通常不会产生质的飞跃，只是把同样的问题换一种表述重写一次。

**解法**：J-Novel 在质检完成后引入"置信度定档"机制。Agent 必须根据自评结果将本章划入三档之一：

| 读数 | 触发条件 | 义务 |
|------|---------|------|
| **稳** | 人侧 ≥7 项 且 评分 ≥70 且 无未决杠精点 | 放行 |
| **薄** | 人侧 4-6 项 / 评分 65-69 / 有 1 个未决杠精点 | **点名最薄项 + 理由**，然后放行 |
| **晃** | 人侧 ≤3 项 / 评分 <65 / retryCount ≥2 | 禁止原路重走，三选一出口 |

三选一出口：
1. **升标准**：升到锚点章标准，全调专项后重检
2. **换路**：用完全不同的原语重述"本章要完成的三件事"，重新动笔
3. **上报**：停下问用户

当 `retryCount == 2` 时，出口 C（换路）被强制触发。当 `retryCount == 3` 时，系统停止自动修复，向用户上报——因为这表明问题被错误地框架化了，继续撞墙不会有新结果。

**"薄"那一档的"点名"不是形式**：写"衔接有点弱"不算；写"第 4 节苏晚进门的情绪接不上第 3 节结尾的沉默，因为她刚得知消息就恢复常态"才算。点名一次，后面想偷懒就偷不掉了。

### 3.5 链式流水线并发协议

**问题**：并发写作（多 Agent 同时创作不同章节）是提速的有效手段，但也是最常见的质量灾难源。无脑将 30 章同时派发给 30 个子代理，等于让 30 个人各写各的——风格漂移、状态断层、衔接断裂三者齐发。

**根因诊断**：并行的单位选错了。章节之间是**链式依赖**的——第 N+1 章的开头 = 第 N 章结尾的延续（人物在哪、什么情绪、知道什么、有没有受伤）。而"一次派 5 章"时，**第 2-5 章的真实结尾还没被写出来**，子代理只能靠细纲"猜"前文。**乱序完成是章节并行的数学必然，不是纪律问题**——5 章同时开写，完成时间必然不同，加再多"请按顺序完成"的规则都没用。

**解法**：J-Novel 明确"**并行的单位是工序，不是章节**"（`guides/chained-pipeline.md`）。核心原则：**创作方向串行（主编独占），文字执行并行（子代理填字）；依赖串行保真，独立并行提速。**

```
❌ 章节并行（会崩）：
   [子代理1: 第1章][子代理2: 第2章][子代理3: 第3章]...
   → 各写各的，完成时间乱，第3章基于假的第2章结尾

✅ 链式流水线（默认）：
   初稿：第1章 → 第2章 → 第3章 → ...          ← 笔手串行，一章接一章
   打磨：         第1章 → 第2章 → 第3章 → ...  ← 磨手并行，跟着初稿跑
   缝合：               第1章 → 第2章 → ...    ← 主编串行缝合边界
```

协议的关键机制包括：

1. **三级策略**：A 链式串行（锚点章/高潮章，定稿才写下一章）/ **B 链式流水（默认）** / C 章节并行（仅"真独立章"——番外/支线日常，不承接上章结尾）。**判据一句话**：这章开头要不要接上一章结尾？要 → A/B；不要 → 可 C。

2. **接口契约冻结**：派发前主编为每章写「进入状态 / 退出状态 / 承接要素 / 交付钩子」，**契约一经派发即冻结**。子代理要偏离契约必须先申报 + 更新相邻章契约，不得自己改了往下写。**这是治"状态分叉"的关键**——把两个子代理各自心照不宣的假设，变成同一份白纸黑字的契约。

3. **前序锚点**：每个子代理写前必读：契约 + 上一章**真实结尾**（500-800 字，由主编从刚写完的正文里截取，**不是细纲的"承接自"**）+ 状态台账出场人物条目 + 文风锚点示例。

4. **锚点滚动**：每批结束后，主编从本批真实章节中抽取最代表文风的 1-2 段，更新下一批细纲的文风锚点示例——锚点跟着故事走，而非固定在第一章。

5. **三轮质检**：子代理自检（第一轮）→ 主编验收（第二轮：硬底线全查 + 锚点章细看 + 风格抽查）→ 交叉互检（第三轮：批内两两互检，只挑刺不改写）。**注意互检对象是已定稿章节**，不是还在写的。

6. **批次验收闸门**（`check_batch_gate.py`，退出码 0 才放行）：下批派发前必须跑完 6 项——① 章节完成连续性（治乱序）② 字数达标 ③ 质检痕迹齐 ④ 台账推进 ⑤ 章节边界无悬空钩子 ⑥ **崩坏红线 1**（连续 3 章同章末型/同开场类型）。**这把"主编自觉"变成了"可验证的退出码"。**

7. **人工放行**（`boundary-waived`）：`check_continuity.py` 是**提示工具，不是硬闸门**——"刻意留后章回收"是正常写法。复查后若判定正常，**不要绕过闸门**，改在 `05-创作台账.md` 写一行显式记录：`boundary-waived: 第8→9章，理由：该钩子第11章回收`。**理由少于 8 个字视为无效放行。**

**效果**：这套协议在保证叙事一致性的前提下实现了可观的并行加速——子代理在写作时不再"自由发挥"，而是基于主编提供的细纲、契约和锚点填充文字，质量上限由主编和细纲决定，不由子代理的运气决定。**连贯性由"上一章真实结尾"保证**（这是"并行单位从章节换成工序"的落地）。

### 3.6 工程化自检：把"我改了"变成"机器验证过"

**问题**：SKILL 自身的规则、脚本、文档会随时间漂移。最危险的一类失败是"**假闸门**"——看起来做了检查，实际从未触发。这类失败比"没做检查"更危险，因为它制造虚假信心。

**解法**：J-Novel 配套了两个自检脚本。

**（1）`audit_release.py`——发布前 QA，一条命令跑完八项**

| # | 检查 | 判据 |
|---|------|------|
| 1 | 引用完整性 | 所有 `guides/flows/prompts/*.md` 引用真实存在，**失效必须为 0** |
| 2 | 脚本语法 | 全部 `.py` 通过 `py_compile` |
| 3 | 阈值一致性 | **17 项**关键阈值在「脚本（唯一事实源）vs 文档」之间无漂移 |
| 4 | 调用链闭合 | **19 个**关键工具/规则每个 ≥2 处调用点（1 处 = 死工具） |
| 5 | 结构完整性 | frontmatter 齐全、代码围栏配平、`##` 标题层级干净 |
| 6 | 残留检查 | **14 个**已废弃说法无"无解释语境"的残留 |
| 6.5 | 跨脚本一致性 | 共用词表/阈值/实现一致；**含「声明-实现一致性」守卫** |
| 7 | 分离回归（`--regress`） | **人类样本全 exit=0、AI 样本至少被一个闸门拦下** |

其中 6.5 的「声明-实现一致性」守卫查五件事：⓪ 自检名单是否漏文件 ① 该 import 的共享实现是否 import 了 ② import 了是否真被调用 ②b 共用的词表是否只此一份 ③ **import 后是否被本地 def 覆盖** ④ 定义了是否真被调用。**判据一律基于"剥掉注释与 docstring 后的代码"**——否则注释里提一句函数名就能骗过守卫。

**（2）`test_guards.py`——守卫故障注入，8 例**

**"加了守卫"和"守卫有效"是两件事。** 新增或改动任何检查项后，都必须**故意把代码改坏一次，看它是否报警**：

```bash
python scripts/test_guards.py     # 退出码 0 = 8/8 全被抓到，且还原后重新全绿
```

它自动 备份 → 注入故障 → 跑 QA → 检查是否报出预期关键字 → **无条件还原** → 确认重新全绿。

**过程记录（这才是它的价值）**：人工版在自测中**连续抓到 4 个"守卫自身失效"**——用 `in src` 判断被注释骗过、守卫扫到 docstring 里的函数名、调用计数把注释也算进去、数字漂移正则不认 markdown 的 `**14 个**`。**每一个都是"我以为守卫有效"。**

| 分布 | 中文量词密度 | 7.04–8.76/千字 | | | |
| 分布 | 长对话（≥30字）占比 | 15.8–27.7% | | | |
| 分布 | 数字密度 | 1.16–3.15/千字 | | | |
| 分布 | 现实锚定计量 | 0.07–0.72/千字 | | | |
| 在场 | 作者在场指数 | 3.73–7.84 | | | |
| 闸门 | 硬性句式（不是X，是Y） | ≤0.12/千字 | | | |

**早期版本中最值得注意的是"情绪词密度"与"身体部位密度"两个指标**：在 2026-08-29 版本修订前，这两个指标呈现典型的"补偿式偏移"——情绪词只有人类的 1/5–1/2（0.07–0.17），身体部位却是人类的 5–7 倍（1.64–2.38）。根因是旧规则"不允许出现情绪词汇"被顶格执行。修订后改为"三种写法配比"（直说 / 动作对话 / 身体反应），情绪词回到 0.25–0.5 区间、身体部位压回 ≤1.0。

**连续性检测**：`check_continuity.py` 用于检测"钩子人物在下一章开头缺席"的边界。在批次放行前由 `check_batch_gate.py` 调用，退出码 1 = 有边界需人工复查（`boundary-waived` 显式放行除外）。

### 4.3 定性评估

**叙事连贯性**：`03-状态台账.md` 逐章跟踪人物状态与伏笔动作，配合 `05-创作台账.md` 的 Verified 编号记录，在 Phase 5 的"台账对账"环节逐条回正文核对。**这一步查的是"我以为写过的，是不是真写进去了"**——一致性通读查正文内部的矛盾，台账对账查台账与正文之间的矛盾。

**文风统一性**：锚点滚动机制保证后序章节对前序文风的继承。锚点示例取自最近确认的真实章节片段，而非第一章的老腔调。

**AI 味诊断**：11 项 AI 味自评量表 + 独立质检子代理（同构/删除/作者在场/用力过猛）共同执行。**需注意脚本全绿 ≠ 像人写的**——见 §3.3 的 A/B 实测证据。

### 4.4 限制说明

1. **规模限制**：当前实证案例的章节数（7-12 章）不足以完全验证框架在 50+ 章长篇中的抗漂移能力，尽管机制设计本身（Seam 重读、锚点滚动、台账对账）指向了可扩展性。

2. **无对照实验**：本文未进行"有/无 J-Novel 机制"的系统性 A/B 对照实验。已有的是针对单条规则的小规模 A/B（如作者在场规则的 v4.2 vs v4.3，见 CHANGELOG），无法量化每个单独机制的边际贡献。

3. **读者反馈缺失**：Reader Simulator 子技能目前只在卷终/完稿由主编组织完整调用，尚未集成为自动化的读者反馈管道。

4. **基线选择偏差**：人类基线取自三部商业化男频网文，其默认审美（用「道」不用「说」、面板结算、爽点密度、一句一段）带题材偏向。写女频、严肃文学、悬疑冷峻派时需用 `--baseline` 重算。

## 5. 局限性与未来工作

### 5.1 当前局限性

**（1）指标耦合**：17 项指标不是正交的。实测（《第0号存档》第 11 章 A/B，三轮）：补长句会把明喻从 1.1 挤到 2.38、补数字会把情绪词挤到 0——**14 项指标耦合，改一项会牵动别项**。配额卡治"缺什么"很灵，治"耦合失衡"要配合一次批量精修。生产流程按两段走：① 生成时用配额卡把大头压住 → ② 复跑脚本 → ③ 只对残留的 2–3 项做一次批量精修。**不要为了全绿无限迭代**——那是新的微步循环。

**（2）执行负荷与成本**：完整流程（Phase 0-5）对 Agent 的认知负荷要求较高。每章的 10 步最小必做清单、质检脚本调用、台账回写等操作在串行模式下会增加单章处理时间。**成本纪律（铁律九）是必需的配套**——历史违规项目是 63 次调用/章、6 章烧掉 45.4M tokens（97.8% 是上下文重发，放大 135 倍）；目标 10–18 次/章。对于短篇创作（<5 章），该框架可能显得"过度工程化"——入口闸门（轻/中/重）是对此的缓解，但"轻"档的收益尚未量化。

**（3）基线泛化性**：句法层阈值基于三类男频网文计算，其人类基线可能不适用于严肃文学、诗歌化散文或轻小说译文体。`--baseline` 参数允许用户重新校准，但增加了使用门槛。

**（4）并发模式复杂度**：`subagent-parallel` 模式下的主编职责清单（接口契约冻结、锚点滚动、依赖图标注、边界缝合、交叉互检组织）对主编 Agent 的质量要求极高。**主编本身仍是单点瓶颈**——把契约定义外包出去等于放弃质量上限。

**（5）自检覆盖面**：`audit_release.py` 的「声明-实现一致性」守卫查四份共享脚本（`check_human_rhythm` / `check_aistyle` / `check_chapter_wordcount` / `check_continuity`），但 `check_repetition.py`、`convert_to_txt.py`、`check_batch_gate.py` 各有独立的读盘实现，未纳入名单。这是已知的覆盖缺口。

### 5.2 未来工作方向

1. **共享实现全覆盖**：把剩余脚本的读盘/取正文统一到 `_shared.py`，并纳入 `_SHARED_FILES` 自检名单。

2. **读者反馈集成**：将 Reader Simulator 升级为完整的读者反馈管道，在 Phase 4/5 中自动生成三层读者验证报告（普通读者/挑剔读者/作者同行），并纳入全书质量报告。

3. **多卷长篇验证**：在 50 章以上的长篇项目中运行完整流程，收集 Seam 重读的有效性数据，为框架的可扩展性提供定量证据。

4. **跨题材基线研究**：扩展人类基线数据库，覆盖言情、悬疑、轻小说、历史等更多题材，使阈值自适应。

5. **有效性的正式 A/B**：对 `review-agent`（独立质检子代理）做系统的 A/B 验证——同一章，一组只跑脚本、一组跑脚本 + 独立质检并按其意见修改，然后盲评对比。**这是当前遗留清单里优先级最高的一项。**

1. 将 J-Novel 作为 Skill 安装到 Agent 宿主环境中
2. 在目标工作目录下创建 `novel-output/` 文件夹
3. 调用该 Skill，Agent 自动进入 Phase 0 初始化
4. 用户提供创作想法后，Agent 按 Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 顺序驱动流程


**成本自查（长跑中定期）：**

```bash
python scripts/audit_tokens.py <项目目录> --chapters N
```

## 7. 结论

本文提出了 J-Novel，一个面向 AI Agent 的长篇小说创作框架。该框架的核心贡献在于将"过程层状态管理"引入了叙事生成任务，通过五字段创作台账、事实三态标记、Seam 重读、三层量化质检（17 项硬指标 + 独立质检子代理）、链式流水线并发协议，以及 SKILL 自身的工程化自检（`audit_release.py` + `test_guards.py`），系统性地解决了 LLM 在长篇创作中面临的三类最昂贵的事故：连续性错觉、长跑漂移和 AI 味顽固复发。

该框架最值得记录的一条工程经验是它在 `CHANGELOG` 中反复出现的**同类错误模式**：

> **底线当目标 → 配额当目标 → 方向当强度 → 真指标做成配额也会变模板。**

同一类错误出现四次（句长"≥18"被写成目标 → 毛边"≥2 处"生产填充物 → "用「道」"被 92% 挂满 → 作者在场指标 0→7.93 达标但盲评判负），每次都有实测证据。最后的统一结论是：**任何数量配额都会被模型填成同构模板，所以修的不是数量，是结构。**

在两部完整小说的实证验证中，J-Novel 产出的文本在句法层与分布层指标上趋近人类基线（具体数值见 §4.2，需与实际质检档案核对），同时消除了传统 AI 创作中常见的逻辑断裂与模板化表达。该框架已在生产环境中完成了端到端的验证。
