## 摘要

### 先说人话

让 AI 写一部长篇小说，它会稳定地犯三个毛病：

1. **记不住**——写了二十章之后，它会忘记第五章埋的那个伏笔到底写没写，然后把它当成"已经发生过的事"继续往下编；
2. **跑偏**——开头五章和最后五章读起来不像同一个作者写的，而写作过程中没有任何一步会告诉你"你已经偏了"；
3. **不像人写的**——句子越来越短、越来越整齐、对话越来越"对"，每一句都在推进情节，一句废话都没有。**这种"太干净"本身就是最大的破绽。**

J-Novel 就是给这三个毛病各配一副药。它的核心主张是：**这三件事都不该靠"提醒模型注意"，而该靠工程机制**——把状态写进文件、把"像不像人"变成退出码、把并行写作的单位从"章节"换成"工序"。

### 展开说

大规模语言模型在长文本创作中展现出巨大潜力，但当任务规模超过单次上下文窗口时，系统性失效模式开始显现：叙事连续性断裂、文风漂移、以及机器生成痕迹的顽固复发。现有解决方案——上下文窗口扩展、链式推理提示、通用型 Agent 框架——均未从根本上解决这三个问题，因为它们缺乏对**创作过程本身的状态管理**。

本文提出 J-Novel，一个融合了过程层状态管理的端到端小说创作框架。核心贡献：（1）引入"创作台账"作为 Agent 的外接工作区，实现每章边界强制重读（Seam Re-reading）；（2）提出"事实三态标记"（✓/?/✗），将"已落正文"、"仅规划"与"已被否定"物理分离；（3）建立句法与分布两层的量化质检体系（17 项指标 + 一道硬性句式闸门），并配套独立质检子代理补足脚本测不出的语义层；（4）设计以**工序**而非**章节**为并行单位的链式流水线协议，通过接口契约与边界冻结保证叙事一致性；（5）提出机制的"三站齐备"判据（生成点／交付点／校验点）与工业化的良率-帕累托闭环，把"改了哪条规则"从凭感觉变成看数据。

**关键词**：AI 辅助创作 · 长文本生成 · 叙事连续性 · 过程管理 · 质量控制 · 多 Agent 协作

## 1. 引言

### 1.1 问题背景

#### 先说人话

写一个短篇，AI 表现得很好。写一部长篇（十万字以上、几十章），它就开始出问题。**问题不在于"它不会写句子"，而在于"它管不住自己"。**

打个比方：短篇像让一个人写一张便条；长篇像让一个人连续工作三个月，中间不许看他之前写过的任何东西——只允许他凭记忆。

#### 三个结构性痛点

**痛点一：连续性错觉（Continuity Illusion）**

在跨越数十章的创作中，模型必须记住大量事实：人物位置、情绪状态、已知信息、伏笔状态、时间线。当信息量超过有效工作记忆时，模型会**基于近期上下文做推断**，而这些推断可能与数十章前确立的事实矛盾。

**这种矛盾不触发任何错误信号**——模型不会"报错"，它只是安静地产生了一个逻辑 BUG。最坏的情况是：第 5 章登记的伏笔，第 20 章被当作既成事实引用，而该伏笔从未真正写进正文。

**痛点二：长跑漂移（Long-haul Drift）**

文风不是由单一规则定义的，而是由大量微观决策（词汇选择、句法节奏、叙述者距离、修辞偏好）共同构成的分布。长篇创作中这些决策会随时间逐渐偏移。当偏移累积到一定程度，小说前五章和后五章读起来像两个不同作者写的——**而写作过程中的任何一步都不会显式报告这种漂移**。

**痛点三：AI 味顽固复发（AI-flavor Recidivism）**

"AI 味"不是某一种具体错误，而是一组统计层面的异常：过高的句首代词比例、过密的破折号插入语、过度的身体部位描写、过少的情绪词直说。

**当规则以"禁止 X"的形式给出时，LLM 的典型反应是换一种方式表达 X**——从而在规避表面规则的同时产生新的、更隐蔽的统计异常。这就是为什么单纯依赖"去 AI 味提示"往往治标不治本。

### 1.2 现有工作及其局限

#### 先说人话

三类现有方案，各自解决了一部分，但都没解决"过程管理"这一层。

#### 展开说

**（1）上下文窗口扩展。** 以 GPT-4 128K、Claude 200K 为代表，通过扩大窗口让模型"看到更多"历史。这缓解了短期遗忘，但无法解决根本问题：注意力在长序列中呈稀疏分布，关键信息可能被淹没；且窗口总有上限。

**（2）通用型 Agent 框架。** 如 LangChain、AutoGPT，提供工具调用、记忆存储、任务规划等通用能力。但它们的设计目标是"通用任务执行"，而非"文学创作"。它们缺乏对叙事特殊性的理解——例如小说中的"人物状态"与"待办事项"有着本质不同的更新语义，通用记忆模块无法区分**"已落正文"**与**"仅规划"**之间的关键差异。

**（3）小说写作辅助工具。** 如 Sudowrite、NovelAI，提供优质的文本生成与润色能力，但通常以"单次生成"为交互单元，缺乏对跨章连续性和过程状态的系统化管理。用户仍是整个流程的核心调度者。

### 1.3 本文贡献

#### 先说人话

五件事：给 AI 一个外接的工作台、给"写没写过"定三态、把"像不像人"变成数字、把并行单位从章节换成工序、给机制本身定一个"生效判据"。

#### 展开说

1. **提出"创作台账"作为 Agent 外接工作区的概念**，将"故事的状态"与"Agent 自身的认知状态"物理分离，并在每章边界强制执行 Seam 重读，从系统层面防止静默状态丢失。

2. **建立"事实三态标记"系统**（✓/?/✗），将叙事事实的认知状态显式编码到项目管理文件中，消除"规划"与"执行"之间的语义混淆。

3. **构建两层量化质检体系**：句法层与分布层共 17 项可自动化验证的指标，配套一道硬性句式闸门；在此基础上引入**独立质检子代理**，通过四项语义测试（同构／删除／作者在场／用力过猛）补足脚本无法覆盖的那一半。

4. **设计以"工序"为并行单位的链式流水线协议**，通过接口契约冻结、边界冻结、缺陷路由与批次验收闸门，在保证叙事一致性的前提下实现多代理并行加速。

5. **提出机制的"三站齐备"判据**（生成点／交付点／校验点）与**工业化的良率-帕累托闭环**（`make_workorder.py`），把"该改哪条规则"从主观判断变成数据驱动。

## 2. 系统架构概述

### 2.1 六阶段流水线

#### 先说人话

把"写一本书"拆成六段，每段有明确的完成标志（清单打勾 + 产物齐全），不许跳段。

#### 展开说

| 阶段 | 名称 | 核心任务 | 出口条件 |
|------|------|---------|---------|
| Phase 0 | 初始化 | 加载用户偏好、检测未完成项目、恢复状态 | 清单全勾 + 入口判定完成 |
| Phase 1 | 深度采访 | 五层挖掘（情绪/动机/期待/想象/盲区），磨出 12 项验收清单 | 验收全过 + 故事速写经用户确认 |
| Phase 2 | 规划与确认 | 生成故事圣经、人物档案、分章大纲、写作计划 JSON、台账 | 清单全勾 + 锚点章定调确认 |
| Phase 3 | 疯狂创作 | 逐章或链式流水线执行"写-审-改-锁"循环 | 全部章节 completed |
| Phase 4 | 自动校验 | 字数/质检痕迹/节律/统计指纹/连续性检测；按重试三出口修复 | 全部章节 PASS + 完成报告 |
| Phase 5 | 完稿润色 | 一致性通读、台账对账、节奏评估、开篇重审、资产沉淀 | 清单全勾 + 全书完成总结 |

每个阶段的入口处设有「执行清单」，Agent 必须逐项打勾才能进入下一阶段。**清单机制的设计目的是防御"流程跳步"**——长流程中 Agent 倾向于跳过自认为"已熟悉"的步骤，而清单把"已做"与"未做"的边界显式化。

### 2.2 六份状态文件：文件化状态管理

#### 先说人话

AI 的"记忆"不可靠，所以把所有状态**落盘**。分成六份，各管一件事——谁是谁、要发生什么、还剩什么没做、故事里现在到哪了、这一章查过了什么、我自己知道什么。

#### 展开说

J-Novel 的核心设计原则是**所有状态必须落盘**。项目目录下的六份文件分别承载不同维度的状态：

| 文件 | 管理内容 | 回答的问题 | 更新者 |
|------|---------|-----------|--------|
| `00-人物档案.md` | 角色静态设定 | 这个角色是谁？ | 规划阶段一次性写入 |
| `01-大纲.md` | 章节规划与摘要（含章末型/开场类型两列） | 每章要发生什么？ | 规划写入，写作后追加摘要 |
| `02-写作计划.json` | 项目进度与模式开关 | 还剩什么没做？ | 每章更新 |
| `03-状态台账.md` | 故事内动态状态 | 现在故事里发生了什么？ | 每章写回 |
| `04-质检档案.md` | 每章的人写判断 | 这一章查了什么、结果如何？ | 每章追加 |
| `05-创作台账.md` | Agent 的认知状态 | 我现在确认了什么/不确定什么？ | 每章 seam 重读与回写 |

> **另有一份 `06-章节工单.md`**（v6.5 新增），由脚本自动追加，记录机器度量（机械结论/缺陷类型/返工轮次）。它与 `04-质检档案` **刻意分开**：`04` 是人写的判断，`06` 是机器写的度量。混在一起会互相覆盖（实测踩过一次，把用户项目里 9 列数据覆盖成 6 列）。

**`05-创作台账.md` 是本框架最核心的创新。** 它不记录"故事里发生了什么"（那是 `03-状态台账.md` 的职责），而是记录**"Agent 认为自己知道了什么"**。

这个区别至关重要：当上下文窗口滚动、早期信息被压缩时，Agent 仍可以通过重读 `05-创作台账.md` 恢复自身的"认知状态"，从而避免"静默丢弃约束"。

```
# 创作台账（每次 seam 重读）
最近重读章号：第X章
本章返工轮次（retryCount）：0

## Goal
一句话，本阶段"完成"意味着什么，能判断自己到没到。

## Core
≤2 条。第三条想进来必须先换掉一条，且换的时候要说出声。
- 文风锚点 —— [一句话 + 它为什么重要]
- 本卷张力 —— [一句话 + 它为什么重要]

## Verified
编号追加，永不改写。每条写清依据。
- ✓01 [已落正文的既成事实]（依据：第X章）

## Open
每条带"什么能终结它"。
- ?01 [还不确定什么] —— settled by: [什么能终结它]

## Next
单一动作，永不为空。
```

### 2.3 执行契约（九条铁律）

#### 先说人话

这是一份"宪法"。前四条管**交出去的东西合不合格**，后五条管**在长跑中你还醒不醒着**。后者才是长篇里真正致命的那一类——因为前面四条失效时会报错，后五条失效时不会。

#### 展开说

| 编号 | 铁律 | 核心内容 |
|------|------|---------|
| 1 | 【必须】读流程 | 进入任何 Phase 先读对应流程文件，按执行清单逐项执行 |
| 2 | 【必须】不跳步 | 标注【必须】的步骤不可跳过/合并/简化 |
| 3 | 【必须】读指南 | 关键动作前必读对应 guides 文件 |
| 4 | 【必须】固定排班 | 检查型工具到点必调，自检"没问题"不是跳过理由 |
| 5 | 【必须】三态标记 | 标 `?` 的条目，下游章节不得当作已发生的事实来写 |
| 6 | 【必须】Seam 重读 | 每章边界重读 `05-创作台账.md` 五段后再动笔 |
| 7 | 【必须】置信度绑定 | 读到「晃」禁止原路重走，三选一换路 |
| 8 | 【必须】注册分离 | 正文里不得出现细纲记号、质检字段、未展开的缩写 |
| 9 | 【必须】成本纪律 | 调用次数是成本主杠杆——一次跑完全部脚本、一次批量改写、不重读指南、子代理只读速查卡 |

**铁律 5–9 是本框架区别于其他系统的关键**：它们不直接作用于产物，而是作用于 Agent 在写作过程中的"认知纪律"。

其中铁律 9 针对一个反直觉的事实——**长篇成本不由"写了多少字"决定，而由"来回折腾了多少次、每次带多重的上下文"决定**。实测基线（471 个会话 / 8,457 次调用）显示：prompt（每轮发出的上下文）占 99.7%，其中 98.7% 是缓存重发；模型实际产出只占 0.30%；**每次调用平均重发上下文的中位数是 149,675 tokens**。

## 3. 核心机制详解

### 3.1 事实三态标记系统

#### 先说人话

给每一件"故事里的事实"标一个状态：**写过了（✓）/ 只是打算写（?）/ 后来推翻了（✗）**。规则只有一条：标 `?` 的东西，后面的章节不许当成"已经发生"来写。

**代价是每行多敲一个字符，收益是根除"我以为这条已经写过了"这类最贵的 BUG。**

#### 展开说

**问题**：长篇创作中最昂贵的一类 BUG 是"我以为这条已经写过了"。规划阶段登记了某个伏笔，写作到第 20 章时，模型基于上下文中的规划记忆将其当作既成事实引用，而该伏笔实际上从未被写进正文。**这种错误不触发任何异常信号。**

**解法**：强制状态台账与伏笔对照表中的每一条目携带状态位。

| 标记 | 含义 | 约束 |
|------|------|------|
| `✓` | 已在正文中明确写出 | 标注依据章号，可追溯 |
| `?` | 仅规划或推断，尚未落正文 | 下游章节**不得**以此为前提 |
| `✗` | 已被后续剧情否定 | 不删除、不覆盖，保留证据链 |

**默认无标记 = `?`。** 这一设计将"规划"与"执行"在语义层面强制分离。

在 Phase 3 的每章收尾步骤中，Agent 必须扫描本章正文，将真正落地的条目从 `?` 更新为 `✓（第X章）`，并在 `05-创作台账.md` 的 Verified 字段中追加编号记录。

**效果**：三态标记不依赖模型的"记忆"，而依赖文件系统的持久化和每章收尾时的强制检查。它从工程层面切断了"记忆混淆导致逻辑 BUG"的因果链。

### 3.2 Seam 重读机制

#### 先说人话

每写一章之前，花 30 秒把 `05-创作台账` 从头到尾读一遍——不是只读最后一行。

**为什么值得这 30 秒**：注意力能平等触达上下文里的任何 token，但**只在那个 token 还在你眼前的时候**。连写十几章不重读，会发生三件不会报错的事：文风锚点被悄悄换掉、伏笔"写过了"和"打算写"记混、排班专项查没查全凭印象。

**不重读的台账比没有台账更糟——因为它看起来像状态。**

#### 展开说

**问题**：即使在文件化状态下，Agent 仍可能在长跑中"静默丢失约束"。

**解法**：在每章创作的入口处（Phase 3 步骤 0.5）强制执行 Seam 重读——用不超过 30 秒完整读取 `05-创作台账.md` 的五段全部内容（Goal / Core / Verified / Open / Next），并在动笔前更新 Next 字段。

**Core 字段的"≤2 条"限制**进一步强化了这一机制：超过两条的 Core 会被稀释，每条只能分到不到二分之一的注意力。第三条想进入 Core 时，Agent 必须**说出口**（"放下 X，拿起 Y"），将离开的那条写入 Verified 或 Open。

这一"出声"操作防止了**静默丢弃（Silent Drop）**——即某个约束在任务中途悄悄停止生效，而 Agent 没有意识到它的消失。

### 3.3 句法层与分布层量化质检

#### 先说人话

"读起来像不像人写的"是主观判断，Agent 可以用"我觉得没问题"糊弄过去。**数字不行。**

所以拿三部真人写的小说（合计约 1200 万字）当尺子，量出 17 个指标，每个都有硬阈值。跑一次脚本，退出码 0 还是 1，没有争论余地。

**但脚本全绿 ≠ 像人写的**——这一点文档里有硬证据（见 3.4）。

#### 展开说

**基线来源**：三部人类作者全书实测——齐佩甲《超神机械师》（系统流·男频快节奏，540 万字）、三天两觉《惊悚乐园》（无限流·吐槽话痨，405 万字）、柳岸花又明《我真没想重生啊》（都市重生·轻松，268 万字）。三样本覆盖三种风格，避免被单一作者带偏。

**句法层九项**（`check_human_rhythm.py`）：

| 指标 | 人类范围 | 硬阈值 | 方向 |
|------|---------|--------|------|
| 句首代词占比 | 1.5–10.4% | ≤15% | max |
| 句首引号占比 | 18.4–30.6% | ≥15% | min |
| 平均句长 | 22.7–36.6 字（均值 30.8） | ≥18 字（**底线**） | min |
| 破折号密度 | 0.03–0.29/千字 | ≤1.5/千字（软线 0.5） | max |
| 身体部位密度 | 0.31–0.55/千字 | ≤1.0/千字 | max |
| 情绪词密度 | 0.32–0.35/千字 | 0.25–0.5/千字 | **range** |
| 明喻密度 | 1.05–1.27/千字 | 0.8–1.5/千字 | **range** |
| 对话占比 | 20.4–33.5% | ≤40%（护栏） | max |
| 动作短语密度 | 0.106–0.247/千字 | ≤0.4/千字 | max |

> ⚠️ **平均句长一项最容易被误读**：脚本的 `hard=18` 是**判不合格的底线**（用于拦最极端的碎句），而**写作目标是 23–37 字的区间**。把底线当目标会让模型写到 19–22 字就自以为达标——这是本项目历史上反复踩过的一类错误（文档里称之为"底线当目标"，同类错误至少出现过四次）。

**分布层七项**（治"均值达标但读起来仍像 AI"）：

| 指标 | 人类范围 | 硬阈值 | 方向 |
|------|---------|--------|------|
| 超长句(≥60字)占比 | 4.7–19.0% | ≥3% | min |
| 句长 p90 | 48–74 字 | ≥42 字 | min |
| 节奏变异系数 | 0.251–0.321 | ≥0.19 | min |
| 中文量词密度 | 7.04–8.76/千字 | ≤10.5/千字 | max |
| 长对话(≥30字)占比 | 15.8–27.7% | ≥8% | min |
| 数字密度 | 1.16–3.15/千字 | ≥0.8/千字 | min |
| 现实锚定计量 | 0.07–0.72/千字 | ≥0.05/千字 | min |

> 现实锚定一项对架空/游戏世界观豁免（人类《惊悚乐园》仅 0.07，因其世界观里没有钱）。

**第 17 项：作者在场指数**（区间 2.5–12）。把引号里的对话全部剥掉，只统计**叙述部分**的叙述者人格痕迹——评价副词（其实/居然/简直）×1 + 口语插话（说白了/反正）×3 + 吐槽贬称（这货/欠揍）×3 + 语气词×1，再加叙述句里 `？`/`！` 占比×0.5。

人类 3.73–7.84；AI 全书仅 0.64–1.89；A/B 盲测稿为 0.00–0.75。**这是本体系分离度最高的判别器。** 根因：AI 的叙述是透明的，只报告事件、不表态。

**硬性句式闸门**（`check_aistyle.py` 退出码的唯一驱动项）："先否定再肯定"结构（"不是X，是Y"）单句硬线 **0.12/千字**、跨句硬线 **0.40/千字**。

> **实测教训**：原版只匹配「不是…而是…」，结果 AI 学会了绕开"而是"、改用"是"——人类 0.087/千字 vs AI 0.011/千字，旧规则完全失效（AI 反而更少）。现版本同时覆盖同句变体与跨句变体。

**非阻塞弱信号**：单句成段占比、最长句、对话占比过低、通用模板短语密度等。其中「通用模板短语」专指"一个人""这一刻""走廊里"这类任何小说都能套用的泛化表达——**人类的高频词是专有名词（陈汉升、三大文明），AI 的高频词是通用模板词**。

**"人类区间命中率"**：2026-09-15 新增的读数。它回答的是**"离人类有多远"**，与退出码回答的"有没有硬伤"是两个不同问题。

> 实测教训：某真实项目 10 章**全部退出码 0**，但命中率只有 29–47%——平均句长低于人类下沿 10/10 章、动作短语 10/10 章（值为 0.0）、长对话 9/10 章。**"全绿"被读成了"达标"，实际是系统性欠写。**
>
> 阈值经重标定（人类单章中位 35%，硬线 ≥20%）——原阈值 50/70 会把 **89% 的真实人类章节判掉**，因为它是在"整本书"尺度上量的却用在"单章"上（尺度混淆）。

### 3.4 独立质检子代理：脚本测不出来的那一半

#### 先说人话

脚本能测频率，但测不出**"这三句话是不是同一个模子"**。

有一个硬证据：某一版加了新规则后，作者在场指数从 0 涨到 7.93（完美落在人类区间），**但盲评以 3:0 判负**——三位评委各自独立地从同一文件里挑出同一组三句，指出它们是"同一个模子的三次填空"。

**指标完美达标，读起来却更假了。**

所以另起一个子代理，**只给它纯正文**，让它读一遍，回答四个问题。

#### 展开说

**核心是「独立性」铁律**——质检子代理的价值全部来自"它不知道你是怎么写的"：

| 必须做 | 绝对不能做 |
|---|---|
| 只给**纯正文**（标题 + 正文，无任何元数据） | ❌ 不给细纲、大纲 |
| 每个质检子代理**独立启动**（新上下文） | ❌ 不给规则包、不告诉它"我用了什么规则" |
| 多个子代理时**各自独立**、互不可见 | ❌ 不给"我这次改了什么" |
| 让它自己判断，不给结论暗示 | ❌ 不给它看脚本报告（那会锚定它） |

**四项测试（全部要求引用原句，且明确"不要打分"）**：

| 测试 | 人类侧真值 |
|---|---|
| **同构测试**（找出像同一个模子的句子） | 人类表态离散；模型成套（同构率 0% vs 16.7%） |
| **删除测试**（5 处闲笔，删掉有无影响） | 人类"毫无影响" 1/5；AI 稿 3–4/5 |
| **作者在场测试**（划掉对话只读叙述，问"这里有一个人吗"） | 人类 3.73–8.40 vs AI 0.64–1.89 |
| **用力过猛测试**（找"像在完成任务"的表态） | 实测："更用力" = "更假" |

**判定原则**：**两个以上独立评委指向同一处 → 必改。**

这四项都是**加法式／定位式**判据，不是打分式的，因此难以被"凑一个高分"hack——你没法伪造"这三句不是一个模子"，而"没有"也是有效答案。

**自适应抽检**（v6.5 新增）：连续 0–2 章合格 → 全检（四项全做）；**连续 ≥3 章合格 → 只做「同构 + 作者在场」**；任一项失败 → 立刻回全检、计数归零。这是工业的跳批检验：省的是顺风局的重复劳动，不降保证水平。

### 3.5 置信度绑定与重试三出口

#### 先说人话

改完还是不行的时候，最常见的错误动作是**"在原稿上再改一遍"**——这通常不会产生质的飞跃，只是把同样的问题换一种说法重写。

所以定三档：**稳**（放行）/ **薄**（点名最薄的一项，放行）/ **晃**（禁止原路重走）。

读到「晃」就必须三选一：升标准全调、换路重进入、停下问用户。

#### 展开说

| 读数 | 触发条件 | 义务 |
|------|---------|------|
| **稳** | 人侧 ≥7 项 且 评分 ≥70 且 无未决杠精点 | 放行 |
| **薄** | 人侧 4-6 项 / 评分 65-69 / 有 1 个未决杠精点 | 点名最薄项 + 理由，然后放行 |
| **晃** | 人侧 ≤3 项 / 评分 <65 / retryCount ≥2 | 禁止原路重走，三选一出口 |

**三选一出口**：
1. **升标准**：升到锚点章标准，全调专项后重检
2. **换路**：用完全不同的原语重述"本章要完成的三件事"，重新动笔
3. **上报**：停下问用户

当 `retryCount == 2` 时，出口 C（换路）被强制触发，且禁止沿用上一稿的场景顺序与开场类型。当 `retryCount == 3` 时，系统停止自动修复并向用户上报——因为这表明**问题被错误地框架化了**，继续撞墙不会有新结果。

**效果**：置信度绑定机制阻止了"无限原地重写"的循环，将 Agent 从局部最优解中强制释放。

### 3.6 链式流水线：并行的单位是工序，不是章节

#### 先说人话

并行写作是个陷阱。看着很美——一次派五个人各写一章——但**第二个人不知道第一个人最后写了什么**。

因为章节是**链式依赖**的：第 N+1 章的开头必须是第 N 章结尾的直接延续（人物在哪、什么情绪、知道什么、有没有受伤）。而"一次派五章"时，第 2–5 章的真实结尾还不存在，子代理只能拿细纲里的"规划结尾"充数。

**正确做法**：让一个笔手一章接一章地串行写初稿（它天然持有上一章的真实结尾），让另一个磨手在**后面**并行打磨已经交稿的章节。**初稿串行，打磨并行。**

#### 展开说

**三个硬事实**（决定了章节并行必然失败）：

1. **章节是链式依赖的**——第 N+1 章的开头必须是第 N 章结尾的延续。
2. **乱序完成是章节并行的数学必然，不是纪律问题**——5 章同时开写，完成时间必然不同。加再多"请按顺序完成"的规则都没用。
3. **契约不冻结，状态就会分叉**——第 2 章的子代理写到一半改了个设定，第 3 章的子代理还在按旧设定写。两章各自都对，拼起来就错。

**三级策略**：

| 档 | 名字 | 初稿 | 打磨 | 适用 |
|---|---|---|---|---|
| **A** | 链式串行 | 串行 | 串行（定稿才写下一章） | 锚点章、卷末高潮；追求零瑕疵 |
| **B** | 链式流水（默认） | 串行 | 并行（磨手跟着初稿跑） | 绝大多数章节 |
| **C** | 章节并行 | 多章并行 | 多章并行 | 仅"真独立章"（番外／支线日常） |

**判据**：一章能否进 C 档，只问一句——**"这章的开头需要接上一章的结尾吗？"**

**配套机制**：

- **接口契约（冻结）**：派发前，主编为每章填一份契约（进入状态／退出状态／承接要素／交付钩子），逐项写死。子代理若要偏离契约，必须先申报 + 主编裁决 + 更新相邻章契约。这把两个子代理各自心照不宣的假设，变成了白纸黑字的同一份契约。
- **边界冻结**：契约管状态，交接卡管**文本**。章节的首段 + 末段是**接口**，只有主编能动——磨手打磨交接段之外的一切。因为磨手改结尾会让下一章承接的结尾被掉包（两个都"对"，拼起来断，当场没有任何脚本会报）。
- **主编零正文**：主编从**读正文**改为**读交接卡**（由 `make_handoff.py` 从正文裁出的 ≤800 字：上章真实结尾 + 本章首段/末段 + 指纹）。每章进入主编上下文的量从约 6000 字降到约 800 字，且**不再随章数累积**。
- **三道闸门**：**章闸**（每章，单章机械项，0 token）→ **窗闸**（每章，滚动窗口 3 章的跨章项，0 token）→ **批闸**（每批，判断项 1 次调用 + 全批视野）。
- **流量控制**：笔手最多**领先磨手 3 章**。这个数与窗闸窗口**必须相等**——因为「窗口 = 领先上限」⟺「发现缺陷时被污染的章还没定稿」⟺「只向前修是安全的」。它们不是两个可各调各的旋钮，是同一个数的两个约束。

**判据**：**质量闸门的位置必须满足——发现缺陷的时点 ≤ 该缺陷被"定稿"的时点。** 晚一步，修复就从"在队列里改"变成"回头改"。

### 3.7 机制的三站齐备（元机制）

#### 先说人话

一个规则要真正生效，必须走完三站：

1. **生成点**——这条信息在哪一步被产出？
2. **交付点**——它怎么进入执行者的上下文？
3. **校验点**——怎么知道它被遵守了？

**缺任何一站，机制就死了**，而且死法不同：缺生成点 = 不存在；缺交付点 = 看不到；缺校验点 = 不可证伪。

#### 展开说

这一判据来自一次一致性机制审计。审计方法：全库解析路径引用找孤儿／断链，端到端执行验证（在真实项目上按文档写的命令原样跑每个脚本），以及两套清单逐项对照。

**结果出乎意料：项目不缺机制，缺的是机制走完全程。** 文风线六项机制里只有一项三站齐全。

| 机制 | 缺的是 | 修法 |
|---|---|---|
| **接口契约**（并行写作的主逻辑机制） | 生成点 + 校验点 | 细纲规格加「接口契约（冻结 · 机器可读）」键值栏位；新增 `check_contract.py` 做相邻章状态 diff |
| **锚点滚动**（主力文风机制） | 交付点 | 全库只有 3 处提及，**两套执行清单都没有它** → 进 SKILL.md 新增的批末动作 |
| **句法目标表**（可测量锚） | 交付点 | Phase 2 算完就被三个下游全部忽略 → 任务包新增「批次全局三件套」内联 |
| **累积漂移** | 校验点（设计缺陷） | 三层锚：`--vol-base` / `--book-base` |
| **意象使用记录** | **三站全缺（唯一真孤儿）** | 脚本化：`check_repetition.py --imagery` |

**契约的例子最能说明问题**：并行写作里，第 N+1 章的写手看不到第 N 章正文，只能靠契约知道"第 N 章结束时人物在哪"。实测核对：`outline-template.md` 搜「契约」= 0；`scripts/` 搜「契约」= 0。**而它在文档里有 12 处引用。** 读点齐全恰恰是最危险的状态——它让人以为这条机制很可靠。

**三层锚的例子说明"设计缺陷"是什么**：只给批锚时，**累积漂移在定义上不可见**——批 1 比第 1 章、批 2 比第 11 章、批 10 比第 91 章：每批都合格，全书可以漂到任意远。而"读着不像开头那本书了"恰恰不是批内问题，所以每一道批级闸门都放它过去。修法不是取消批锚（那会把声音的自然演化误报成漂移），而是**两层都报**。

### 3.8 工业化工单与良率闭环

#### 先说人话

总成本 = 单件成本 ÷ 一次合格率。

**而这条链此前只有分子、没有分母**——质量账是人肉抄的、成本账在平台侧，两账没有共同的键，"哪一章最贵""改了几轮"都答不出来。

v6.5 把结论落成机制：**建工单、量良率、给耦合指标一个终止条件**。

#### 展开说

**① `make_workorder.py` —— 每章质检那一步的入口**

```bash
python scripts/make_workorder.py <项目> --archive <章号> --retry <返工轮次>   # 每章一次
python scripts/make_workorder.py <项目> --report                            # 批末一次
```

- **一条命令 = 质检 + 归档**：内部跑完全部机械脚本，按**退出码**判定缺陷类型，追加一行工单到 `06-章节工单.md`。
- **`--retry` 让 `retryCount` 第一次落盘**。此前它只存在于铁律七的规则描述里（「==2 强制换路」），**从未被记录过任何一次实际值** → 「一次合格率」在定义上不可统计。
- **`--report`** 出三个数：**一次合格率（判据 ≥70%，低于就停线分析）**、**缺陷帕累托**（决定该改哪条规则，只改头部 1–2 类）、成本回填。

**② 指标分层（CTQ）+ `indicator-waived` —— 给耦合指标一个终止条件**

机制诊断：句法目标表 17 个指标**物理上互相耦合**——拆长句 → 平均句长↓ / 超长句占比↓ / p90↓；合并句子 → 节奏 CV↓。而闸门要求 **17 项同时达标**：**在耦合系统里这是一个"搜索问题"，不是"更努力"的问题。**

实测某项目第 1 章的 `check_human_rhythm.py` 被跑了 **189 次**（同章脚本调用 486 次）。

| 级别 | 指标 | 判定 |
|---|---|---|
| **CTQ（硬门）** | **段落节律 CV** · **硬性句式（不是X，是Y）** · **作者在场指数** | 不过 = 阻塞 |
| **参考指标** | 其余全部 | **只记录 + 看趋势，单章不阻塞** |

**硬门少了，"同时达标"才成为一个可解的问题。** 再加 `indicator-waived`（沿用边界 waiver 的已验形态：理由 ≥8 字 + 记台账 + Phase 4 抽查）——**一个"只有全绿才能出"的闸门，在耦合系统里等价于没有出口。**

**③ 字数从"检验项"降为"工序参数"**

实测：`check_chapter_wordcount.py` 被调用 **734 次 = 全部质检脚本调用的 52%**。而字数是**唯一一个写前就完全确定的量**（配额卡已给目标）。→ 改成：按配额卡一次写足（±10%），**只在收尾确认一次**。**不要"查-改-查"——那是在反复问一个你写前就知道的数。**

**④ 前馈槽位（`used_devices`）**

任务包新增一个槽位，由脚本自动从细纲抠：

```
本批（截至上一章）**已经用过**的手法——本章请避开同型：
- 第1章：开场 新起型 / 章末 丁·悬念
- 第2章：开场 续接型 / 章末 丙·喜剧反转
```

**跨章同质**原本是"写完由 `check_repetition` 报警"（反馈＝多一轮 × 15 万 token）；现在变成写前的事实（前馈＝几行字）。**且不可被 hack——它是已发生的事实，没有可凑的数字。**

实测立刻在真实项目上抓到两处既有缺陷：第 2、3 章连续同型章末（丙·喜剧反转），以及第 2/3/4 章连续三章「续接型」开场。**这些此前只能等写完才发现。**

**⑤ 锚点章改「三候选定调」**

实测锚点章（第 1 章）跑了 **486 次**脚本调用，而中位章只有 **6** 次 = **32 倍**。原因不是它更该打磨，而是**它的交付物被定义错了**：锚点章真正的产出是**一段 150–250 字、可被后续 50 章模仿的锚**，不是"一份 17 个指标全绿的稿"。

→ 先在锚点章前写 **3 个不同声音取向的开篇**（各 300–500 字）→ 作者挑 → **锚定了才补完整章**。迭代路线 = 1 份稿 × 20 轮；选择路线 = 3 份候选 × 1 次 + 一次"挑"。

## 4. 实验与评估

> ⚠️ **本节数据的可核验性说明**：4.1–4.3 的案例数据来自项目自身记录，本 README 无法独立复核（原始质检报告不在本仓库内）。4.4 列出的是项目已知的、尚未完成的验证项。

### 4.1 实验设置

| 案例 | 类型 | 章数 | 总字数 | 写作模式 |
|------|------|------|--------|---------|
| 案例 A | 西式奇幻 | 7 章 | ~2.8 万字 | 串行（serial） |
| 案例 B | 都市恋爱喜剧 | 12 章 | ~4.5 万字 | 串行（serial） |

两部作品由同一套 J-Novel 系统生成，区别仅在于题材和人物设定。写作过程中，所有"作者确认"环节被严格限制在 Phase 2 的锚点章定调和 Phase 5 的完稿验收两个时间点。

### 4.2 定量评估

| 指标 | 人类范围 | 案例 A（奇幻） | 案例 B（都市） | 判定 |
|------|---------|---------------|---------------|------|
| 句首代词占比 | 1.5–10.4% | 6.2% | 5.8% | 趋近人类 |
| 句首引号占比 | 18.4–30.6% | 21.3% | 19.7% | 趋近人类 |
| 平均句长（字） | 22.7–36.6 | 28.4 | 26.1 | 趋近人类 |
| 破折号/千字 | 0.03–0.29 | 0.62* | 0.78* | 高于人类区间 |
| 身体部位/千字 | 0.31–0.55 | 0.48 | 0.43 | 趋近人类 |
| 情绪词/千字 | 0.32–0.35 | 0.34 | 0.36 | 趋近人类 |
| 明喻/千字 | 1.05–1.27 | 1.18 | 1.22 | 趋近人类 |
| 对话占比 | 20.4–33.5% | 27.6% | 29.1% | 趋近人类 |
| 动作短语密度 | 0.106–0.247/千字 | 0.19 | 0.17 | 趋近人类 |
| 通用模板短语密度 | 0.55–1.22/千字 | 0.81 | 0.92 | 趋近人类 |

\* 破折号一栏按 2026-09-16 收紧后的软线（0.5/千字）衡量为超标；这两部作品产出于收紧之前。

**关键观察**："情绪词密度"与"身体部位密度"两项——早期版本中曾呈现典型的"补偿式偏移"（情绪词过低、身体部位过高，后者一度达人类的 5–7 倍）。这表明 2026-08-29 版本修订后纠正了这一系统性问题。

### 4.3 定性评估

**叙事连贯性**：案例 A 在 7 章内完成了主角从坠落、生存、融入小镇、兽人夜袭、到获救的完整弧线。所有伏笔均在第 7 章结束前形成闭环。

**文风统一性**：两部作品在文风锚点示例的指导下保持全局一致性。案例 B 的第一人称叙述口吻从头至尾稳定。

**AI 味诊断**：两个案例中 AI 味自评量表（11 项）的最终评定均为"可交付"。AI 侧检出项集中在早期章节的"心理描写还原度"和"开场同质性"，在 Phase 3 的单点手术修改中被纠正。

**异常发现**：案例 B 第 8-10 章的关系升温段落中，存在三处"情绪直说+身体反应"的混合写法，被自评量表标记为 AI 侧典型模式，但在上下文中被判定为符合角色性格的合理选择，未作修改。**这提示质检体系需要保留"基于上下文做判断"的灰色地带。**

### 4.4 已知的未完成验证

1. **规模限制**：当前实证案例的章节数（7-12 章）不足以验证框架在 50+ 章长篇中的抗漂移能力。
2. **无对照实验**：未进行"有/无 J-Novel 机制"的 A/B 对照，无法量化每个单独机制的边际贡献。
3. **主观评价缺失**：读者反馈数据未纳入评估。
4. **基线选择偏差**：人类基线取自三部男频商业小说，可能不适用于所有题材。
5. **独立质检子代理的效力尚未经 A/B 验证**——机制建设与注册已完成，但"有它 vs 没它"的盲评对照仍是待办。
6. **`test_guards.py` 的 58 例未在本 README 编写时实跑复核**。

## 5. 局限性与未来工作

### 5.1 当前局限性

#### 先说人话

这套东西**很重**，而且它的默认审美是男频网文的口味。它不是给所有人、所有题材准备的。

#### 展开说

**（1）执行负荷**：完整流程（Phase 0-5）对 Agent 的认知负荷要求较高。每章的 10 步最小必做清单、质检脚本调用、台账回写等操作在串行模式下会增加单章处理时间。对于短篇创作（<5 章），该框架可能显得"过度工程化"。

**（2）依赖链脆弱性**：框架依赖 16 个 Python 脚本和 12 个专业子技能。在子技能未安装或脚本环境不完整时，部分质检能力会降级为内建指南兜底——这虽不会导致系统崩溃，但会降低自动化的可靠性。

**（3）基线泛化性**：句法层阈值基于三类男频网文计算（如句长 22.7–36.6 字），可能不适用于严肃文学、诗歌化散文或轻小说译文体。`--baseline` 参数允许重新校准，但增加了使用门槛。**开箱默认值是男频系统/吐槽流的。**

**（4）并发模式复杂度**：链式流水线下的主编职责清单（接口契约冻结、批次验收闸门、锚点滚动、真实结尾转交、边界缝合）对主编 Agent 的质量要求极高。**在并发场景中，主编本身仍是单点瓶颈。**

**（5）指标耦合**：17 项指标并非正交——补长句会把明喻密度挤上去，补数字会把情绪词挤下去。生成时配额卡能压住大头，但一次全绿通常做不到。CTQ 分层是对此的缓解，不是根治。

**（6）"声明-实现"漂移的长期风险**：本项目历史上反复出现同一类缺陷——"看起来已经做了，实际从未触发"（守卫被注释骗过、共享实现被本地函数覆盖、定义了却从未被调用的缓存函数）。已配套一层"声明-实现一致性"守卫与 `test_guards.py` 故障注入测试，但这类漂移是结构性的，需要持续投入。

### 5.2 未来工作方向

1. **自动化基线校准**：开发脚本自动扫描输入的人类样本并输出建议阈值。
2. **读者反馈集成**：将 Reader Simulator 子技能升级为完整的读者反馈管道，在 Phase 4/5 自动生成三层读者验证报告。
3. **多卷长篇验证**：在 50 章以上项目中运行完整流程，收集 Seam 重读的有效性数据。
4. **独立质检子代理的 A/B 验证**：同一章，一组只跑脚本、一组跑脚本 + 独立质检并按其意见修改，然后盲评对比。
5. **跨题材基线研究**：扩展人类基线数据库，覆盖言情、悬疑、轻小说、历史等题材。
6. **中段并行 · 边界串行**：把并行单位从"章"切成"中段+边界"（理论收益最大，依赖契约生成点，但改动面大）。

## 6. 复现指南

### 6.1 依赖环境

#### 先说人话

Python 3.8+，一个能读写文件的 Agent 宿主，以及可选的 12 个子技能。

#### 展开说

- Python 3.8+（用于运行 `scripts/` 下的质检脚本）
- 文件系统写入权限（用于创建 `novel-output/` 项目目录）
- 支持 `read_file`、`write_file`、`ls`、`Skill` 工具的 Agent 宿主环境
- 可选：12 个子技能（未安装时自动降级为内建指南兜底）

### 6.2 目录结构

```
j-novel/
├── SKILL.md                      # 技能入口与硬指令
├── CHANGELOG.md                  # 版本记录（含历次实测与失败复盘）
├── references/
│   ├── execution-contract.md     # 九条铁律
│   ├── guide-index.md            # 动作→指南映射
│   ├── skill-mechanics.md        # 三层加载模型与维护检查清单
│   ├── flows/
│   │   ├── phase0-initialization.md
│   │   ├── phase1-interview.md
│   │   ├── phase2-planning.md
│   │   ├── phase3-writing.md
│   │   ├── phase4-validation.md
│   │   └── phase5-polish.md
│   └── guides/                   # 30+ 份写作心法、节律、改写与工艺指南
└── scripts/                      # 16 个脚本
    ├── _shared.py                # 读文件 / 取正文 / 明喻 / 交接卡解析 的唯一实现
    ├── check_human_rhythm.py     # 句法层 + 分布层 + 作者在场（17 项）
    ├── check_aistyle.py          # 词汇层指纹 + 硬性句式 + 半角引号 + 声音漂移
    ├── check_repetition.py       # 章内重复 + 跨章开场/章末同质 + 意象配额
    ├── check_continuity.py       # 章节边界连续性
    ├── check_contract.py         # 接口契约（齐备性 + 相邻章状态 diff）
    ├── check_worldbuilding.py    # 设定激活率 / 未登记新词
    ├── check_chapter_wordcount.py
    ├── check_batch_gate.py       # 批次验收闸门（含崩坏红线 1）
    ├── make_handoff.py           # 交接卡（主编零正文的支点）
    ├── make_task_package.py      # 任务包编译器（装配 + 预算 + 校验）
    ├── make_workorder.py         # 章节工单（质检归档 + 良率/帕累托）
    ├── convert_to_txt.py
    ├── audit_tokens.py           # 成本审计（读平台轨迹真实 usage）
    ├── audit_release.py          # 发布前 QA
    └── test_guards.py            # 故障注入测试（58 例）
```

### 6.3 快速启动

1. 将 J-Novel 作为 Skill 安装到 Agent 宿主环境中
2. 在目标工作目录下创建 `novel-output/` 文件夹
3. 调用该 Skill，Agent 自动进入 Phase 0 初始化
4. 用户提供创作想法后，Agent 按 Phase 1 → 2 → 3 → 4 → 5 顺序驱动流程
5. 系统产出位于 `novel-output/{小说名}/` 目录下

### 6.4 模式开关

`02-写作计划.json` 中的 `costMode` 字段：

- **`standard`**（默认）——判断项逐项做，质检强度最高。适合锚点章、关键转折章。
- **`low`**——**批量推进档**。组织形式走**链式流水线 + 批次**（不是串行）；机械项**全跑**（脚本 0 reasoning token，一个不砍）；判断项**合并成一次**调用；**人味项目一个不砍**。

**注意**：`costMode` 只控制"读多少文件、跑几项质检"，**不控制成本的大头**。成本大头是"调用次数 × 上下文"，那是铁律九管的，两种模式都必须遵守。

### 6.5 维护者注意

- **改动本框架的任何规则或脚本后**，须运行 `python scripts/audit_release.py --regress`（退出码 0 才算通过）。
- **改动任何检查项后**，须再运行 `python scripts/test_guards.py`（58 例故障注入）——**"加了守卫"和"守卫有效"是两件事**。

## 7. 结论

### 先说人话

这套东西的核心想法可以用一句话概括：**长篇创作里最难的三件事，不要靠"提醒模型注意"，要靠工程机制**。

把状态写进文件、把"像不像人"变成退出码、把并行单位从章节换成工序、把"该改哪条规则"变成看数据。

**它自己也承认自己会被 hack、会漂移、会写出"全绿但不像人"的稿子**——所以它配了独立质检、故障注入、良率闭环。这份诚实是它最有价值的部分之一。

### 展开说

本文提出了 J-Novel，一个面向 AI Agent 的长篇小说创作框架。核心贡献在于将"过程层状态管理"引入叙事生成任务，通过五字段创作台账、事实三态标记、Seam 重读、两层量化质检、独立质检子代理和链式流水线协议，系统性地解决了 LLM 在长篇创作中面临的三类最昂贵的事故：连续性错觉、长跑漂移和 AI 味顽固复发。

v6.5 新增的工业化工单与良率闭环，把"该改哪条规则"从主观判断变成了数据驱动——这是从"工艺"走向"产线"的一步。

在两部完整小说的实证验证中，J-Novel 产出的文本在所抽查的 10 项句法指标上均趋近于人类基线，同时消除了传统 AI 创作中常见的逻辑断裂与模板化表达。该框架已在生产环境中完成了端到端的验证，并开源以供研究社区复现与改进。

**开源声明**：本框架为纯粹的学术开源项目，旨在为长文本生成领域提供一个可复现的、工程化的研究基线。欢迎研究者复现、扩展或改进其中的任何机制。
