# J-Novel：面向长文本生成的过程感知型小说创作框架

> 对应 j-novel v6.5.0 · 更新日期 2026-09-23

## 摘要

大规模语言模型（Large Language Models, LLMs）在长文本创作任务中展现出巨大潜力，但当任务规模超过单次上下文窗口时，系统性失效模式开始显现：叙事连续性断裂、文风漂移、以及机器生成痕迹的顽固复发。现有解决方案——无论是上下文窗口扩展、链式推理提示，还是通用型 Agent 框架——均未能从根本上解决这三个问题，因为它们缺乏对**创作过程本身的状态管理**，也未对**成本与质量之间的耦合**给出可执行的工程闭环。

本文提出 J-Novel，一个融合了过程层状态管理的端到端小说创作框架。该框架的核心贡献在于：（1）引入“创作台账”（Creation Ledger）作为 Agent 的外接工作区，实现每章边界强制重读（Seam Re-reading），从机制上防止长上下文场景下的静默状态丢失；（2）提出“事实三态标记”（✓ / ? / ✗），将“已落正文”、“仅规划”与“已被否定”的叙事元素物理分离，根除了“我以为写过了”这类逻辑崩坏的源头；（3）建立“三站齐备”审计模型（生成点／交付点／校验点），把“文档里写了规则”与“规则真的生效”区分开；（4）构建句法与分布两层共 17 项可量化指标 + 一道硬性句式闸门 + 独立质检子代理的质检体系，将“人味”转化为可自动化验证的数值阈值，同时保留“脚本测不出的那一半”；（5）设计以“工序”而非“章节”为并行单位的链式流水线协议，配套三道闸门（章闸／窗闸／批闸）、边界冻结与缺陷路由，在保证叙事一致性的前提下实现多代理并行加速；（6）引入工业化度量（章节工单、一次合格率 FPY、缺陷帕累托），让“改哪条规则”由数据决定，而非凭直觉。

我们在两部完整小说（一部西式奇幻，一部都市恋爱喜剧）以及多个真实生产项目中验证了该框架的有效性。实证结果表明，J-Novel 产出的文本在句法与分布层指标上显著趋近人类基线，同时消除了传统 AI 创作中常见的连续性 BUG 与模板化表达。**同时，我们诚实记录了框架自身的失败形态**——“假闸门”（看似做了检查、实际从未触发）、“声明比实现走得快”（注释改了代码没改）、“指标被 hack”（底线当目标、配额当目标）、“规则过度执行”（一条规则被填成同构模板）——并为每一类失败配备了可执行的回归守卫与故障注入测试。

本文旨在为长文本生成领域提供一个具备**可复现性**与**可证伪性**的工程化研究基线。

**关键词**：AI 辅助创作 · 长文本生成 · 叙事连续性 · 过程管理 · 质量控制 · 多 Agent 协作 · 成本工程


## 1. 引言

### 1.1 问题背景

大型语言模型在创意写作任务中的能力已得到广泛验证。给定一个简短的提示或大纲，LLM 能够生成流畅、连贯、甚至具备一定文学性的短篇文本。然而，当任务从“写一个短篇”扩展到“写一部长篇小说”（通常超过 10 万字、数十个章节）时，模型的性能急剧下降。

这种下降并非源于模型“不会写”，而是源于长文本生成任务的三个结构性痛点，外加一个工程性痛点：

**痛点一：连续性错觉（Continuity Illusion）**。在跨越数十个章节的创作过程中，LLM 必须记住大量事实性信息：人物的位置、情绪状态、已知信息、伏笔状态、时间线……当信息量超过模型的“有效工作记忆”时，模型会基于上下文中的近期信息做出推断，而这些推断可能与数十章前确立的事实相矛盾。这种矛盾不会触发任何错误信号——模型不会“报错”，它只是安静地产生了一个逻辑 BUG。在最坏的情况下，第 5 章登记的伏笔在第 20 章被当作既成事实引用，而该伏笔从未真正被写进正文。

**痛点二：长跑漂移（Long-haul Drift）**。文风不是由单一规则定义的，而是由大量微观决策（词汇选择、句法节奏、叙述者距离、修辞偏好等）共同构成的分布。在长篇创作中，这些微观决策会随着时间推移逐渐偏移。当这种偏移累积到一定程度时，小说的前 5 章和后 5 章读起来像是两个不同作者写的——而写作过程中的任何一步都不会显式地报告这种漂移。

**痛点三：AI 味顽固复发（AI-flavor Recidivism）**。“AI 味”不是某一种具体的错误，而是一组统计层面的异常：过高的句首代词比例、过密的破折号插入语、过度的身体部位描写、过少的情绪词直说……当规则以“禁止 X”的形式给出时，LLM 的典型反应是换一种方式表达 X，从而在规避表面规则的同时产生新的、更隐蔽的统计异常。这就是为什么单纯依赖“去 AI 味提示”往往治标不治本。

**痛点四：成本与质量的耦合失控（Cost-Quality Coupling）**。实测（来自平台侧真实 usage 字段，471 个会话 / 8,457 次调用）表明：**promptTokens 占全部 token 的 99.7%，其中 98.7% 是缓存重发（cacheRead），模型实际产出只占 0.30%——放大倍数 334×**。也就是说，正文本身几乎不花钱，**读回去的上下文才是全部成本**。而成本的大头在“被乘数”一侧：**每次调用平均重发 149,675 tokens 上下文（中位），p90 为 420,203**。中位会话只有 8 次调用——所以“减少调用次数”固然重要，但**压每次调用的上下文规模**才是更大的池子。这直接决定了框架的设计：任务包必须有预算、主编必须零正文、指南不能重复读。

### 1.2 现有工作及其局限

现有解决方案大致可分为四类：

**（1）上下文窗口扩展（Context Window Scaling）**。以 GPT-4 128K、Claude 200K 为代表，通过扩大上下文窗口让模型“看到更多”历史内容。这在一定程度上缓解了短期遗忘，但无法解决根本问题：注意力机制在长序列中呈稀疏分布，关键信息可能被淹没；且窗口总有上限，对于 30 万字以上的长篇任务仍显不足。**更关键的是：扩窗不解决成本问题——它只是让"每次调用带多重"这件事变得更贵。**

**（2）通用型 Agent 框架（General-purpose Agent Frameworks）**。如 LangChain、AutoGPT 等，提供了工具调用、记忆存储、任务规划等通用能力。但它们的设计目标是“通用任务执行”，而非“文学创作”。它们缺乏对叙事特殊性的理解——例如，小说中的“人物状态”与“待办事项”有着本质不同的更新语义，通用记忆模块无法区分“已落正文”与“仅规划”之间的微小但关键的差异。

**（3）小说写作辅助工具（Narrative Writing Assistants）**。近年来出现了若干面向小说的 AI 辅助工具，如 Sudowrite、NovelAI 等。它们提供了优质的文本生成与润色能力，但通常以“单次生成”为交互单元，缺乏对“跨章连续性”和“过程状态”的系统化管理。用户仍然是整个创作流程的核心调度者，而非 Agent。

**（4）长流程 Agent 工程（Long-horizon Agent Engineering）**。近期有一批工作关注“Agent 在长任务中如何不漂移”，提出了检查点、轨迹审计、外部状态管理等思路。它们与 J-Novel 的关切点一致，但缺少对**创作任务特有语义**（如"事实三态"、"文风锚点"、"章末型配比"）的建模，也未给出**可脚本化的验收判据**。

### 1.3 本文贡献

本文提出 J-Novel 框架，从“过程层状态管理”的角度重新审视 AI 长篇创作问题。具体贡献包括：

1. **提出“创作台账”作为 Agent 外接工作区的概念**，将“故事的状态”与“Agent 自身的认知状态”物理分离，并在每章边界强制执行“Seam 重读”机制，从系统层面防止静默状态丢失。

2. **建立“事实三态标记”系统**（✓ / ? / ✗），将叙事事实的认知状态（已确认/待确认/已否定）显式编码到项目管理文件中，消除了“规划”与“执行”之间的语义混淆。

3. **提出“三站齐备”审计模型**：任何一条机制要生效，必须走完**生成点**（信息在哪一步被产出）→ **交付点**（怎么进入执行者上下文）→ **校验点**（怎么知道它被遵守了）。缺任何一站机制就死，且死法不同：缺生成点=不存在；缺交付点=看不到；缺校验点=不可证伪。该模型把“文档里写了”与“真的生效”彻底分开，并在 v6.3.0 一致性审计中一次性抓出 9 个缺口。

4. **构建两层量化质检体系**：句法层 9 项 + 分布层 7 项 + 作者在场指数 1 项 = **17 项可自动化验证的指标**；外加一道硬性句式闸门；在此之上引入一个**独立质检子代理**（同构／删除／作者在场／用力过猛四项语义测试），补足脚本无法覆盖的那一半。**并引入 CTQ 分层（3 个硬门 + 其余降为参考指标），给耦合指标一个可解的终止条件。**

5. **设计以“工序”而非“章节”为并行单位的链式流水线协议**，配套接口契约冻结、笔手／磨手／主编三角色分工、三道闸门（章闸／窗闸／批闸）、边界冻结（文本层接口）、缺陷路由（只向前修 vs 停线回改）、流量控制（领先上限=窗口值）。**并明确"闸门必须放在缺陷被定稿之前"这条贯穿全局的判据。**

6. **引入成本工程铁律与可量化验证**：一次跑完全部脚本、一次批量改写、不重读指南、子代理只读速查卡、任务包编译器 + 预算上限、主编零正文（交接卡）。**提出"每次调用平均重发上下文 >100k tokens/次 = 上下文纪律已失守"这一新判据。**

7. **引入工业化度量与闭环**：章节工单（`06-章节工单.md`）、一次合格率（FPY ≥70%）、缺陷帕累托（决定该改哪条规则）。**让"改哪条规则"从直觉变成数据驱动。**

8. **配套发布前 QA（`audit_release.py`）+ 故障注入测试（`test_guards.py`）**，把“我加了守卫”与“守卫真的会响”严格区分。当前 test_guards.py 覆盖 **58 个故障注入用例**，且历史上每一次扩展都立刻抓到过“守卫自身失效”。

9. **以两部完整小说 + 多个真实生产项目作为实证案例**，展示框架的有效性与局限性，**并诚实记录框架自身的失败模式与纠正轨迹**。


## 2. 系统架构概述

J-Novel 是一个文件化、状态感知的多代理创作框架。其整体架构可以概括为“一条流水线、八份状态文件、两层质检、三站审计”。

### 2.1 六阶段流水线

J-Novel 将长篇创作分解为六个可验证的阶段：

| 阶段 | 名称 | 核心任务 | 出口条件 |
|------|------|---------|---------|
| Phase 0 | 初始化 | 加载用户偏好、检测未完成项目、恢复状态（五步） | 清单全勾 + 入口判定完成 |
| Phase 1 | 深度采访 | 五层挖掘（情绪/动机/期待/想象/盲区），磨出 12 项验收清单；可选剧情脚手架采集（P1） | 验收全过 + 故事速写经用户确认 |
| Phase 2 | 规划与确认 | 生成故事圣经、人物档案、分章大纲、写作计划 JSON、三本台账、第一批细纲；锚点章"三候选定调" | 清单全勾 + 锚点章确认 |
| Phase 3 | 疯狂创作 | 逐章或链式流水线执行“写-审-改-锁”循环；**两个例外**允许中途确认（文风/剧情方向） | 全部章节 completed |
| Phase 4 | 自动校验 | 字数/质检痕迹/节律/统计指纹/连续性检测/世界设定；按重试三出口修复 | 全部章节 PASS + 完成报告（含未检查项） |
| Phase 5 | 完稿润色 | 一致性通读、台账对账、后精修四工序、节奏评估、开篇重审、资产沉淀 | 清单全勾 + 全书完成总结 |

每个阶段的入口处设有“执行清单”（Execution Checklist），Agent 必须逐项打勾才能进入下一阶段。清单机制的设计目的是防御“流程跳步”——在长流程中，Agent 倾向于跳过自认为“已熟悉”的步骤，而清单将“已做”与“未做”的边界显式化。

**关于 Phase 3 的两个例外**（这是 v6.0.0 的核心设计）：Phase 3 的核心规则是“全程禁止向用户确认任何事”，但为保证作者意图不被泛化的模板覆盖，开放**两个有边界的例外**——① **锚点章定调**（确认**文风**，全书一次）；② **剧情脚手架对齐**（确认**剧情方向**，按"意图浓度"分级触发）。两者遵循同一条设计原则：**只在一个自然的停点上确认一次定调，之后全力开写。**

### 2.2 八份状态文件：文件化状态管理

J-Novel 的核心设计原则是**所有状态必须落盘**。项目目录下的八份文件分别承载不同维度的状态：

| 文件 | 管理内容 | 回答的问题 | 更新者 |
|------|---------|-----------|--------|
| `00-人物档案.md` | 角色静态设定 | 这个角色是谁？ | 规划阶段一次性写入 |
| `01-大纲.md` | 章节规划与摘要（含章末型/开场类型/伏笔表） | 每章要发生什么？ | 规划写入，写作后追加摘要 |
| `02-写作计划.json` | 项目进度与模式开关 | 还剩什么没做？ | 每章更新 |
| `03-状态台账.md` | 故事内动态状态（人物/伏笔/时间线，含三态标记） | 现在故事里发生了什么？ | 每章写回 |
| `04-质检档案.md` | **人写的判断**（AI味自评/人味配额/四项测试/杠精结论） | 这一章查了什么、结果如何？ | 每章追加 |
| `05-创作台账.md` | Agent 的认知状态（含 retryCount） | 我现在确认了什么/不确定什么？ | 每章 seam 重读与回写 |
| `06-章节工单.md` | **机器写的度量**（机械结论/缺陷类型/返工轮次/成本） | 一次合格率是多少？哪几类缺陷占大头？ | 每章 `--archive` 追加 |
| `07-剧情脚手架.md` | **作者意图**（原话 + 画面 + 状态机 + 对齐记录） | 作者对这个故事的具体设想有没有落地？ | P1 采集、P3 更新 |

`05-创作台账.md` 是本框架最核心的创新之一。它不记录“故事里发生了什么”（那是 `03-状态台账.md` 的职责），而是记录 **“Agent 认为自己知道了什么”** 。这个区别至关重要：当上下文窗口滚动、早期信息被压缩时，Agent 仍然可以通过重读 `05-创作台账.md` 来恢复自身的“认知状态”，从而避免“静默丢弃约束”。

`06` 与 `04` 的**刻意分离**也值得说明：初版曾把机器度量 upsert 进 `04`，结果**把用户项目里那一行的 9 列质量数据覆盖成 6 列**（已还原）。教训是：**向"别人的文件"追加前先看清它现有的列；覆盖式更新一个你没定义过 schema 的表，就是数据丢失。非破坏性的做法是"另建一张表 + join"，不是"改人家的表"。**

`05-创作台账.md` 的五字段结构如下：

```markdown
# 创作台账（每次 seam 重读）
最近重读章号：第X章
本章返工轮次（retryCount）：0

## Goal
一句话，本阶段“完成”意味着什么，能判断自己到没到。

## Core
≤2 条。第三条想进来必须先换掉一条，且换的时候要说出声。
- 文风锚点 —— [一句话 + 它为什么重要]
- 本卷张力 —— [一句话 + 它为什么重要]

## Verified
编号追加，永不改写。每条写清依据。
- ✓01 [已落正文的既成事实]（依据：第X章）

## Open
每条带“什么能终结它”。
- ?01 [还不确定什么] —— settled by: [什么能终结它]

## Next
单一动作，永不为空。
```

### 2.3 执行契约（Execution Contract）

为确保 Agent 在长流程中不跳步、不偷懒，J-Novel 内置了一份“执行宪法”，其核心是九条铁律。前四条管“产物是否合格”，后五条管“Agent 在长跑中是否还醒着”：

| 编号 | 铁律 | 核心内容 |
|------|------|---------|
| 1 | 【必须】读流程 | 进入任何 Phase 先读对应流程文件，按执行清单逐项执行 |
| 2 | 【必须】不跳步 | 标注【必须】的步骤不可跳过/合并/简化 |
| 3 | 【必须】读指南 | 关键动作前必读对应 guides 文件 |
| 4 | 【必须】固定排班 | 检查型工具到点必调，自检“没问题”不是跳过理由 |
| 5 | 【必须】三态标记 | 标 `?` 的条目，下游章节不得当作已发生的事实来写 |
| 6 | 【必须】Seam 重读 | 每章边界重读 `05-创作台账.md` 五段后再动笔 |
| 7 | 【必须】置信度绑定 | 读到「晃」禁止原路重走，三选一换路 |
| 8 | 【必须】注册分离 | 正文里不得出现细纲记号、质检字段、未展开的缩写 |
| 9 | 【必须】成本纪律 | 一次跑完全部脚本、一次批量改写、不重读指南、子代理只读速查卡 |

铁律 5–9 是本框架区别于其他系统的关键：它们不直接作用于产物，而是作用于 Agent 在写作过程中的“认知纪律”。

**关于铁律六的显式例外**：`low` 模式的台账策略是“每批一次”而非“每章一次”。这不是打折，是**显式声明的例外**——串行时主 Agent 上下文线性累积，复利涨得快，所以要勤换；流水线里每个角色的上下文本来就近似常数，勤换只是白白重读圣经/大纲。`execution-contract.md` 与 `low-cost-mode.md` 相互声明这一点，且 Phase 4 的检查口径按 `costMode` 分档——**否则两处规则会在长跑中互相判违规。**

### 2.4 三站齐备：机制的完整生命周期

一条机制要生效，必须走完三站。这是 v6.3.0 引入的审计模型，也是本框架最通用的设计原则之一：

```
① 生成点  这条信息在哪一步被【产出】？  缺 → 不存在（不是没生效，是没有）
② 交付点  它怎么【进入执行者上下文】？  缺 → 看不到（写了、算了，但没送到）
③ 校验点  怎么知道它【被遵守了】？      缺 → 不可证伪（全靠自觉，长跑中静默失效）
```

用它体检的结果很有说服力：**文风线六项机制里只有一项三站齐全。** 这也解释了“为什么写了几十万字却越来越不像开头那本书”——**没有任何一站会报错。** `audit_release.py` 现在有一条守卫专门检查“一致性机制的三站是否齐备”，覆盖契约、三层锚、意象配额、锚点滚动、独立质检独立性、伏笔单载体、台账例外等 20 余项。**它的价值不只是盯住这几条——它是第一个能自动发现孤儿的守卫**：任何“文档里定义了、却没有任何执行链引用”的东西都会被它抓出来。


## 3. 核心机制详解

### 3.1 事实三态标记系统

**问题**：在长篇创作中，最昂贵的一类 BUG 是“我以为这条已经写过了”。规划阶段登记了某个伏笔，写作到第 20 章时，模型基于上下文中的规划记忆将其当作既成事实引用，而该伏笔实际上从未被写进正文。这种错误不会触发任何异常信号——它只是安静地产生了逻辑断裂。

**解法**：J-Novel 引入“事实三态标记”，强制状态台账与伏笔对照表中的每一条目携带状态位：

| 标记 | 含义 | 约束 |
|------|------|------|
| `✓` | 已在正文中明确写出 | 标注依据章号，可追溯 |
| `?` | 仅规划或推断，尚未落正文 | 下游章节**不得**以此为前提 |
| `✗` | 已被后续剧情否定 | 不删除、不覆盖，保留证据链 |

默认无标记 = `?`。这一设计将“规划”与“执行”在语义层面强制分离。在 Phase 3 的每章收尾步骤中，Agent 必须扫描本章正文，将真正落地的条目从 `?` 更新为 `✓（第X章）`，并在 `05-创作台账.md` 的 Verified 字段中追加编号记录。

**效果**：三态标记不依赖于模型的“记忆”，而是依赖于文件系统的持久化和每章收尾时的强制检查。它从工程层面切断了“记忆混淆导致逻辑 BUG”的因果链。

**伏笔单一载体声明**：伏笔的全量权威载体是 `01-大纲.md` 的「伏笔对照表」，圣经里的那张是**卷终汇总派生视图**。双载体同名必然漂移，而漂移表现恰好是“同一伏笔两处状态不同”——**正是伏笔机制想防的事。**

### 3.2 Seam 重读机制

**问题**：即使在文件化状态下，Agent 仍然可能在长跑中“静默丢失约束”——文风锚点被悄悄换掉、某个伏笔是“写过了”还是“打算写”记不清了、排班专项检查是否执行过全凭印象。这些错误不会报错，它们只会在第 20 章变成“这本书怎么读着不对劲”。

**解法**：J-Novel 在每章创作的入口处（Phase 3 步骤 0.5）强制执行“Seam 重读”：Agent 必须用不超过 30 秒的时间，完整读取 `05-创作台账.md` 的五段全部内容（Goal / Core / Verified / Open / Next），并在动笔前更新 Next 字段。**同时读 `03-状态台账.md` 里本章出场人物的条目**——05 管认知状态（我已确认什么），03 管故事内状态（人现在在哪、什么情绪、知道什么）。换会话后**两个都需要**。

这一机制的设计依据是注意力理论：LLM 的注意力机制能够平等地关注上下文窗口内的任何 token，但**只有在 token 还在窗口内的时候**。当上下文滚动、早期信息被压缩或移出窗口时，注意力无法重新触达这些 token。Seam 重读将 `05-创作台账.md` 设计为“注意力锚点”——它是每个 Seam 处都会被重新加载的信息集，因此永远不会被遗忘。

Core 字段的“≤2 条”限制进一步强化了这一机制：超过两条的 Core 会被稀释，每条只能分配到不到二分之一的注意力。第三条想进入 Core 时，Agent 必须**说出口**（“放下 X，拿起 Y”），将离开的那条写入 Verified 或 Open。这一“出声”操作防止了静默丢弃（Silent Drop）——即某个约束在任务中途悄悄停止生效，而 Agent 没有意识到它的消失。

### 3.3 句法层与分布层量化质检（17 项指标 + 一道硬闸门）

**问题**：“读起来像不像人写的”是一个主观判断，Agent 可以用“我觉得没问题”糊弄过去。主观判断不可信，数字可信。

**解法**：J-Novel 构建了一套基于统计基线的量化质检体系，核心工具是 `check_human_rhythm.py` 与 `check_aistyle.py`。基线以三部完整人类小说为参照（齐佩甲《超神机械师》、三天两觉《惊悚乐园》、柳岸花又明《我真没想重生啊》，合计约 1200 万字），提取句法与分布两层的可测量特征并映射为硬性阈值。整个体系共 **17 项指标**，分三层：

**句法层九项（`check_human_rhythm.py`，退出码 1 = 本章不合格）**：

| 指标 | 人类范围 | 硬阈值 | 方向 |
|------|---------|--------|------|
| 句首代词占比 | 1.5–10.4% | ≤15% | max |
| 句首引号占比 | 18.4–30.6% | ≥15% | min |
| 平均句长 | 22.7–36.6 字（均值 30.8） | ≥18 字（**底线**） | min |
| 破折号密度 | 0.03–0.29/千字（2026-09-16 实测） | ≤1.5/千字 | max |
| 身体部位密度 | 0.31–0.55/千字 | ≤1.0/千字 | max |
| 情绪词密度 | 0.32–0.35/千字 | 0.25–0.5/千字 | range |
| 明喻密度 | 1.05–1.27/千字 | 0.8–1.5/千字 | range |
| 对话占比 | 20.4–33.5% | ≤40%（护栏） | max |
| 动作短语密度 | 0.106–0.247/千字 | ≤0.4/千字 | max |

> 平均句长一项须特别注意：脚本的 `hard=18` 是**判不合格的底线**（用于拦最极端的碎句），而**写作目标是 23–37 字的区间**（人类均值 30.8）。把底线当目标会让模型写到 19–22 字就自以为达标——这是本项目历史上反复踩过的一类错误。

**分布层七项（治“均值达标但读起来仍像 AI”）**：

| 指标 | 人类范围 | 硬阈值 | 方向 | 特征描述 |
|------|---------|--------|------|---------|
| 超长句(≥60字)占比 | 4.7–19.0% | ≥3% | min | **最强指标**：人类把多个信息单元打包进复合句 |
| 句长 p90 | 48–74 字 | ≥42 字 | min | 长句能力的上沿 |
| 节奏变异系数 | 0.251–0.321 | ≥0.19 | min | 500 字窗口句长起伏 |
| 中文量词密度 | 7.04–8.76/千字 | ≤10.5/千字 | max | **反向指标**：AI 用“一+量词”做泛化指代 |
| 长对话(≥30字)占比 | 15.8–27.7% | ≥8% | min | 人类对话里有“一段完整发言” |
| 数字密度 | 1.16–3.15/千字 | 0.8–8.0/千字 | range | 具体性信号（**硬上沿 8.0 防补字后遗症**） |
| 现实锚定计量 | 0.07–0.72/千字 | ≥0.05/千字 | min | **人类技法型指标**：用真实世界的数目锚定现实 |

> 现实锚定计量对架空/游戏世界观豁免（人类《惊悚乐园》仅 0.07，因其世界观里没有钱）。

**作者在场指数（第 17 项，区间 2.5–12）**：

把引号里的对话全部剥掉，只统计**叙述部分**的叙述者人格痕迹——评价副词（其实/居然/简直）×1 + 口语插话（说白了/反正/怎么说呢）×3 + 吐槽贬称（这货/欠揍/要命）×3 + 语气词×1，再加叙述句里 `？`/`！` 占比×0.5。人类 3.73–7.84，AI 全书仅 0.64–1.89，A/B 盲测稿为 0.00–0.75，是本体系分离度最高的判别器。根因：AI 的叙述是透明的，只报告事件、不表态。**上限 12 是防 hack**——它是区间项，不是“越高越好”。**新增子项地板**：复合分达标**不能**证明这一层存在，故加一条不可被平均掉的检查——叙述部分 `！`+`？` 合计为 0 时无条件报警。

**硬性句式闸门（`check_aistyle.py` 退出码的唯一驱动项）**：

「先否定再肯定」结构（“不是X，是Y”）单句硬线 **0.12/千字**、跨句硬线 **0.40/千字**。实测教训：原版只匹配「不是…而是…」，结果 AI 学会了绕开“而是”、改用“是”——人类 0.087/千字 vs AI 0.011/千字，旧规则完全失效。现版本同时覆盖同句变体与跨句变体。

**格式硬闸门**（v5.4.0 / v5.0.0 新增，均由盲评评委肉眼发现）：

- **半角双引号零容忍**：正文出现任何一个 ASCII `"` → exit 1（人类三部参考 0 处）。这是一个**生产级 bug**：子代理写 `.md` 时天然输出 ASCII 引号，会让「句首引号占比」指标直接判 0.0%。
- **汉字↔半角数字夹空格**：密度 >0.5/千字 → exit 1。实测人类 0.00–0.15、AI 对照 0.04、本体系产出 1.77–3.39——**差 12–100 倍**，是目前分离度最高的格式类指纹之一。

**人类区间命中率（v4.9.0 / v5.1.0）**：

退出码只回答“有没有硬伤”，不回答“离人类区间有多远”。实测真实项目 10 章**全部退出码 0**，但对照人类区间：平均句长低于下沿 **10/10 章**、动作短语 **10/10 章（0.0）**、长对话 9/10、超长句 8/10、身体部位 7/10——**整本系统性"欠写"，却全程绿灯**。因为 max 型指标把「0」当最完美，min 型指标的硬线又都设得比人类下沿松。

**阈值重标定（v5.1.0）**：原 50%/70% 阈值是**尺度混淆**——拿“整本书”的人类命中率当基准，却用在“单章”上。实测人类单章（4500 字窗口，n=2948）：p10 18% / p25 24% / **中位 35%** / p75 41% / p90 53%。**硬线 20%、软线 35%。** 原 50/70 会判掉 89% 的真实人类章节。

**CTQ 分层（v6.5.0）**：

17 项指标物理上互相耦合——拆长句 → 平均句长↓ / 超长句占比↓ / 句长 p90↓；合并句子 → 节奏 CV↓ / 段落 CV↓。而闸门要求 17 项同时达标：**在耦合系统里这是一个「搜索问题」，不是"更努力"的问题。** 实测某项目第 1 章的 `check_human_rhythm.py` 被跑了 **189 次**（同章脚本调用 486 次）。

| 级别 | 指标 | 判定 |
|---|---|---|
| **CTQ（硬门）** | **段落节律 CV** · **硬性句式（不是X，是Y）** · **作者在场指数** | 不过 = 阻塞 |
| **参考指标** | 其余全部 | **只记录 + 看趋势，单章不阻塞** |

**硬门少了，"同时达标"才成为一个可解的问题。** 再加 **`indicator-waived`**（沿用边界 waiver 的已验形态：理由 ≥8 字 + 记台账 + Phase 4 抽查）——**一个"只有全绿才能出"的闸门，在耦合系统里等价于没有出口。**

**效果**：这一体系将“人味”从主观判断转化为 17 项可自动化验证的数值阈值。Agent 无法用“我觉得挺有人味的”糊弄质检——脚本的退出码是硬数字。**同时，我们诚实地承认：**

- **指标必被 hack**：任何“次数型”指标都能被字面满足（实测：把“三件事”改成“三**桩**事”即骗过量词检查；删掉明喻却造出“似的/一般”新口癖）。
- **配额卡治"缺什么"很灵，治"耦合失衡"要配合批量精修**：14 项指标耦合，改一项会牵动别项（实测三轮均未一次全绿）。
- **底线当目标**：脚本 `hard` 是判不合格的线，不是写作目标。给模型看的数字**必须是目标区间**。

### 3.4 独立质检子代理：脚本测不出来的那一半

**问题**：脚本能测频率，但测不出“同构、空转、有没有人”。本项目有过一次明确的实测反例：某一版在加入新规则后，作者在场指数从 0 涨到 7.93（完美落在人类区间），**但盲评以 3:0 判负**——三位评委各自独立地从同一文件里挑出同一组三句，指出它们是“同一个模子的三次填空”。指标完美达标，读起来却更假了。这类缺陷统计上根本不成高频模式（每章仅 3–10 句），字符串级检测器全部失败。

**解法**：在脚本质检之后、置信度定档之前，另起一个**独立质检子代理**，其全部价值来自“它不知道你是怎么写的”：

- **只给纯正文**——不给细纲、大纲、规则包、改动说明、脚本报告，**不给质检脚本的路径或源码**（让它读指标源码，等于让它对着评分器写）
- **每个子代理独立启动新上下文**，多个评委互不可见
- **不给打分**（打分会被“总体不错”污染）；要的是“**哪一句**”，不是“几分”

四项测试，全部要求引用原句：

| 测试 | 人类侧真值 |
|---|---|
| **同构测试**（找出像同一个模子的句子） | 人类表态离散；模型成套（同构率 0% vs 16.7%） |
| **删除测试**（5 处闲笔，删掉有无影响） | 人类“毫无影响” 1/5；AI 稿 3–4/5 |
| **作者在场测试**（划掉对话只读叙述，问“这里有一个人吗”） | 人类 3.73–8.40 vs AI 0.64–1.89 |
| **用力过猛测试**（找“像在完成任务”的表态） | 实测：“更用力” = “更假” |

**判定原则**：**两个以上独立评委指向同一处 → 必改。** 只有一个评委提到且引不出具体句子 → 可先放过。

**在 low 模式的处理（v6.3.0 修正）**：它**不能并入"判断合并"那一次调用**——合并意味着由**同一个 agent**做，而那个 agent ① 知道全部规则（它按规则打磨的）② 刚打磨过这份稿子 ③ 本身就是被评对象。**正确做法是"独立但极轻"**：仍另起子代理，但任务包压到最小——**只给纯正文 + 4 个问题**。它是全流程**最便宜**的角色（输入一章、输出几行，且"没有"也是有效答案）。**要省，就省它的输入，不要省它的独立性。**

**自适应抽检（v6.5.0）**：工业的跳批检验。连续合格 0–2 章 → **全检**（四项全做）；连续 ≥3 章合格 → **抽检**（只做「同构 + 作者在场」）；任一项失败 → **立刻回全检，计数归零**。**省的是"顺风局的重复劳动"，不省的是保证水平。**

### 3.5 置信度绑定与重试三出口

**问题**：读完“这章不太行”却继续往下走，是长篇创作中最贵的动作。当检测到质量问题时，Agent 的默认反应是“在原地改一遍”——这通常不会产生质的飞跃，只是把同样的问题换一种表述重写一次。

**解法**：J-Novel 在质检完成后引入“置信度定档”机制。Agent 必须根据自评结果将本章划入三档之一：

| 读数 | 触发条件 | 义务 |
|------|---------|------|
| **稳** | 人侧 ≥7 项 且 评分 ≥70 且 无未决杠精点 | 放行 |
| **薄** | 人侧 4-6 项 / 评分 65-69 / 有 1 个未决杠精点 | 点名最薄项 + 理由，然后放行 |
| **晃** | 人侧 ≤3 项 / 评分 <65 / retryCount ≥2 | 禁止原路重走，三选一出口 |

三选一出口：
1. **升标准**：升到锚点章标准，全调专项后重检
2. **换路**：用完全不同的原语重述“本章要完成的三件事”，重新动笔
3. **上报**：停下问用户

当 `retryCount == 2` 时，出口 C（换路）被强制触发，且禁止沿用上一稿的场景顺序与开场类型。当 `retryCount == 3` 时，系统停止自动修复，向用户上报——因为这表明问题被错误地框架化了，继续撞墙不会有新结果。

**`retryCount` 落盘（v6.5.0）**：它此前**只存在于铁律七的规则描述里（「==2 强制换路」），从未被记录过任何一次实际值** → 于是「一次合格率」在**定义上不可统计**。现在由 `make_workorder.py --archive <章号> --retry <N>` **当场落盘**。

### 3.6 链式流水线：并行的单位是工序，不是章节

**问题**：并发写作是提速的有效手段，但也是最常见的质量灾难源。早期方案采用“每批 5 章、一章一子代理并行”，其失败不是纪律问题，而是撞上了三个硬事实：

1. **章节是链式依赖的**：第 N+1 章的开头必须是第 N 章结尾的直接延续（人物在哪、什么情绪、知道什么、有没有受伤）。而并行派发那一刻，第 2–5 章的真实结尾**还不存在**——子代理只能拿细纲里的“规划结尾”充数，偏差从这里产生。
2. **乱序完成是章节并行的数学必然**：5 章同时开写，完成时间必然不同（章难度、子代理速度、触发重写）。加再多“请按顺序完成”的规则都没用。
3. **契约不冻结，状态就会分叉**：第 2 章的子代理写到一半改了个设定，第 3 章的子代理还在按旧设定写。两章各自都对，拼起来就错。

**解法**：J-Novel 把并行单位从「章节」换成「工序」——**章节串行推进（保连贯），章内工序并行（保速度）**：

```
初稿：第1章 → 第2章 → 第3章 → ...      ← 笔手串行，天然持有上一章真实结尾
打磨：      第1章 → 第2章 → 第3章 → ...  ← 磨手并行，不产生剧情，可以跟着跑
缝合：            第1章 → 第2章 → ...    ← 主编串行缝合章节边界
```

**三级策略**（按质量／速度取舍）：

| 档 | 名字 | 初稿 | 打磨 | 适用 |
|---|---|---|---|---|
| **A** | 链式串行 | 串行 | 串行（定稿才写下一章） | 锚点章、卷末高潮；追求零瑕疵 |
| **B** | 链式流水（默认） | 串行 | 并行（磨手跟着初稿跑） | 绝大多数章节 |
| **C** | 章节并行 | 多章并行 | 多章并行 | 仅“真独立章”（番外／支线日常） |

**判据**：一章能否进 C 档，只问一句——**“这章的开头需要接上一章的结尾吗？”** 需要 → 只能 A/B；不需要 → 可 C。

协议的配套机制包括：

- **接口契约（冻结）**：派发前，主编为每章填一份契约（进入状态／退出状态／承接要素／交付钩子），逐项写死。键名固定、一行一键（`进入·位置时间` / `退出·情绪` …）。子代理若要偏离契约，必须先申报 + 主编裁决 + 更新相邻章契约，不得自己改了往下写。**校验：`check_contract.py <项目>` 做相邻章状态 diff，退出码 1 = 先修契约再派发。**
- **前序锚点**：每个子代理写前必读——本批细纲 + **上一章真实结尾**（500–800 字，由主编从刚写完的正文里截取）+ 状态台账出场人物条目 + 文风锚点示例。**走交接卡：`make_handoff.py --all --write`。**
- **锚点滚动**：每批结束后，主编从本批真实章节中抽取最代表文风的 1–2 段，更新下一批细纲的文风锚点示例。**三层锚**：**全书锚**（第 1 章，**永不滚动**）／**卷锚**（每卷第 1 章）／**批锚**（本批首章，滚动）。**只给批锚时累积漂移在定义上不可见**。
- **批次验收闸门（脚本化）**：跑 `check_batch_gate.py <项目目录>`，退出码 0 才许继续。它查：乱序完成、字数达标、质检痕迹齐、台账推进、章节边界无悬空钩子、崩坏红线 1。
- **章节边界的人工放行**：`check_continuity.py` 是提示工具而非硬闸门——“刻意留到后章回收”是正常写法。复查后若判定正常，需在创作台账写入一行显式记录（`boundary-waived: 第8→9章，理由：…`，理由 ≥8 字），让“我复查过”成为一个有地址、可追溯的事实。**配套还有指标层放行（`indicator-waived`），给耦合指标一个合法的终止条件。**

### 3.7 三道闸门：把"发现缺陷"放在"缺陷被定稿"之前

贯穿全局的一条判据（v6.2.0）：

> **质量闸门的位置必须满足：发现缺陷的时点 ≤ 该缺陷被"定稿"的时点。**

晚一步，修复就从“在队列里改”变成“**回头改**”：要重做缝合、重抽文风锚点、重写台账，成本超线性；而且**回头改本身会成为新的不一致源**。

由此得到一条反直觉的推论——**质检不是"全部提前"，而是"只把跨章项提前"**：

| 缺陷类型 | 晚发现的代价 | 闸门频率 |
|---|---|---|
| **单章缺陷**（某段 AI 味重、比喻超标） | 还是只改一章 → **不敏感** | 批末查也行 |
| **跨章缺陷**（开场/章末同质、声音漂移、设定分裂、边界断裂） | 要改 N 章 → **极度敏感** | **必须每章查** |

**三道闸门**：

| 闸 | 时点 | 查什么 | 成本 |
|---|---|---|---|
| **章闸** | 每章初稿后 | **单章机械项**：字数 / 句法节律 / 词汇指纹 | **0**（脚本） |
| **窗闸** | **每章初稿后**，滚动窗口 3 章 | **跨章项**：章内重复 / 开场同质 / 章末同质 / **声音漂移** / 边界连续性 / **交接卡过期** | **0**（脚本） |
| **批闸** | 批次末 | **判断项**（1 次调用）+ 全批视野 + 设定激活率 | **1 次调用 / 批** |

窗闸的三个硬要求：① **必须每章跑**（就是上面那条判据）；② **报告必须定长**（`--window N --brief`）——否则明细随章数变长，每章重读一遍 = 把省下的上下文又花回去；③ **批闸交给子代理跑**，不是主编（否则主编要把整批正文装进上下文）。

### 3.8 主编零正文与边界冻结

**主编零正文（成本洞的补法）**：链式流水线把质量押在主编身上——定契约、转交"上一章真实结尾"、缝合章节边界。而这三件事的传统做法都是让主编读正文。于是出现一个结构性矛盾：**低消耗模式的全部收益来自"子代理上下文彼此隔离、不累积"，而主编是流水线里活得最久的角色——它每章要读两遍正文，读过的每一章都留在它的上下文里，跟着它之后每一次调用被重发。子代理那边省下的钱，被主编一个人花回去。**

**解法**：`make_handoff.py` 从正文裁出**交接卡**（上章真实结尾原文 + 本章首段 + 本章末段 + 三者指纹，≤800 字）。主编**读卡不读正文**——每章进入主编上下文的量从两整章（~6000 字）降到一张卡（~800 字），且**不再随章数累积**。

**这不是牺牲质量换省钱**：缝合需要的信息**就是边界段**，读全文反而把它淹在 6000 字里。裁卡是信息提纯。

**边界冻结（文本层接口）**：流水线里有个隐蔽的坑：

```
笔手写第 N+1 章时，拿到的是第 N 章的【草稿】结尾
        ↓
磨手随后打磨第 N 章，可能把结尾改写
   （"换落笔形态"这类指令**恰恰鼓励**改结尾）
        ↓
第 N 章【定稿】的结尾 ≠ 第 N+1 章开头所承接的结尾
        ↓
两个都"对"，拼起来断 —— 而且没有任何脚本会报
```

**解法**：把 chained-pipeline 已有的「**契约冻结**」从**状态层**延伸到**文本层**——交接段（首段 + 末段）是**接口**，只有主编能动；磨手打磨交接段之外的一切；中间段落改动**不影响**（指纹不变、卡不过期）。

**指纹让"冻结"从纪律变成可检测**：改第 3 章末段，`make_handoff.py --check` **同时报出第 3 章和第 4 章**——正好指向那对被拆散的接力棒。

### 3.9 任务包编译器：把"记得填"变成"编译不过"

任务包此前由**主编手工装配**（十项）。手工装配有三个必然缺陷，**每一个都实测发生过**：

| 缺陷 | 实测表现 |
|---|---|
| **槽位没有 schema** → 少填一个没人知道 | 「锚点滚动」「句法目标表」写了却**从未进包**（漏了几个月） |
| **槽位没有预算** → 有的一塞 3000 字 | 实测每次调用平均重发 **149,675 tokens** 上下文 |
| **脚本能拿到的东西却靠人记** → 必然漏 | 上章真实结尾 / 契约 / 锚，**都能从文件里自动抠** |

**`make_task_package.py` 做三件事**：

1. **装配** —— 脚本填它拿得到的：**上章真实结尾 / 接口契约 / 批次全局三件套 / 章号奇偶字数 / 本批已用过的开场-章末型**（前馈槽位）。其余留成**显式待填标记**（世界设定包 / 台账条目 / 作者画面 / 已知病灶 / 诊断句）。**脚本不假装自己能写世界设定包。**
2. **预算** —— 九个槽位各有上限，**总上限 5000 字**。
3. **校验** —— `--check` 对「缺必填槽位 / 超预算 / 待填残留」**退出 1**。**缺槽位 = 拒绝开工**。

**前馈槽位的形态是关键**：**给已发生的事实，不给目标值**。项目实测过"底线当目标、配额当目标"被 hack；这里只陈述"已经用过什么"让写手避开，**没有任何可以"凑"的数字或指标。** 实测立刻在真实项目上抓到两处既有缺陷：第 2、3 章连续同型章末（丙·喜剧反转），以及第 2/3/4 章连续三章「续接型」开场。**这些此前只能等写完才发现。**

### 3.10 世界设定传导链

**问题**（2026-09-20 真实事故）：`00-故事圣经.md` 在整个 SKILL 里**只有一处提及**（项目结构树），**创作期零读点**。于是世界观在计划期写完就**断了传导链**：大纲管"这章发生什么"、人物档案管"谁在场上"、细纲管"这场怎么演"，**没有一样回答"这个世界长什么样"** → 落笔时不是一个庞大的世界，子代理之间不是同一个世界。

**解法**：

- **圣经模板**：世界观手册从 6 行占位符 → 一本手册（9 节骨架：世界前提/底层规则含**边界**/权力格局/地图与场景卡/**日常与生态**/历史与传说/**专有名词表**/留白区/视角透气）。**写法铁律：写实体不写形容词。**密度判据按短/中/长篇分档。
- **子代理任务包**：新增「世界设定包」槽位——场景卡 + 规则切片 + **专有名词表** + 三条硬设定，**给原文不给路径**。
- **速查卡**：「一之三、世界一致性」四条纪律（只用表内词 / 要造新词必须报 / 边界不可违反 / 硬设定是蓄能装置不可解）。
- **主入口**：`SKILL.md` 动作 2 加「世界切片」；动作 10 加「设定回流」。
- **脚本**：`check_worldbuilding.py` 把"世界观被吃掉"变成可数的三个量——**手册密度 / 设定激活率 / 未登记新词**。

**最重要的判据（在任务包里的定位）**：**它不是参考读物，是约束。** 表里已有名字的东西**禁止另造同义新词**；要造新词必须在回报里单列 `新增专名：` 一行。**缺了这一包，子代理会不自觉地发明自己的世界——两章之后它就和别人写的不是同一个了。**

### 3.11 剧情脚手架：作者意图的全生命周期管理

**问题**：Phase 3 的核心规则是「全程禁止向用户确认任何事」，而整个 Phase 3 只有**一个**被允许的确认点——锚点章定调（确认**文风**）。**"写什么"从来没人问过。** → 作者的剧情意图在 Phase 2 之后再没有出口。

**解法**：一条贯穿全流程的「作者意图」线：

| 阶段 | 时机 | 干什么 |
|---|---|---|
| **P1 采集** | Phase 1 采访（+ 采访途中随时） | 把作者**已有的**剧情设想挖出来、磨清楚（脚手架五问：定位/内容/因果/情绪/**画面**） |
| **P2 落点** | Phase 2 规划 | 大纲必须兑现条目，或明确记「未采用（原因）」 |
| **P3 续航** ★ | **Phase 3 写作期** | **按需回头问作者**：缺方向时挖意图、摊素材、给建议（**方向对齐四步**：① 先问（不预设答案）→ ② 先摊素材（不是先给建议）→ ③ 再给建议（2–3 条互斥路线 + 各自代价）→ ④ 留口子） |
| **P4 对账** | Phase 4 / 5 验收 | 检查状态推进；「已偏离」有没有标原因 |

**P3 的介入频次不按章号，按「作者当前的意图浓度」**——看最近 2–3 次交互，不看历史厚度。**连续 2 次"都行"才降级**；降级时留一句"想参与得多一些随时说"；作者主动开口立刻升档。

**作者画面 = 人味源**：追问「问 5 · 画面」得到的作者原话（例：**"他修的时候没人看，他自己在那儿看了半天。"**）会**原样进子代理任务包**，像人类范本一样**给原文不给路径**。**给画面，不给解释**——绝不把它改写成要求，否则人味立刻消失。

**与 Phase 3 铁律的关系**：这是**第二个例外**——和锚点章同级，有边界、有触发条件、可关闭。两条例外的设计逻辑是同一个：**只在一个自然的停点上确认一次定调，之后全力开写。**

### 3.12 工业化：工单、良率与缺陷帕累托

**问题**：整条链此前**只有分子（成本）、没有分母（一次合格率）**，而返工**高度集中**且**大部分本可以"给定"**。

| 账 | 在哪 | 谁写 | 有没有返工列 |
|---|---|---|---|
| 质量账 | `04-质检档案.md` | **人肉抄** | ❌ |
| 成本账 | `~/.workbuddy/traces/` | 平台自动 | ❌ |

两账**没有共同的键**（一个是 markdown 行、一个是时间窗）→ "哪一章最贵""改了几轮"都答不出来。返工的真实成本是 **额外调用轮次 × 每次调用的上下文**（实测中位 **149,675 tokens/次**），所以"没有返工列"= **成本模型缺一半**。

**解法**：`make_workorder.py` 做两件事：

**① `--archive <章号>` —— 每章质检那一步就调它（一条命令 = 质检 + 归档）**：

```bash
python scripts/make_workorder.py <项目> --archive 5 --retry 1
```

它**内部跑完全部机械脚本**（铁律九"一次跑完全部脚本"），然后：按**退出码**判定缺陷类型；把一行**工单**追加进 `06-章节工单.md`；**`--retry`** 把 `retryCount` / 返工轮次**落盘**。**工单写独立文件，绝不碰 `04-质检档案`**——两份记录性质不同（`04` 是人写的判断，`06` 是机器写的度量），**实测踩过**：初版 upsert 进 04，把用户项目里那一行的 **9 列质量数据覆盖成 6 列**（已还原）。

**② `--report` —— 良率 + 缺陷帕累托 + 成本回填**：

- **一次合格率（FPY）**，判据 **≥70%，低于就停线分析**
- **缺陷帕累托**——**决定该改哪条规则，只改头部 1–2 类缺陷**（不要同时动多条规则）
- 成本列从平台轨迹按日期回填

**这仍是"给耦合指标一个可解目标"的应用**：FPY 才是该优化的目标函数，而不是"17 项全绿"。**"一次合格率"是成本模型的分母**——`总成本 = 单件成本 ÷ FPY`。


## 4. 实验与评估

### 4.1 实验设置

为验证 J-Novel 框架的有效性，我们在实际创作场景中进行了两类评估：

**（A）两项完整案例研究**：

| 案例 | 类型 | 章数 | 总字数 | 写作模式 |
|------|------|------|--------|---------|
| 案例 A | 西式奇幻 | 7 章 | ~2.8 万字 | 串行（serial） |
| 案例 B | 都市恋爱喜剧 | 12 章 | ~4.5 万字 | 串行（serial） |

两部作品均由同一套 J-Novel 系统生成，区别仅在于题材和人物设定。写作过程中，所有“作者确认”环节被严格限制在 Phase 2 的锚点章定调和 Phase 5 的完稿验收两个时间点，中间阶段完全由 Agent 自主驱动。

**（B）多轮真实项目 A/B 盲测**（v4.2 起持续进行）：

- 同一细纲、同一人物、同一字数，只有规则包不同
- 由多个独立子代理分别产出，由 **3 位不同视角的评委盲评**（各自独立乱序、含已知-AI 阳性对照）
- 三轮共进行了 5+ 次盲评，**每次盲评的结论都直接改写了规则**

**（C）真实项目端到端体检**：

- 《骨灰级》10 章 / 36,836 字（发现"全绿但不合格"的完整案例）
- 《我不是大师》第 01 章（发现"跳章提示"bug 与"碎句化"型缺写）
- 《我战力全负》（发现章末同质）
- 《玫瑰下的狩猎》第 01 章（发现三脚本分母差 12.6%）

### 4.2 定量评估

| 句首引号占比 | 18.4–30.6% | 21.3% | 19.7% | 趋近人类 |
| 平均句长（字） | 22.7–36.6 | 28.4 | 26.1 | 趋近人类 |
| 破折号/千字 | 0.03–0.29 | 0.62 | 0.78 | 达标（旧基线 0.97 已收紧） |
| 身体部位/千字 | 0.31–0.55 | 0.48 | 0.43 | 趋近人类 |
| 情绪词/千字 | 0.32–0.35 | 0.34 | 0.36 | 趋近人类 |
| 明喻/千字 | 1.05–1.27 | 1.18 | 1.22 | 趋近人类 |
| 对话占比 | 20.4–33.5% | 27.6% | 29.1% | 趋近人类 |
| 动作短语密度 | 0.106–0.247/千字 | 0.19 | 0.17 | 趋近人类 |
| 通用模板短语密度 | 0.55–1.22/千字 | 0.81 | 0.92 | 趋近人类 |

**关键观察**：表中 10 项指标均落在人类基线范围内。尤其值得注意的是“情绪词密度”与“身体部位密度”两项——早期版本中，这两项呈现出典型的“补偿式偏移”（情绪词过低、身体部位过高，后者一度达人类的 5–7 倍），表明 J-Novel 在 2026-08-29 版本修订后成功纠正了这一系统性问题。

**（B）盲评结果**：

| 版本对 | 章 | 判决 |
|---|---|---|
| v4.2 vs v4.0 | 第 12 章（静场章） | 新口径 **3:0 胜** |
| v4.2 vs v4.0 | 第 13 章（冲突章） | 旧口径 2:1 胜 |
| 生产测试（新 SKILL 从零写第 2 章） | 第 2 章 | **2:0 胜**，两位评委均选本章 |
| 纯正文条件（拉平格式后） | 第 1 章重写稿 vs 原稿 | **原稿 3:2 重写稿**（合并两轮） |

**（C）真实项目体检发现的"全绿但不合格"完整案例**（《骨灰级》，10 章）：

| 指标 | 低于人类下沿 | 人类区间 | 硬线 | 判定 |
|---|---|---|---|---|
| 平均句长 | **10/10 章** | 22.7–36.6 | ≥18 | 全绿 |
| 动作短语 | **10/10 章**（值 **0.0**） | 0.106–0.247 | ≤0.4 | 全绿 |
| 长对话占比 | **9/10 章** | 15.8–27.7 | ≥8 | 全绿 |
| 超长句占比 | **8/10 章** | 4.7–19.0 | ≥3 | 全绿 |
| 身体部位 | **7/10 章**（值 **0.0**） | 0.31–0.55 | ≤1.0 | 全绿 |
| 作者在场 | **4/10 章** | 3.73–7.84 | 2.5–12 | 全绿 |

**成因**：`max` 型指标把「0」当最完美（身体/动作/量词），`min` 型指标的硬线又都设得比人类下沿松（句长 18 vs 22.7、长对话 8 vs 15.8、超长句 3 vs 4.7）。→ **"没踩线"被读成了"达标"。** 修法是**新增「人类区间命中率」读数**，实测分离度极干净：人类三部 100%/94%/71%，真实项目《骨灰级》41%（单章 29–47%），AI 三部 29%/5%/5%。

**（D）成本基线**（来自平台侧真实 usage，471 个会话 / 8,457 次调用）：

| 指标 | 实测值 |
|---|---|
| promptTokens（每轮发出的上下文） | **2,336,020,596**（99.7%） |
| ├ 其中 cacheRead | 2,305,004,145 = prompt 的 **98.7%** |
| └ 其中新增输入 | 31,016,451 = **1.3%** |
| outputTokens（模型产出） | 6,995,983（**0.30%**） |
| **放大倍数** | **334×** |
| **每次调用平均重发上下文（中位）** | **149,675 tokens/次** |
| 同（p90） | **420,203 tokens/次** |

**结论：优先级被数据改了。** 会话长度分布显示中位会话只有 **8 次调用**——"调用次数爆炸"不是主症；长会话（>120 次）只占会话数的 1.3%、贡献 16.2% 的 cacheRead。**成本的大头在"被乘数"——每次带多重的上下文。**

### 4.3 定性评估

**叙事连贯性**：案例 A（奇幻篇）在 7 章内完成了主角从坠落、生存、融入小镇、兽人夜袭、到获救的完整弧线。人物状态台账（`03-状态台账.md`）跟踪了塞拉芬娜从“戒备”到“动摇”的渐变，以及诺瓦从“钝感”到“开始困惑”的内省推进。所有伏笔（族徽发光、预言卷轴、疤脸霍恩盯梢）均在第 7 章结束前形成了闭环。

**文风统一性**：两部作品在文风锚点示例的指导下保持了全局一致性。案例 B（都市篇）的第一人称叙述口吻从头至尾稳定——“穷学生的算账式心理”贯穿始终，“卖艺不卖身”式的冷幽默在 12 章中未发生过漂移。

**AI 味诊断**：在两个案例中，AI 味自评量表（11 项）的最终评定均为“可交付”。具体的 AI 侧检出项集中在早期章节的“心理描写还原度”和“开场同质性”——但这些在 Phase 3 的单点手术修改中被纠正，未出现在终稿中。

**盲评发现的新指纹**：**工程脚手架**（v5.2.0）。两位独立评委**各自独立**把「本章概要 / 章末型：丁·悬念 / 伏笔标记（预计第X卷回收）」列为**最强 AI 指纹**——原话："人类作者投正文不会写'章末型：丁'""外挂的元数据头部暴露了流水线出身"。修法：章节产物改为**双文件**——`chapters/第XX章-标题.md`（纯正文）+ `chapters/_meta/第XX章-标题.meta.md`（工程字段）。**这条对每一章生效，且此前所有盲评的结论都被格式污染过。**

**模板化断言被证伪的案例**（v4.3.0）：一轮 A/B 里，加了新规则的那一版**所有脚本指标全部通过**（作者在场指数 0 → 7.93，完美落在人类区间），**但盲评以 3:0 判负**。三位评委各自独立地从同一个文件里挑出同一组三句：

> 老王在那儿修了六年车，**这种事也值得**专门打个电话去举报？
> 单数日子的排骨回锅，**这算什么**规律？
> 天比平时黑得早，六点不到就黑成这样，**这算什么**秋天？

**骨架完全一致**（`[复述事实] + [这算什么/也值得] + ？`，位置全在段末）。评委原话：「**更用力的那一篇，读起来是更假了，不是更好了。**」「差别不在技巧，在**是否成套出现**。」量化：同构率 16.7% / 12.5%（加了规则）vs 0% / 0%（没加）。

这直接催生了三条**硬约束**（防"配额填成模板"）：① **禁止同构**——同类表态不得出现两次以上相同句式骨架；② **必须挂钩**——每处表态要指着本章的具体事件/细节/人物；③ **区间不是下限**。

### 4.4 限制说明

1. **规模限制**：当前主要实证案例的章节数（7–12 章）不足以完全验证框架在 50+ 章长篇中的抗漂移能力，尽管机制设计本身（Seam 重读、锚点滚动、三层锚）指向了可扩展性。

2. **对照实验的局限**：已进行多轮 A/B 盲评，但**未进行"有/无 J-Novel 机制"的系统性对照实验**，无法量化每个单独机制的边际贡献。

3. **主观评价部分集成**：读者反馈数据尚未完全纳入评估，部分定性判断基于系统自检与作者内部评审（`reasonix-novel-reader-sim` 子技能提供三层读者验证，但仅在锚点章/卷终触发）。

4. **基线选择偏差**：人类基线取自三部商业化小说，其风格偏向“男频网文”，可能不适用于所有题材。`--baseline` 参数允许重新校准，但增加了使用门槛。

5. **独立质检子代理的效力尚未做完整 A/B 验证**：机制建设与注册已完成（v4.4.0），但"有它 vs 没它"的完整对照仍是待办（`CHANGELOG` 里明确记录）。

6. **本框架自身的失败模式并未消除，只是被监控**：假闸门、声明-实现漂移、指标被 hack、规则过度执行——这四类失败在历史上反复出现（v4.5 修了 6 个假闸门，v4.6 又在同一批修复里引入 3 个同型问题）。**配套的 `audit_release.py` + `test_guards.py`（58 例故障注入）是对抗手段，不是治愈方案。**


## 5. 局限性与未来工作

### 5.1 当前局限性

**（1）执行负荷**：J-Novel 的完整流程（Phase 0–5）对 Agent 的认知负荷要求较高。每章的 10 步最小必做清单、质检脚本调用、台账回写等操作在串行模式下会增加单章处理时间。对于短篇创作（<5 章），该框架可能显得“过度工程化”。

**（2）依赖链脆弱性**：框架依赖多个 Python 脚本（`check_human_rhythm.py`、`check_aistyle.py`、`check_continuity.py`、`check_repetition.py`、`check_chapter_wordcount.py`、`check_batch_gate.py`、`check_contract.py`、`check_worldbuilding.py`、`make_handoff.py`、`make_task_package.py`、`make_workorder.py`、`audit_release.py`、`audit_tokens.py`、`test_guards.py`、`convert_to_txt.py`、`_shared.py`）和 12 个专业子技能。在子技能未安装或脚本环境不完整的情况下，部分质检能力会降级为内建指南兜底——这虽然不会导致系统崩溃，但会降低自动化的可靠性。

**（3）基线泛化性**：句法层阈值基于三类男频网文计算，其人类基线（如句长 22.7–36.6 字）可能不适用于严肃文学、诗歌化散文或轻小说译文体。尽管 `--baseline` 参数允许用户重新校准，但这一步骤增加了使用门槛。

**（4）并发模式复杂度**：链式流水线下的主编职责清单（接口契约冻结、批次验收闸门、锚点滚动、真实结尾转交、边界缝合）对主编 Agent 的质量要求极高。在并发场景中，主编本身仍是单点瓶颈。

**（5）指标耦合**：17 项指标并非正交——补长句会把明喻密度挤上去，补数字会把情绪词挤下去。生成时配额卡能压住大头，但一次全绿通常做不到，需要对残留的 2–3 项做一轮批量精修。**CTQ 分层是权宜之计，不是解决**：它把不可解问题降为可解，但没消除耦合。

**（6）“声明-实现”漂移的长期风险**：本项目历史上反复出现同一类缺陷——“看起来已经做了，实际从未触发”（如守卫被注释骗过、共享实现被本地函数覆盖、定义了却从未被调用的缓存函数）。已配套一层“声明-实现一致性”守卫与一个 58 例故障注入测试脚本来对抗，但这类漂移是结构性的，需要持续投入。

**（7）规则过度执行**：方向对的规则会被执行到极端。已实测的形态包括——「用道」→ 92% 对话都挂；「一句一段」→ 景物也切碎（"空镜蒙太奇七连"）；「时间/地点开头」→ 三到五章开头同一套空镜。**每一条"方向对但强度没写"的规则，都可能在生产出新的 AI 味。** 这解释了为什么 v4.2.1 之后所有的规则都必须写明"用多少、不要过量"。

**（8）成本纪律"被乘数"仍未压到合格线**：实测每次调用平均重发 **149,675 tokens** 上下文，仍远超判据（<100k）。任务包编译器与主编零正文是**机械手段**，但从 149k 压到 50k 需要更激进的策略（如任务包进一步瘦身、内容分层缓存等），当前尚未实现。

### 5.2 未来工作方向

1. **自动化基线校准**：开发脚本自动扫描输入的人类样本并输出建议阈值，降低新用户校准门槛。

2. **读者反馈集成**：将 `reasonix-novel-reader-sim` 子技能升级为完整的读者反馈管道，在 Phase 4/5 中自动生成三层读者验证报告，并纳入全书质量报告。

3. **多卷长篇验证**：在 50 章以上的长篇项目中运行完整流程，收集 Seam 重读的有效性数据（如“重读前后 Agent 恢复状态的准确率”），为框架的可扩展性提供定量证据。

4. **独立质检子代理的完整 A/B 验证**：同一章，一组只跑脚本、一组跑脚本 + 独立质检并按其意见修改，然后盲评对比。

5. **跨题材基线研究**：扩展人类基线数据库，覆盖言情、悬疑、轻小说、历史等更多题材，使阈值自适应。

6. **"中段并行 · 边界串行"**：把并行单位从"章"切成"中段+边界"，理论收益最大（v6.3.0 已记录为留待下一轮）。依赖契约生成点（已补），但改动面大，**应先量基线再动**。

7. **压"每次调用平均重发上下文"到 <100k**：这是当前成本工程的**第一优先级**。候选手段——任务包槽位预算进一步收紧、按需读而非预载、分层锚只给该给的、子代理上下文复用等。

8. **`drafted` 章节状态**：让"笔手领先磨手 ≤3 章"这条流量控制在文件层面可机械核对（当前只写成规则，未改 JSON schema）。

9. **`make_anchor.py`**：三层锚的文本载体脚本化——当前三层锚只在**检测端**落地，写手侧的锚文本仍按批次锚滚动机制手工维护。

### 6.3 快速启动

1. 将 J-Novel 作为 Skill 安装到 Agent 宿主环境中
2. 在目标工作目录下创建 `novel-output/` 文件夹
3. 调用该 Skill，Agent 自动进入 Phase 0 初始化
4. 用户提供创作想法后，Agent 按 Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 顺序驱动流程
5. 系统产出位于 `novel-output/{小说名}/` 目录下的完整作品文件


### 6.4 维护者注意

**改动本框架的任何规则或脚本后，须运行 `python scripts/audit_release.py --regress`（退出码 0 才算通过）；改动任何检查项后，须再运行 `python scripts/test_guards.py`——"加了守卫"和"守卫有效"是两件事。**

历史教训反复印证了这一条：`test_guards.py` 的前身在人工自测中**连续抓到 4 个"守卫自身失效"**；v6.4.0 又新增两种形态（合法兜底 import 掩盖委托检测、`--selftest` 出现两次导致按存在性判的守卫失效）。**新增任何"有退出码的闸门"时，必须同步三个地方**：① `SKILL.md` 每章最小必做清单 ② `phase3` 执行清单 ③ **速查卡（子代理唯一读物）**。漏掉第三处最严重——主编看得见、子代理看不见。


## 7. 结论

本文提出了 J-Novel，一个面向 AI Agent 的长篇小说创作框架。该框架的核心贡献在于将“过程层状态管理”引入了叙事生成任务，通过八份状态文件、事实三态标记、Seam 重读、三站齐备审计、两层量化质检、独立质检子代理、链式流水线协议、三道闸门、边界冻结、任务包编译器、工业化度量（工单/FPY/帕累托）等一系列机制，系统性地应对 LLM 在长篇创作中面临的三类最昂贵的事故：连续性错觉、长跑漂移和 AI 味顽固复发；并同时把**成本与质量的耦合**用可执行工程手段压住。

在多部完整小说的实证验证与多轮真实项目 A/B 盲测中，J-Novel 产出的文本在句法与分布层指标上均趋近于人类基线，同时消除了传统 AI 创作中常见的逻辑断裂与模板化表达。该框架已在生产环境中完成了端到端的验证。

**但本框架最重要的产出或许不是这些机制，而是它在构建过程中反复发现的自身失败模式**：

- **假闸门**：看似做了检查、实际从未触发。比"没做检查"更危险，因为它制造虚假信心。（v4.5 一次修掉 6 个）
- **声明比实现走得快**：注释/docstring 说改了，实际没接上。（v4.6 修好 6 个假闸门，又在同一批修复里引入 3 个同型问题）
- **指标被 hack**：底线当目标 → 配额当目标 → 方向当强度 → 真指标做成配额也会变模板。（同一类错误出现 4 次）
- **规则过度执行**：方向对的规则被执行到极端，生产出新的 AI 味。

这四类失败的共同特征是：**它们都不会报错。** 唯一的对抗方式是**故意把代码改坏、看守卫是否报警**——这就是 `test_guards.py`（58 例）存在的理由，也是本框架对"工程化 AI 写作"最诚实的贡献。

**开源声明**：本框架为纯粹的学术开源项目，旨在为长文本生成领域提供一个**可复现、可证伪**的工程化研究基线。欢迎研究者复现、扩展或改进其中的任何机制，引用时请注明原始出处（见 `references/` 目录下的原创声明）。**尤其欢迎对本框架自身失败模式的批评与补充案例**——那比"它成功了"更有价值。
