# Phase 2：规划与确认

> **前置条件**：Phase 1 完成，作者已确认故事速写与标题。

本阶段把"聊出来的故事"变成"写下去的工地"：合成故事圣经、生成人物档案/大纲/写作计划三件套文件、生成第一批细纲，最后请作者确认规划与写作模式。

```
本阶段执行清单：
[ ] 1. 【必须】创建项目目录 novel-output/{小说名}/
[ ] 2. 【必须】故事圣经（读 guides/bible-template.md）
[ ] 3. 【必须】人物档案 00-人物档案.md（读 guides/character-template.md + character-building.md）
[ ] 4. 【必须】大纲 01-大纲.md（读 guides/outline-template.md + plot-structures.md + **volume-arc-planning.md（超长篇）**，每章字段完整）
[ ] 5. 【必须】写作计划 02-写作计划.json（含 writingMode/writingTempo）
[ ] 6. 【必须】状态台账 03-状态台账.md（人物/伏笔/时间线，**全部带三态标记**）
[ ] 6.5【必须】创作台账 05-创作台账.md（读 guides/creation-ledger.md，五字段）
[ ] 7. 【必须】第一批细纲（第 1-5 章，读 guides/hook-techniques.md 定招式）
[ ] 8. 【必须】展示规划摘要 + 作者确认（写作模式 + 写作节奏）——**规划摘要必须带「我的保留意见」**
[ ] 9. 【必须】锚点章定调（精写第 1 章 → 作者确认文风 → 抽取锚点示例）
→ 清单全勾 + 作者确认 = 本阶段完成，进入 Phase 3
```

---

## 步骤 1：创建项目文件夹

创建 `novel-output/{小说名称}/`（相对当前工作目录）。后续所有项目文件都放在这里。

## 步骤 2：合成故事圣经

把采访中与你共同打磨的所有设定整理成一份**故事圣经**，用 `write_file` 存到 `novel-output/{小说名}/故事圣经.md`。模板见 `references/guides/bible-template.md`。

**关于圣经的写作要求：**

1. **圣经必须写得非常详细。** 这套圣经可能会交给不同的子代理去执行写作，因此每一个子代理拿到圣经后都应该能理解故事的完整蓝图，写出风格一致、情节连贯的章节。
2. **确保所有共识都被记录。** 采访阶段你们讨论过的、用户特别强调的、反复打磨后定下来的每一个点，都必须写进圣经。这些共识是用户对故事的真实思考，是圣经最重要的内容。
3. **深入详细地撰写。** 一个没参与过采访的子代理，应该能通过阅读圣经直接掌握故事的全貌——包括人物的内心世界、世界观的关键细节、每一章的叙事策略和情感目标。写得越详细，未来的写作越稳定。

## 步骤 3：生成人物档案

创建 `00-人物档案.md`，使用 `references/guides/character-template.md` 模板，参考其说明创建主角、反派、配角档案。**人物档案必须详细**：每个角色的性格核心、致命缺陷、说话风格/口头禅、恐惧/弱项、背景故事都要具体到可以直接指导写作的程度。写作阶段每章开始前都会读取出场人物的档案，所以这里写不清楚，后面每一章都会受影响。

## 步骤 4：生成大纲

创建 `01-大纲.md`，使用 `references/guides/outline-template.md` 模板填入完整的章节规划。**大纲必须以人物驱动情节**——参照 `00-人物档案.md`，确保情节服务于人物成长弧线。每个章节都要有：核心事件（**2-3 句，禁止一句话**）、承接上章、**开场类型（续接/新起/跳接，默认续接）**、章首引子（仅新起型填写）、悬念钩子、出场人物、场景列表、情感基调、伏笔操作，并登记「人物状态变化表」。

> **超长篇（2000+ 章）必须先读 `references/guides/volume-arc-planning.md`。** 分三步：① 采访阶段就定死「锁死清单」（卖点/主线悬念/主角内核/世界规则）；② 只详细规划「下一卷 + 下一批 5–10 章」的细纲，卷按「弧」拆分（每弧 20–50 章，写清弧目标/事件链五步/爽点分布/弧末钩子）；③ 把不确定的项放进「留白清单」，每项配"验证什么数据 + 阈值 + 两种走向"。**别试图一次性规划 4000 章——那是中篇的思路，套在连载上必塌。**

> **详细度 = 防断档的第一道防线。** Chinese Novelist 的大纲只有"核心事件一句话"，写长了必然出现上文不接下文、剧情 BUG。融合版要求：核心事件写清"发生了什么+为什么+造成什么后果"，承接上章必填，每章人物状态有变化——这些都是 Phase 3 写前分析（步骤 1）的强制输入，大纲缺字段 = 写作停摆。**大纲写得多详细，写作就有多省心。**

**结构选择**：按题材从 `references/guides/plot-structures.md` 选一个结构骨架（三幕式/英雄之旅/悬疑/言情等），把章节落点填进去。中点反转务必安排——故事进行到一半改变走向的事件。

**情绪编排**：规划章节情感基调时，按「落差/蓄能/释放」设计（Reasonix Mood Composer 的方法论）：
- **蓄能**：关键情绪节点（牺牲、反转、高潮）前 2-3 章必须有积蓄——让读者在节点前对角色产生期待/在乎，眼泪是被"他本来可以不用牺牲"触发的
- **落差**：冲击力来自事件前后之差，不是事件本身——检查每个情绪节点的前后状态是否有足够落差
- **释放**：揭示方式比事件本身重要——证据递进 + 延迟放大，释放后要有余波（下一章开头消化）
- **检查蓄能是否被提前放空**：关键节点前不要用一句玩笑/温暖细节把紧张提前消解
- **反预期失序（P3，防情绪节奏过精确）**：避免全书出现可预测的机械循环（如"虐→暖→燃"不断重复）。在 1-2 个节点故意"反预期"：该虐的地方用一场荒诞的喜带过、该燃的地方故意压一下、该温暖的地方反而冷淡。人类长篇总有"失控"——规划时就留出"失控名额"，让情绪曲线有呼吸、有意外

## 步骤 5：生成写作计划 JSON

创建 `02-写作计划.json`，基于大纲内容填充。**这是项目的唯一真相源**，所有进度、状态、字数都在这里维护。

```json
{
  "version": 2,
  "novelName": "[小说名称]",
  "projectPath": "novel-output/[小说名称]",
  "totalChapters": 30,
  "minWordsPerChapter": 3000,
  "createdAt": "[ISO时间]",
  "updatedAt": "[ISO时间]",
  "status": "planning",
  "writingMode": "[serial|subagent-parallel|agent-teams]",
  "writingTempo": "[marathon|chapter-by-chapter]",
  "chapters": [
    {
      "chapterNumber": 1,
      "title": "[章节标题]",
      "qualityLevel": "[anchor|advance]",
      "filePath": "第01章-[章节标题].md",
      "status": "pending",
      "wordCount": null,
      "wordCountPass": null,
      "retryCount": 0
    }
  ]
}
```

字段说明：
- `qualityLevel`：`anchor` 品质锚点章（开篇/高潮/转折等关键章节，精写）或 `advance` 普通推进章（批量生产）——由你根据大纲判断每章的重要性标记
- `writingMode`：写作模式（步骤 7 由用户选择后填入）
- `writingTempo`：写作节奏（步骤 7 由用户选择后填入）：`marathon` 疯狂创作（一口气写完，默认）/ `chapter-by-chapter` 逐章确认

## 步骤 5.5：生成状态台账

创建 `03-状态台账.md`——**并发的"共享记忆"，连续性防护的第三道关卡**（配合 `references/guides/continuity-check.md` 与 `references/guides/parallel-workflow.md` 使用）：

```markdown
# 状态台账（实时更新）

## 人物状态
| 角色 | 位置 | 情绪 | 关系 | 已知信息 | 身体状态 | 落地 | 最近更新 |
|------|------|------|------|---------|---------|------|---------|
| [主角] | [起点位置] | [起点情绪] | [与各人关系] | [知道什么] | [健康/伤势] | ? | 第0章(开局) |

## 伏笔状态
| 伏笔 | 状态 | 落地 | 埋设/推进章节 | 计划回收 |
|------|------|------|--------------|---------|
| [伏笔1] | 待埋设 | ? | — | 第X章 |

## 时间线
当前故事时间：[开局时间点]
```

> **「落地」列 = 三态标记（铁律五，J-Novel 新增）**
> | 标记 | 含义 | 写法 |
> |---|---|---|
> | `✓` | 已在正文明确写出 | `✓（第3章）` |
> | `?` | 仅规划/推断，未落正文 | `?` |
> | `✗` | 已被后续剧情否定 | `✗（第14章推翻）` |
>
> **默认无标记 = `?`。任何标 `?` 的条目，下游章节不得当作已发生的事实来写。**
> 它回答的是"这条是不是已经写进正文了"——与「状态」列（待埋设/已埋设/已回收）是两个不同的问题，两条都要填。
> 这是长篇里最贵的一类 BUG 的疫苗：第 5 章登记的伏笔，第 20 章被当成既成事实引用。

**更新规则**：
- **每章完成后**：作者（串行模式）或子代理（并行模式）把本章人物终态、伏笔动作写回台账，更新"最近更新"章号，**并把新落正文的条目的「落地」列从 `?` 改为 `✓（第X章）`**
- **每次回写时扫一遍**：有没有标 `?` 的条目已经被后文当成事实写了？命中即修
- **批次间**：主编核对台账一致性（并行模式），发现冲突以细纲和圣经为准裁决
- **卷终**：与 Bible Updater 的伏笔状态机同步（见 `bible-template.md`），并把创作台账的 Verified 逐条拿回正文对账

## 步骤 5.6：初始化质检档案

创建 `04-质检档案.md`——**每章质检痕迹的集中存放处**（质检摘要**不写入章节正文**，正文保持纯净可发布）：

```markdown
# 质检档案（《[小说名]》）

| 章节 | 字数 | 硬性句式 | AI味自评 | 衔接 | 逻辑 | 质量评分 | 杠精结论 | 备注 |
|------|------|---------|---------|------|------|---------|---------|------|
| 第1章 | | | | | | | | |
```

每章质检完成后，把完整质检摘要追加到档案（格式见 Phase 3 步骤 19）。Phase 4 校验与全书质量报告都以本档案为数据源。

## 步骤 5.7：初始化创作台账（J-Novel 核心新增）

创建 `05-创作台账.md`——**你自己的外接工作区**，模板见 `guides/creation-ledger.md`。

```markdown
# 创作台账（每次 seam 重读）

最近重读章号：第0章（开局）

## Goal
一句话。本阶段（或本批次）"完成"意味着什么，写得能判断自己到没到。

## Core
（≤2 条。第三条想进来必须先换掉一条，且换的时候要说出声）
- 文风锚点 —— [一句话 + 它为什么重要]
- 本卷张力 —— [一句话 + 它为什么重要]

## Verified
（编号追加，永不改写。每条写清依据，即它出现在哪一章）
- ✓01 [已落正文的既成事实]（依据：第X章）

## Open
（每条带"什么能终结它"）
- ?01 [还不确定什么] —— settled by: [什么能终结它]

## Next
单一动作，永不为空。
```

**它和 `03-状态台账.md` 的分工（不要混）：**

| | 03-状态台账 | 05-创作台账 |
|---|---|---|
| 记什么 | 故事内状态（人在哪、伏笔什么状态、时间线） | 创作过程状态（我确认了什么、不确定什么、下一步） |
| 回答什么问题 | "现在故事里发生了什么" | "现在我知道什么 / 不知道什么" |
| 谁读 | 子代理写前读起点、写后写回终态 | 主编每个 seam 自己重读 |

**它不是待办清单。** `02-写作计划.json` 管"还剩什么没做"，创作台账管"现在已经确定了什么"。它们回答不同的问题，谁也替代不了谁。

## 步骤 6：细纲与章节任务卡（按写作模式分级）

> **细纲的本质是对 LLM 的写作指令。** 生成细纲前先读 `references/guides/prompt-engineering.md`——它回答一个关键问题：**你写进细纲的每一条指令，会不会诱导 LLM 用"最省力的 AI 味写法"去执行它？** 比如你写"补充细节"，LLM 就用破折号补刀；你写"写具体"，LLM 就写"一个人"。细纲指令的措辞，决定了子代理初稿的天花板。

> **细纲不是一刀切必做。** 它的核心价值在"并行风格统一"（子代理看不到主编上下文）；串行模式下主 Agent 持有圣经+大纲+台账+已写章节，完整细纲边际价值低。**分级策略：**

| 写作模式 | 细纲策略 | 产出 |
|---------|---------|------|
| **串行 serial** | 生成**章节任务卡**（下方轻量版） | 每章一张任务卡 |
| **子代理并行 subagent-parallel** | **必须完整细纲**（下方完整格式） | 每批一个细纲文件 |
| **锚点章/高潮章**（任意模式） | 可选生成**单章完整细纲** | 高价值章节精写 |

### 章节任务卡（串行模式用，比完整细纲轻 80%）

```markdown
## 第 N 章任务卡
- **核心任务**：[本章必须发生的事件，2-3 句]
- **衔接锚点**：[承接自第 N-1 章结尾的哪个画面/悬念]
- **人物状态**：起点[查台账] → 终点[变化]
- **伏笔操作**：[埋/收/推进]
- **情绪曲线**：[起 → 承 → 转 → 合]（是否反预期？见步骤 4 情绪编排）
- **本章亮点**：[1 个让读者记住的瞬间]
```

### 完整细纲（并行模式用）

圣经和大纲告诉你"每一章要写什么"，但没告诉你"这一章怎么写"。细纲是施工图纸——它告诉你这一章分几个场景、每个场景在哪里发生、谁出场、什么情绪、埋什么伏笔、场景之间怎么衔接，甚至通过拆解过的文风示例告诉子代理"这一章应该写成什么样"。

**细纲的详细程度直接决定写作质量和风格统一性。你花在细纲上的每一分钟，都会在后续写作中成倍回报。**（融合版的重要继承：这是 Reasonix 并发写作风格统一的杀手锏，Chinese Novelist 缺少这一层，导致并行时风格漂移。）

生成 `第1-5章节细纲.md` 文件，包含以下内容：

### 第一部分：批次全局信息

```markdown
# 【故事标题】— 第1-5章细纲

## 一、批次全局信息

### 全书文风基因（贯穿全书的文字DNA，每个子代理必须严格遵循）
- **叙述者口吻**：[2-3句话描述叙述者的身份、视角和语言风格]
- **内心独白处理**：[内心活动的呈现方式，如自由间接引语、碎片化、自嘲式]
- **对话节奏**：[对话整体风格，如保留沉默与停顿，重要回答前用动作填充]
- **感官描写偏好**：[感官描写的独特视角，绑定哪个角色的感知习惯]
- **章节收尾方式**：[反高潮/金句/悬念钩子，全书的收尾偏好]

### 文风锚点示例
[从已确认章节或采访共识中提取最能代表本书文风的段落，150-250字]
**关键特征提取**：句子平均长度 / 断句节奏 / 修辞风格 / 情绪传递方式 / 叙述者与角色的距离
**特征拆解（逐句对照）**：[拆成3-6个关键句逐句分析——切入点、信息量、修辞效果]

### 句法目标表（可测量锚点，J-Novel 核心新增）

> **光有定性锚点不够。** "读起来像不像人"是主观判断，Agent 可以用"我觉得挺像的"糊弄过去。数字不行。
> 所以锚点必须**提出数字，并当成每章的硬性目标**。

**做法**：找一部你认可的人类样本（同题材最佳），跑一遍探针取基线：

```bash
python scripts/check_human_rhythm.py --baseline <人类样本.txt>   # 打印该样本的全部基线值
python scripts/check_human_rhythm.py <章节文件>                  # 对比本章是否达标（退出码 1 = 不合格）
```

把结果写进细纲，每个子代理都要遵守：

```markdown
## 本卷句法目标（基线来源：《XXX》全书实测）
| 指标 | 基线 | 每章目标 |
|---|---|---|
| 句首代词占比 | X% | ≤15% |
| 句首引号占比 | X% | ≥15% |
| 平均句长 | X 字 | ≥18 字（弱） |
| 破折号/千字 | X | ≤1.5 |
| 身体部位/千字 | X | ≤1.0 |
| 情绪词/千字 | X | 0.25–0.5（区间，不是越低越好） |
| 明喻/千字 | X | 0.8–1.5（区间） |
| 对话占比 | X% | ≤40%（无下限，护栏） |
| 动作短语密度 | X | ≤0.4/千字 |
```

**Phase 3 质检时，把本章实测值与目标值并列写进 `04-质检档案.md`。** 数字对不上就是不合格，跟字数不够一样硬。
换题材时用 `--baseline` 重新校准，不要拿别的题材的基线硬套。

> 这一步是整套体系里最值钱的：它把"读起来像不像人"变成"这九个数字达没达标"。
> Agent 可以骗自己写得有人味，骗不了脚本。

### 批次人物状态总览
[每个核心人物在批次开始前的状态起点：情绪、关系、内心冲突阶段、本批次弧光方向]

### 批次伏笔总览
| 伏笔内容 | 当前状态 | 本批次操作 | 目标章节 |
|---------|---------|-----------|---------|
```

### 第二部分：逐章详细规划

```markdown
## 第 N 章：[章名]

### 基本信息
- **字数**：目标 X000 字
- **品质等级**：⭐ 品质锚点章 / ● 普通推进章
- **整体情感基调**：[一句话]
- **本章核心任务**：[圣经规划的主要事件展开为2-3句]

### 衔接锚点
- **承接自**：第X章结尾 —— [上一章结尾的画面、情绪、未解决的问题]
- **本章开头方式**：[第一个场景从哪个时刻、哪个视角切入]
- **开头参考**：[1-2句参考开篇]

### 人物状态追踪
[本章开始和结束时每个出场核心人物的状态，以及关键行为约束]

### 场景规划
#### 场景 1：[标签]
- **地点/时间** / **出场人物** / **核心事件** / **情感基调**
- **场景速写**：开头（1-2句参考）→ 中间展开（3-4句参考）→ 关键处理说明 → 收尾（1-2句参考）
- **场景情感曲线**：[情绪1] → [情绪2] → [情绪3] → [收尾情绪]

#### 场景 N：章末总钩子
- **结尾方式** / **留给读者的悬念** / **场景速写参考**

### 本章伏笔操作清单
- **埋设**：[伏笔] → 预计回收章节
- **回收**：[伏笔] ← 埋设章节
- **推进**：[伏笔] —— 通过什么方式提醒读者
```

### 细纲生成时机

- **规划确认时：** 串行模式生成全部章节任务卡；并行模式生成第一批完整细纲（第 1-5 章），请作者过目确认
- **写作推进中（并行）：** 每完成一个批次（如第 1-5 章），在开始下一批次前生成新的完整细纲（第 6-10 章）。以实际已写章节为准，细纲是活文档。

> **分级规则**：串行模式（serial）用章节任务卡即可（完整细纲可选）；并行模式（subagent-parallel）**必须**有完整细纲——子代理的风格统一全靠它。锚点章/高潮章无论模式，值得单章完整细纲。
>
> **悬念编排内建**：细纲/任务卡的每章钩子参考 `references/guides/hook-techniques.md` 的招式库（钩子十三式/引子七式/悬念强度五级/单章三段式/三弧并行）——钩子不要全靠临场发挥，规划时就把招式定好。

## 步骤 7：展示规划摘要并确认

向作者展示规划摘要（小说名称、总章数、目标字数、主要人物、写作计划摘要），然后使用 `AskUserQuestion` 确认两个决策：

**决策一：写作模式**

```
Question: 选择写作模式
Options:
- 逐章串行（主 Agent 自己逐章写，细纲精简，适合短中篇，文风最稳）
- 子Agent并行（分层保真并发：滚动批次+状态台账+锚点滚动+交叉衔接评审，适合中长篇；机制详见 guides/parallel-workflow.md）
- Agent Teams（多 Agent 协作模式，Agent 间可通讯，需平台支持 TeamCreate）
```

**决策二：写作节奏**

```
Question: 选择写作节奏
Options:
- 疯狂创作（规划确认后一口气写完所有章节再报告，中途不打断；推荐）
- 逐章确认（每章写完等你点头再写下一章，质量可控但需要你全程在场）
```

用户选择后：
- 将 `writingMode` 和 `writingTempo` 写入 `02-写作计划.json`
- 更新 `status` 为 `"in_progress"`
- 细纲确认（第一批）→ 进入 **Phase 3**：疯狂创作

### 步骤 7.5：我的保留意见（必须写，不是客套）

**展示规划摘要时，强制带这一节：**

```
💭 我的三个保留：
1. [一句话] —— 理由：[一句话]。（你可以不采纳，但你应该知道我为什么这么想）
2. …
3. …
```

**为什么强制**：首席内容官的价值一半在方案，一半在敢说不同意。最擅长藏起来的四类东西，写之前挨个扫一遍：

1. **被咽下的保留** —— "这个设定我觉得不成立，但他好像挺喜欢"
2. **未标注的不确定** —— "这块我其实没把握，但写成了确定的语气"
3. **出于礼貌的省略** —— "说了会显得我在挑刺"
4. **说出来会让这份稿子难堪的话** —— "按这个大纲，第 20 章大概率会塌"

命中任何一条，就写进这一节。**保留意见的门槛是作者的利益，不是作者的舒适。**

## 步骤 8：锚点章定调（进入 Phase 3 前的最后一道闸）

**这是融合版新增的关键机制，解决"疯狂创作写歪文风"的风险。**

正式批量写作前，先精写**第 1 章（品质锚点章）**并请作者确认：

1. **精写第 1 章**：按 Phase 3 的逐章创作流程完整执行（写前分析 → 撰写 → 五件套质检 → 修改），这是全书质量基准，值得花最多功夫
2. **请作者确认文风**（这是疯狂创作模式下唯一允许的中途确认点）：
   - 确认通过 → **从第 1 章确认版中截取最能代表文风的段落（150-250 字），作为「文风锚点示例」写入所有批次细纲的「文风锚点示例」栏**——后续所有章节（含子代理）都以它为语感参照
   - 需要调整 → 根据反馈修改第 1 章，直到作者点头
   - 作者说"风格可以，直接开写" → 跳过确认环节，锁定文风后进入批量创作
3. 更新 `02-写作计划.json`：第 1 章 `status` → `"completed"`，写入字数

> 为什么这么做：Reasonix 1.x 每章都确认（保证风格统一但慢），Chinese Novelist 疯狂创作（快但风格靠大纲硬撑）。锚点章机制取中间——**只确认一次定调，锁定文风锚点，之后全力开写**。这也是 Reasonix 细纲"文风锚点示例取自已确认章节"逻辑的显式化。

**锚点章完成后，进入 Phase 3 批量创作（从第 2 章开始）。**
