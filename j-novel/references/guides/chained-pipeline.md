# 链式流水线（治"并行写作的连贯性崩塌"）

> 这份指南回答一个问题：**并行写作，怎么才能既不牺牲速度、又不牺牲章节连贯性？**
>
> 适用：`writingMode: "subagent-parallel"` / `"agent-teams"`。如果你的并行写作出现过「章与章逻辑对不上 / 延续性差 / 风格不统一 / 第 3 章先于第 2 章写完」，根因就在这里。
>
> **成本视角**：本流水线是 `costMode: "low"` 的**默认组织形式**。但两者接缝上有两个洞——
> 主编读正文导致上下文累积、跨章缺陷发现太晚导致回头修。修法见
> `low-cost-mode.md` 第三节（主编零正文 / 三道闸门 / 边界冻结 / 缺陷路由 / 流量控制）。

---

## 一、根因：并行的单位选错了

现在的做法是「**一次派 5 个子代理，各写一章**」。看起来高效，但它撞上了三个硬事实：

### 事实 1：小说的章节是**链式依赖**的，不是独立任务

第 N+1 章的**开头**必须是第 N 章**结尾**的直接延续（人物在哪、什么情绪、知道什么、有没有受伤）。这不是"建议"，是章节能读通的前提。

**而并行派发时，第 N 章还没写完——第 N+1 章拿不到第 N 章的真实结尾。**

（检查一下你的流程文件：如果有"子代理必须读上一章真实结尾"这条，同时又"一次派 5 章"，那这条规则在物理上无法执行——派发那一刻，第 2-5 章的真实结尾还不存在。子代理只能拿细纲里的"规划结尾"充数，而规划≠实际，偏差就在这里产生。）

### 事实 2：**乱序完成是章节并行的数学必然，不是纪律问题**

5 章同时开写，完成时间必然不同（有的章简单、有的子代理快、有的触发重写）。所以"第 3 章写完了、第 2 章还在打磨"**不是谁不守纪律**——只要"章节"是并行单位，就必然乱序。加再多"请按顺序完成"的规则都没用。

### 事实 3：**契约不冻结，状态就会分叉**

第 2 章的子代理写到一半，觉得"让主角在这里受个伤更好"——它改了，但第 3 章的子代理还在按"主角没受伤"写。两章都对、拼起来就错。这是逻辑 BUG 最主要的来源。

---

## 二、解法：并行的单位从「章节」换成「工序」

一句话：**章节串行推进（保连贯），章内工序并行（保速度）。**

```
❌ 现在的做法（章节并行）：
   [子代理1: 第1章][子代理2: 第2章][子代理3: 第3章][子代理4: 第4章][子代理5: 第5章]
   → 各写各的，完成时间乱，第3章基于假的第2章结尾

✅ 链式流水线（工序并行）：
   初稿：第1章 → 第2章 → 第3章 → ...            ← 串行！笔手一章接一章
   打磨：         第1章 → 第2章 → 第3章 → ...    ← 与初稿并行（磨手跟着跑）
   缝合：               第1章 → 第2章 → ...      ← 主编串行缝合边界
```

**关键**：初稿由**同一个笔手**一章接一章写——它天然持有上一章的真实结尾。而"打磨（质检/去AI味/对话专项）"和"下一章初稿"可以同时进行，速度不丢。

**收益**：连贯性 BUG 归零（因为初稿链是串行的、真实的）；速度损失很小（打磨本来就不占写作瓶颈）。

## 三、三级策略（按质量/速度取舍）

| 档 | 名字 | 初稿 | 打磨 | 适用 |
|---|---|---|---|---|
| **A** | **链式串行** | 串行 | 串行（定稿才写下一章） | 锚点章、关键剧情章、卷末高潮；追求零瑕疵 |
| **B** | **链式流水**（默认推荐） | 串行 | **并行**（磨手跟着初稿跑） | 绝大多数章节；质量与速度平衡 |
| **C** | **章节并行** | 多章并行 | 多章并行 | **仅限"真独立章"**：番外、支线日常、明确与主线无承接关系的场景 |

> **判据**：一章能不能进 C 档，只问一句——**"这章的开头需要接上一章的结尾吗？"**
> 需要 → 只能 A 或 B；不需要（独立场景/时间地点人物都换了）→ 可以 C。

**默认全走 B。** 只有主编明确标注"独立章"的才允许 C。

## 四、接口契约（防"状态分叉"，B/C 档必做）

派发前，主编为**每一章**填一份契约，写进细纲。**这是链式流水线的"接口定义"**：

```markdown
### 第 N 章 · 接口契约（冻结）

【进入状态】= 第 N-1 章的退出状态，逐项写死：
  - 位置／时间：…
  - 情绪：…
  - 关系：…
  - 已知信息：…（读者和角色各知道什么）
  - 身体状态：…（有没有伤、伤在哪、影响什么）
  - 手上持有的东西：…

【退出状态】= 第 N+1 章的进入状态，同样逐项写死。

【承接要素】本章开头必须接住第 N-1 章的：______（哪句话/哪个画面/哪个悬念）
【交付钩子】本章结尾必须留下：______（供第 N+1 章开头接）

【冻结标志】契约一经派发即冻结。
```

**冻结规则（这条是治 BUG 的关键）**：

> 子代理若要偏离契约（改结局状态、改人物伤情、改谁知道了什么），**必须先申报 + 主编裁决 + 更新相邻章的契约**，不得自己改了往下写。

- 允许偏离，但必须走流程：改第 N 章退出状态 → 同步更新第 N+1 章进入状态 → 才继续
- 不允许偏离的：**进入状态**（这是上一章交付的，不能改）

**为什么有效**：把"两个子代理各自心照不宣的假设"变成了"白纸黑字的同一份契约"。状态分叉在源头被掐掉。

## 四·二、边界冻结（把契约从**状态层**延伸到**文本层**）

**契约管的是状态**（谁在哪、知道什么、有没有受伤）。但流水线还有一个**纯文本**的坑：

```
笔手写第 N+1 章时，拿到的是第 N 章的【草稿】结尾
        ↓
磨手随后打磨第 N 章，可能把结尾改写
   （"换落笔形态"这类指令**恰恰鼓励**改结尾——甲/乙/丙三型都要求特定落笔）
        ↓
第 N 章【定稿】的结尾 ≠ 第 N+1 章开头所承接的结尾
        ↓
两个都"对"，拼起来断 —— 而且没有任何脚本会报，因为两章各自都通顺
```

**这是流水线独有的病，串行模式不存在**（串行是先定稿再写下一章）。

**解法：章节边界是接口，接口冻结。**

| | 契约（状态层） | 交接卡（文本层） |
|---|---|---|
| 冻结什么 | 位置/情绪/关系/已知信息/身体状态 | **首段 + 末段** |
| 防的是 | 两个子代理各自心照不宣的假设 | **接力棒被掉包** |
| 谁有权改 | 主编（裁决后） | 主编（缝合权限） |
| 怎么验 | 台账三态标记 | **`make_handoff.py --check` 指纹比对** |

- **磨手打磨交接段之外的一切**；**交接段只有主编能动**——因为它是接口；
- 确需动交接段 → 主编**必须重跑缝合**（`check_continuity.py`）→ 必要时让笔手补一句桥接；
- **中间段落改了不影响**（指纹不变、卡不过期、不必重做）——这条让规则不至于太烦。

**指纹让"冻结"从纪律变成可检测**：改第 3 章末段，脚本会**同时报出第 3 章和第 4 章**
（第 4 章的卡里存着它当时承接的上章末段）——正好指向那对被拆散的接力棒。

## 五、三个角色的分工

### 笔手（写作子代理，串行）
- **一章接一章连续写初稿**，不等待打磨完成
- 每章开工前拿到：契约 + **上一章的真实结尾**（**由交接卡给出，不是细纲、也不用读整章正文**）
- 写完立刻交稿，主编（或脚本）截取本章真实结尾 → 传给下一章
- **最多领先磨手 3 章**（见第十一节：这个数和窗闸窗口必须相等）

### 磨手（质检/打磨子代理，可与笔手并行）
- 跟着笔手的产出走：打磨已经交稿的章节
- 做：`check_human_rhythm` / `check_aistyle` / 字数 / 硬性句式 / 对话专项 / 情绪专项 / 去 AI 味
- **只打磨，不改剧情走向**（剧情归契约管）
- **交接段（首段/末段）不许动**——那是接口，归主编（见第四·二节）。
  确实需要改，就申报主编，由主编改并重跑缝合

### 主编（串行，质量负责人）
- **定契约**（每章进入/退出状态）——这是主编最核心的工作，不能外包。
  **按批次一次投影完**（从细纲派生，1 次调用），不要一章一次地想
- **裁交接卡**：`python scripts/make_handoff.py <项目> --all --write`
  → **主编此后只读卡、不读正文**（见下）
- **缝合边界**：每章定稿前，对照交接卡里的「上章末段 / 本章首段」检查并补桥接句
- 维护台账、滚动锚点、**跑窗闸**（每章）与**批闸**（每批）
- ⚠️ **批闸不要自己跑**：批闸要"全批视野"，主编自己跑就得把全批正文装进上下文。
  交给**批闸子代理**（只给台账 + 各脚本退出码 + 抽检 2 章），主编只看结论

> ### 主编必须"零正文"
>
> 本流水线的全部成本收益来自"子代理上下文彼此隔离、不累积"，
> 而**主编是活得最久的角色**。它每章读两遍正文（一遍取结尾、一遍缝合），
> 读过的每一章都留在上下文里，跟着它**之后每一次**调用被重发
> → **子代理省下的钱被主编一个人花回去**。
>
> | | 读正文（旧） | 读交接卡（新） |
> |---|---|---|
> | 每章进入主编上下文的量 | 两整章 ≈ **6000 字** | 一张卡 ≈ **800 字** |
> | 是否随章数累积 | **是**（且乘以剩余章数） | 否（卡是文件，可随时重读、滚掉） |
>
> **这不是牺牲质量换省钱**：缝合需要的信息**就是边界段**，读全文反而把它淹在 6000 字里。
> 裁卡是**信息提纯**。

## 六、边界缝合 SOP（主编每章必做）

笔手写完、磨手打磨完，主编做最后一道 **30 秒缝合**：

0. **先跑 `python scripts/make_handoff.py <项目> --check --window 3`**
   —— 有"卡已过期"就先重跑缝合，别在过期信息上做判断
1. **读交接卡里的「上章真实结尾」**（不是摘要、也不是整章正文）——对照本章首段，
   问"读者从上一章翻过来，能无缝接上吗？"
2. **读交接卡里的「本章末段」**——对照下一章的契约进入状态，
   问"下一章要的开局条件，这一章给到了吗？"
3. 缺一句桥接 → 补一句（**只补不删，不重写剧情**）
4. 补过 → 重新生成该章交接卡（`--chapter N --write`），指纹随之更新

> 缝合的产出物是可验证的：`check_continuity.py` 的退出码 +
> `make_handoff.py --check` 的指纹。**"我缝过了"不算，脚本绿了才算。**

## 七、乱序问题的正面回答

用了链式流水线后，你可能仍会看到"第 3 章初稿写完了，第 2 章还在打磨"。**这是正常的，而且无害**——因为：

- 第 3 章的**初稿**是基于第 2 章的**真实结尾**写的（笔手串行）→ **逻辑和延续性有保证**
- 只是"打磨完成时间"有先后 → 只影响交付节奏，不影响质量

**真正会崩的是"第 3 章基于假的第 2 章结尾写"**——那是章节并行才有的病，链式流水线从机制上消除了它。

**交付时统一按序号整理即可**（打磨是先完成还是后完成，不影响最终产物）。

## 八、什么时候可以放宽到章节并行（C 档）

同时满足三条才可以：

1. 章节**不承接**上一章结尾（时间/地点/人物至少换两项）
2. 章节的**退出状态不被任何后续章依赖**（或者它本来就是支线收尾）
3. 主编在细纲里**显式标注** `独立章：可并行`

否则一律 A/B 档。

## 九、和现有机制的对接

| 现有机制 | 在链式流水线里的位置 |
|---|---|
| 细纲（场景速写/人物状态追踪） | **契约的载体**——每章契约写进细纲 |
| 状态台账 | 笔手写前读进入状态、写后回写退出状态；主编核对 |
| 锚点滚动 | 照旧：每章/每批从最近定稿抽锚点 |
| 交叉互检 | 照旧，但注意**互检对象是已定稿章节**，不是还在写的 |
| 批次验收闸门 | 照旧，且**链式流水下天然满足**（笔手串行，不存在乱序）。**但要加一条**：`make_handoff.py --check`（边界未被动过）——见第四·二节 |
| `check_continuity.py` | 缝合后的验证工具（退出码 0 = 边界接住了） |
| **交接卡**（`make_handoff.py`） | **主编的输入端**：上章真实结尾 / 本章首段 / 本章末段 + 指纹。**主编读卡不读正文** |
| **窗闸**（`--window 3 --brief`） | 每章初稿后跑：重复 / 开场·章末同质 / 声音漂移 / 交接卡过期。**报告定长** |
| **剧情脚手架 `07-剧情脚手架.md`** | 作者的剧情意图；有则进笔手任务包（**作者画面**一栏），与契约不冲突——契约管状态，脚手架管方向 |

## 十、缺陷路由：只向前修 vs 停线回改

流水线会不断报出问题。**不是每个都值得回头改**——判据一句话：

> ### **"这个缺陷会不会污染下游？"**

| 类型 | 例子 | 处理 | 为什么 |
|---|---|---|---|
| **局部** | 本章某段 AI 味重、比喻超标 | **磨手改**（并行，不入主编上下文） | 不影响下游，改完即完 |
| **系统·可向前** | 开场同质、章末公式化、声音漂移、设定新词没登记 | **不回改已定稿章**；写进「本批已知病灶」→ 注入笔手任务包 → 后续章不再犯 | 回改要重做缝合/锚点/台账；**且回改本身成为新的不一致源** |
| **硬伤·必须停线** | 契约违反、连续性断、设定矛盾、人物状态错 | **暂停流水线 → 回改 → 恢复** | 下游已基于它，不回改则错误扩散 |

**"只向前修"质量上也对**（不只是省）：一个已缝合、已抽过锚点的章节，再回头动它
会让缝合和锚点**同时失效**。批量写作里，"忍一章、后面不再犯"经常比"回头全改"结果更好。

**为什么它在本流水线里是安全的**：窗闸（窗口 3）＋ 领先上限（3）保证被污染的章
**还在磨手队列里、尚未定稿** → 在队列里改就行，**根本不需要"回头"**。

---

## 十一、流量控制：笔手最多领先磨手 **3 章**

- **上限 = 3 章**。超限时笔手暂停，主编清空磨手队列（或自己上手改最快的那章）。
- **为什么正好等于窗闸窗口**：

  > **窗闸窗口 = 领先上限** ⟺ **发现缺陷时，被污染的章还没定稿**
  > ⟺ **"只向前修"是安全的**（在队列里改，不必回头）

  窗口比领先小 → 发现太晚，要回头；窗口比领先大 → 白查已经定稿的章。
  **它们不是两个可以各调各的旋钮，是同一个数的两个约束。**
- **顺带解掉了一个取舍**：风险窗口封顶在 3 章、**与批次大小无关**
  → 批次可以放心取大值（8–10），把每批的固定开销摊薄。**效率和质量的取舍被解掉了。**

## 十二、一句话记住

> **并行的应该是"工序"，不是"章节"。**
> 初稿必须串行（因为故事是顺序的），打磨可以并行（因为它不产生剧情）。
> 想要快，就压榨工序流水线的重叠度；不要拿章节去并行——那是拿连贯性换速度，而且必然亏。
>
> **再加一句（质量与成本的共同约束）**：
> **闸门必须放在"缺陷被定稿之前"。** 晚一步，修复就从"在队列里改"变成"回头改"，
> 成本超线性、还会破坏已经做好的缝合与锚点。
