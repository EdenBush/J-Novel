# 低费用模式（Low-Cost Mode）

> 触发：`costMode: "low"`。
>
> **定位：批量推进档。** 目标是四个，**缺一不可**：
> ① **快速批量写文** ② **高效质检／修改／润色（人味不降）** ③ 快速成稿 ④ 低 token。
>
> **⚠️ 先读 `token-efficiency.md`（铁律九）。** 成本的大头是"调用次数 × 上下文"，
> 那是铁律九管的，**standard 和 low 两种模式都必须遵守**。
>
> **本模式的默认组织形式是链式流水线**（第二节），而流水线与本模式之间有**两个接缝**
> 必须补（第三节）——不补就是"又快又低、但质量漏水"。

---

## 一、成本归因：low 模式到底该省什么

**实测基线**（日志真实 usage，非估算）：6 章 / 1.24 万汉字 = **45.4M tokens**，
其中 **97.8% 是 cacheRead（上下文重发）**，output 只占 0.7%，**放大 135 倍**。

看清这句话：「**每一轮都要把整个上下文重发一遍**」。
所以成本 ≈ **上下文里装了多少 × 还要跑多少轮**。

### 四把钥匙（按效果排序）

| # | 钥匙 | 省的是 | 老设计 |
|---|---|---|---|
| **①** | **子代理隔离（链式流水线）** | **cacheRead 大头**——每个子代理上下文**独立、不累积** | ❌ 老设计"默认串行"，**方向是反的**（见第二节） |
| **②** | **减少轮次**（一条命令跑完脚本／一次批量改／一次成稿） | 每一轮的上下文重发 | ⚠️ 部分有 |
| **③** | **上下文里少放东西**（只读速查卡 + 内联，不读 guide 全文） | 每轮的重发量 | ✓ 有 |
| **④** | **会话分段**（每 2–3 章换会话，靠文件交接） | 上下文线性累积 | ⚠️ 归给铁律九 |

> **老设计的问题**：它的六条规则里五条在"少读文件／少判断"，
> 而**少读文件只省 12%**（它自己写的）。真正的大头在 ① 和 ②。
> **更严重的是它砍掉的东西 —— 见第四节。**

---

## 二、批量：low 模式默认走**链式流水线 + 批次**（推翻旧设计）

> **⚠️ 旧设计写的是"低费用模式默认串行，因为并行会重复读上下文"——这个判断是错的。**
>
> - **串行**：主 Agent 连写 N 章，上下文**线性累积** → 写第 N 章时要重发前 N−1 章的一切
>   → 97.8% 的 cacheRead 正是这么来的；
> - **并行（链式流水线）**：每个子代理上下文 **只有任务包**（速查卡 + 细纲 + 上章尾 + 设定包），
>   **不带历史、互不污染** → cacheRead 反而小得多。
>
> **结论：批量场景下，链式流水线比串行更省 token，而且快得多。**

**low 模式的默认组织形式**（`guides/chained-pipeline.md`）：

```
笔手：串行写初稿（章序不可并行——每章必须拿到上一章真实结尾）
磨手：并行打磨已交稿的章节（质检 / 润色 / 对话情绪专项）
主编：裁世界设定包 → 缝合章节边界 → 跑批次闸门 → 文件交接换会话
```

- **批次 = 5–10 章**（`guides/parallel-workflow.md`）。**low 模式取大值（8–10）**：
  批次越小，每批那份固定开销（重读圣经/大纲/台账、换会话后的重新定位）摊得越薄；
  而"批越大风险越大"这个顾虑**已被第三节的流量控制消掉**（风险窗口由领先上限封顶，
  不随批次变大）。
- 每批结束：跑 `check_batch_gate.py` → 换会话（文件交接，不靠上下文记忆）
- **每个子代理的任务包**：速查卡 + 本批细纲 + 上一章真实结尾 + **世界设定包** + **作者画面（若有）**，
  全部**内联**，**不给 guide 路径**（给了它也不会去读，读了还要每轮重发）

**为什么这条同时实现"快"和"低"**：并行的**总耗时**下来了，而每个子代理的**独立上下文**
让 cacheRead 不再随章数累积——**这是 low 模式最大的一笔省**。

## 三、低消耗 × 链式流水线：质量与效率的接缝（本模式的核心）

> 第二节只解决了"快"和"低"。**质量怎么办？** 链式流水线把质量押在三个机制上：
> 主编缝合边界、契约冻结状态、磨手逐章打磨。而这三个机制与本模式的成本目标**有冲突**——
> 不处理，就会变成"跑得飞快，但错误以同样的速度扩散"。

### 3.0 一条判据，决定所有闸门放在哪

> ### **质量闸门的位置必须满足：发现缺陷的时点 ≤ 该缺陷被"定稿"的时点。**

**为什么**：一旦发现晚于定稿，修复就要**回头**——回头要重做缝合、重抽文风锚点、
重写台账。成本从线性变超线性；更糟的是**回头改本身会成为新的不一致源**
（缝合已经做过、锚点已经抽过，改动会让它们失效）。

由此得到一条反直觉的推论——**质检不是"全部提前"，而是"只把跨章项提前"**：

| 缺陷类型 | 晚发现的代价 | 闸门频率 |
|---|---|---|
| **单章缺陷**（某段 AI 味重、比喻超标） | 还是只改一章 → **不敏感** | 批末查也行 |
| **跨章缺陷**（开场/章末同质、声音漂移、设定分裂、边界断裂） | 要改 N 章 → **极度敏感** | **必须每章查** |

按"发现得晚有多贵"排序放闸门，而不是按"这条规则重不重要"排序。

### 3.1 三道闸门

| 闸 | 时点 | 查什么 | 成本 |
|---|---|---|---|
| **章闸** | 每章初稿后 | **单章机械项**：字数 / 句法节律 / 词汇指纹 | **0**（脚本） |
| **窗闸** | **每章初稿后**，滚动窗口 3 章 | **跨章项**：章内重复 / 开场同质 / 章末同质 / **声音漂移** / 边界连续性 / **交接卡过期** | **0**（脚本） |
| **批闸** | 批次末 | **判断项**（1 次调用）+ 全批视野 + 设定激活率 | **1 次调用 / 批** |

```bash
# 窗闸：每章初稿后跑，一条命令，输出**定长**
python scripts/check_repetition.py --all <项目> --window 3 --brief   # 重复 + 开场/章末同质
python scripts/check_aistyle.py --all <项目> --drift --brief \
       --window 3 --base <本批首章号>                                # 声音漂移（见 3.1.1）
python scripts/make_handoff.py <项目> --check --window 3             # 交接卡过期（见 3.3）
python scripts/check_continuity.py <项目>                            # 边界衔接
python scripts/check_chapter_wordcount.py --all <项目>               # 字数
```

**三个"必须"**：

1. **窗闸必须每章跑，不能批末跑**——理由就是 3.0 那条判据。
   实测事故形态：一个 10 章批次里，笔手从第 3 章起连续用同一种开场，
   到批末闸门才发现 → **7 章要回改**。窗闸会在第 3 章就报出来。
2. **窗闸报告必须定长**（`--window N --brief`）。否则明细随章数线性变长，
   每章重读一遍 = **把省下的上下文又花回去**——省钱的机制变成花钱的机制。
3. **批闸交给子代理跑，不是主编**。否则主编要把整批正文装进上下文（见 3.2）。

#### 3.1.1 声音漂移：把"风格一致性"从判断层降到机械层

风格一致性以前只能靠 LLM 读全章比风格——那是判断层的价格（贵），而且通常拖到批末。
但 `check_aistyle.py` **本来就在算这些指纹**（段落节律 CV / 对话占比 / 转折词 /
直接情绪词 / 明喻 / 万能模板），跨章比一下是 **0 token** 的事。`--drift` 做两件事：

- **抓突变**：本章 vs 前 3 章中位数
- **抓渐变**：本章 vs **批首章**（固定基线）——渐变对滚动基线**天然免疫**
  （每章只偏 15%，永远够不到阈值），只能靠固定基线。这就是 `--base <批首章号>` 的作用：
  **每批重新定基**，否则会拿全书第 1 章当基线，把"声音随剧情自然演化"误报成漂移。

判据分两级（闸门太吵就没人看了）：**≥2×** 判失败、**≥1×** 提示。
另有一条：**段落节律 CV 跌破健康下限 0.6** 直接可疑——段长从长短交替变成段段均匀，
是 AI 化最典型的指纹，而倍数判据看不见它（0.76→0.17 只是"降了 78%"）。

**改过漂移判据就跑一次自测**：`python scripts/check_aistyle.py --selftest`
（纯内存、不碰磁盘，用合成指纹复验三个已踩过的坑：突变要抓到 / **基线之前的章不许判** /
基线为 0 时"从无到有地爆发"要抓到。真实项目实测抓出过 `--base N` 的误判——那时脚本会去
判基线**之前**的章，而它们的"前 3 章中位数"是空集，于是报出纯噪声的"漂移"。）

### 3.2 主编零正文（最大的一笔省，而且**不降质量**）

**冲突在哪**：链式流水线把质量押在主编身上，而主编的三件事——定契约、转交
"上一章真实结尾"、缝合边界——传统做法**都要读正文**。于是：

> 本模式的全部收益来自"子代理上下文彼此隔离、不累积"，
> 而**主编是流水线里活得最久的角色**。它每章读两遍正文（一遍取结尾、一遍缝合），
> 读过的每一章都留在它的上下文里，跟着它**之后每一次**调用被重发。
> → **子代理那边省下的钱，被主编一个人花回去。**

（`parallel-workflow.md` 原来甚至写着主编"必持**全部真实章节**"，理由是"100 万 token
窗口足够"——那是**窗口够不够**的论证，不是**成本**的论证。已修正。）

**解法：主编零正文。**

```bash
python scripts/make_handoff.py <项目> --all --write    # 从正文裁出交接卡（0 token）
```

交接卡（`chapters/_meta/handoff-NN.md`，≤800 字）只含主编真正要的东西：
上章真实结尾原文 + 本章首段 + 本章末段 + 三者指纹。主编**读卡不读正文**。

| | 读正文（旧） | 读交接卡（新） |
|---|---|---|
| 每章进入主编上下文的量 | 两整章 ≈ **6000 字** | 一张卡 ≈ **800 字** |
| 是否随章数累积 | **是**（且乘以剩余章数） | 否（卡是文件，随时可重读、滚掉） |
| 缝合质量 | 看全文 | **看的就是边界段**——缝合本来只需要这两段 |

**这不是"为了省钱牺牲质量"，恰恰相反**：缝合需要的信息**就是边界段**，
读全文反而把那两段淹在 6000 字里。裁卡是**信息提纯**。

**批闸同理**：批闸要"全批视野"，让主编跑就等于把全批正文装进它的上下文。
交给**批闸子代理**（只给台账 + 各脚本退出码 + 抽检的 2 章），主编只看结论。

### 3.3 边界冻结（治流水线特有的"接力棒掉包"）

**这是流水线独有的坑，串行模式不存在**：

```
笔手写第 N+1 章时，拿到的是第 N 章的【草稿】结尾
        ↓
磨手随后打磨第 N 章，可能把结尾改写
   （"换落笔形态"这类指令**恰恰鼓励**改结尾——四型里甲/乙/丙都要求特定落笔）
        ↓
第 N 章【定稿】的结尾 ≠ 第 N+1 章开头所承接的结尾
        ↓
两个都"对"，拼起来断。而且**没有任何脚本会报**——因为两章各自都通顺
```

**解法：章节边界是接口，接口冻结。** 这是把链式流水线已有的「**契约冻结**」
从**状态层**扩展到**文本层**——同一条原则的两半：

| | 契约（已有） | 交接卡（本次） |
|---|---|---|
| 冻结什么 | **状态**：位置/情绪/关系/已知信息/身体状态 | **文本**：首段 + 末段 |
| 防的是 | 两个子代理各自心照不宣的假设 | 接力棒被掉包 |
| 谁有权改 | 主编（裁决后） | 主编（缝合权限） |
| 怎么验 | 台账三态标记 | **`make_handoff.py --check` 指纹比对** |

**规则**：

- 磨手打磨**正文**（交接段之外的任意段落）；
- **交接段（首段 + 末段）只有主编能改**——因为它是接口；
- 确需动交接段 → 主编**必须重跑缝合**（`check_continuity.py`）→ 必要时让笔手补一句桥接；
- 中间段落改了**不影响**（指纹不变，卡不过期，不必重做）——这条让规则不至于太烦。

**指纹让"冻结"从纪律变成可检测**：实测改第 3 章末段，脚本**同时报出第 3 章和第 4 章**
（第 4 章的卡里存着它当时承接的上章末段）——正好指向那对被拆散的接力棒。

### 3.4 缺陷路由：只向前修 vs 停线回改

窗闸会不断报出问题。**不是每个都值得回头改**——判据一句话：

> ### **"这个缺陷会不会污染下游？"**

| 类型 | 例子 | 处理 | 为什么 |
|---|---|---|---|
| **局部** | 本章某段 AI 味重、比喻超标 | **磨手改**（并行，不入主编上下文） | 不影响下游，改完即完 |
| **系统·可向前** | 开场同质、章末公式化、声音漂移、设定新词没登记 | **不回改已定稿章**；写进「本批已知病灶」→ 注入笔手任务包 → 后续章不再犯 | 回改要重做缝合/锚点/台账；且回改本身引入新的不一致 |
| **硬伤·必须停线** | 契约违反、连续性断、设定矛盾、人物状态错 | **暂停流水线 → 回改 → 恢复** | 下游已基于它，不回改则错误扩散 |

**为什么"只向前修"质量上也对**（不只是省）：一个已经缝合过、抽过锚点的章节，
再回头动它会**让缝合和锚点失效**——修复动作本身成为新的不一致源。
在批量写作里，"忍一章、后面不再犯"经常比"回头全改"结果更好。

**为什么它在本模式里安全**：窗闸（窗口 3）＋ 领先上限（3，见 3.5）保证被污染的章
**还在磨手队列里、尚未定稿** → 在队列里改就行，**不需要"回头"**。两个数字必须相等，
原因见下。

### 3.5 流量控制：笔手最多领先磨手 **3 章**（与窗闸窗口同值）

- **上限 = 3 章**。超限时笔手暂停，主编清空磨手队列（或自己上手改最快的那章）。
- **为什么正好等于窗闸窗口**：这两个数字必须**对齐**，因为

  > **窗闸窗口 = 领先上限** ⟺ **发现缺陷时，被污染的章还没定稿**
  > ⟺ **"只向前修"是安全的**（在队列里改，不必回头）

  窗口比领先小 → 发现太晚，要回头；窗口比领先大 → 白查已经定稿的章。
  所以它们不是两个可以各调各的旋钮，是**同一个数的两个约束**。
- **它带来的额外好处**：风险窗口封顶在 3 章，**与批次大小无关**。
  所以批次可以放心取大值（8–10），把每批的固定开销摊薄——**效率和质量的取舍被解掉了**。

### 3.6 批首验章：low 模式的"锚点章"

standard 模式用**锚点章**（第 1 章精写、作者确认、锁定文风）定调。
**low 模式不是不需要锚点，而是锚点降到批次粒度**：

- 批次第 1 章写完后，**立刻**走完章闸 + 窗闸 + **完整判断项（含四项独立测试）**；
- 通过 → 笔手全速推进本批；不通过 → 只改这一章，改完再验（≤2 轮）；
- 这一章的**定稿**即成为本批的「批内成文锚点」，进后续章的任务包
  （它也正好是 `--drift --base` 的固定基线）。

**成本**：判断项本来每章就要做一次（第四节），所以**这不是额外开销，是位置调整**——
把它**提前到"批首"并当作闸门**，而不是随磨手进度平铺。
**收益**：系统缺陷在扩散前被挡住。第 1 章发现 vs 第 10 章发现，差 9 章的重写。

## 四、质检：机械项**全跑**（免费），判断项**合并成一次**（不砍）

> **⚠️ 旧设计写的是"只跑 3 个脚本，砍掉自评/杠精/评分/子技能"——这是把免费的扔了、把贵的砍了。**
>
> - **机械项是脚本**：零 reasoning、退出码是硬判据。**砍它等于白扔质量**；
> - **判断项是 LLM 调用**：贵在"重复问好几遍"，**但不该不问**——人味就住在这一层。

### 4.1 机械项：一条命令跑完全部脚本（**全保留，一个不砍**）

```bash
python scripts/check_chapter_wordcount.py --all <项目目录>   # 字数（下限读项目配置）
python scripts/check_human_rhythm.py 第X章.md                # 句法节律（exit 1=不合格）
python scripts/check_aistyle.py 第X章.md                     # 词汇指纹 + 硬性句式 + 半角引号
python scripts/check_repetition.py --all <项目目录>          # 章内重复 + 跨章开场/章末同质
python scripts/check_continuity.py <项目目录>                # 章节边界衔接
python scripts/check_worldbuilding.py <项目目录>             # 设定激活率 / 未登记新词
python scripts/make_handoff.py <项目目录> --check            # 交接卡齐备 + 边界未被动过
```

**七个脚本一条命令串起来跑，一次读完整报告。**
（`--all` 的几个在**批闸**跑全量；带 `--window 3 --brief` 的形态在**窗闸**每章跑。）

> **为什么全跑**：它们**不花 reasoning token**，只花一次工具调用的往返。
> 旧设计省掉 `check_repetition` 后，**跨章开场/章末同质这类结构级问题就再也发现不了**——
> 而它们恰恰是"批量写文"最容易犯的毛病（连写几章一个模子）。

### 4.2 判断项：**合并成一次调用**（项目一个不减）

老设计里它是 4–5 次独立调用：AI味自评 → 人味配额 → 杠精 → 评分 → 子技能。
**合并成一次**，一个 prompt 里问完：

```
【一次性判断】（1 次调用，问完所有问题）
  ① AI 味自评 11 项（逐项判"人侧/AI侧"）
  ② 人味配额数数（毛边 / 废话 / 比喻 / 金句 / 意象 / 情感差异）
  ③ 四项独立测试（同构测试 / 删除测试 / 作者在场测试 / 用力过猛测试）
  ④ 输出：不合格项 + **一句可执行的改法**（不是长篇报告）
```

**收益**：调用次数 4–5 → **1**；**检查项目一个不少**。
（这跟铁律九的"一次批量改写"是同一个道理——**合并同类调用，不是取消调用**。）

**独立质检子代理（四项测试）在 low 模式的处理 —— ⚠️ 它是上面那条"合并"的例外**

> **2026-09-23 修正**：这里原来写的是"**并入上面那一次判断**，或与磨手的润色合并"。
> 那是把「合并同类调用」这条正确原则**误用在了"独立性"上**，而且与
> `review-agent.md` 第六节**直接矛盾**——那一节写明独立质检必须
> 「**另起一个子代理，只给纯正文**」。
>
> 合并意味着由**同一个 agent** 做，而那个 agent：
> ① **知道全部规则**（它按规则打磨的）→ 违反"只给纯正文、不给它看规则"；
> ② **刚打磨过这份稿子** → 违反独立性（人会为自己的改动辩护）；
> ③ 而且它**本身就是被评对象**。
>
> **四项测试的全部价值就在"评委不知道应该长什么样"。合并 = 取消它。**

**正确做法：独立但极轻。** 仍然**另起一个子代理**，但把它的任务包压到最小——
**只给本章纯正文 + 四个问题**，不给细纲、不给规则包、不给脚本路径。

**它其实是全流程最便宜的角色**：输入只有一章正文，输出只有几行定位（且"没有"也是有效答案）。
**砍它省不下钱，却砍掉了整条链上唯一"不看规则的眼睛"。**
换句话说——**要省，就省它的输入，不要省它的独立性。**

### 4.3 改：一次批量改写

报告里的全部超标项**一次改完**，复跑一次确认。
**禁止"改一处 → 跑一次脚本"**（实测占 60% 的调用、30 次脚本/章）。

## 五、人味不降清单（low 模式**必须保留**）

用户的原话是"高效质检修改润色（**人味**）"——**low 降的是重复劳动，不是人味**。

| 必留项 | 为什么不能省 | 成本 |
|---|---|---|
| **写前声音预置三行** | "人味"的根；三个坐标定不下来，整章都会飘 | ≈0（写在细纲里） |
| **人类范本片段**（内联 1–2 段） | 给**原文**不给路径——模型放什么就检索什么 | 200–400 字 |
| **加法层 3–5 招**（按细纲挑，不逐条打卡） | 只删 AI 味会写成白开水，**加法决定上限** | 读速查卡即可 |
| **世界设定包**（内联） | 缺了它子代理会各自发明一套世界 → 两章之后分裂 | 500–800 字 |
| **作者画面**（若有脚手架条目） | 流水线上最保人味的素材——**作者自己的眼睛** | 50 字 |
| **四项测试**（★ **独立但极轻**，**不并入**自评那一次） | 脚本测频率，**测不出同构/空转/有没有人**；而它的价值在**独立性**——并入"知道规则、刚打磨过这份稿子"的那个 agent 等于取消它 | 另起子代理，但**只给纯正文 + 4 个问题**（全流程最便宜的角色） |
| **跨章同质检测** | 批量写文独有的结构级同构，单章看不出来 | **0（脚本）** |
| **声音漂移检测** | 批量写文独有的"声音散了"，单章看不出来 | **0（脚本）** |
| **批首验章** | 系统缺陷必须在扩散前挡住 | 判断项位置调整，非新增 |
| **交接卡** | 主编不读正文的代价是零质量损失——卡里就是缝合要的全部信息 | **0（脚本）** |

## 六、其余硬规则

### 6.1 必读文件：只读一张卡

- **standard**：动笔前读 writing-mindset + human-quota + concrete-voice + human-rhythm 全文，质检读 5–6 本。
- **low**：动笔前**只读 `guides/quick-reference-card.md`**（一页，约 1.5k tokens）。
  脚本报某项超了，**才翻 `rewrite-playbook.md` 对应那一节**（只读那一节，不读全文）。

### 6.2 文件编辑：Write 整文件覆盖

- 大纲／细纲／章节用 **Write 一次写完**。
- **禁止**用 Edit 反复试 `old_str`——实测这是巨大的隐性 token 黑洞
  （匹配失败 → 重读文件 → 重试，每一轮都在重发上下文）。
- 只有"改已写章节里的 1 句话"才用 Edit（且一次命中）。
- **例外（流水线）**：交接段的改动只有主编做（见 3.3），且改完必须 `make_handoff.py
  --write` 重生成卡 + 重跑缝合。

### 6.3 过程叙述压缩

- 不写"我来分析一下""现在我开始规划"这类过程叙述。
- 质检报告**一行化**：`第X章：字数3125✓ 节律0 词汇0 重复0 同质0 漂移0 → 合格`。
- 给用户的汇报只报"写到第几章 + 关键指标 + 有没有问题"。

### 6.4 台账／圣经：合并批处理 —— ★ **这是对铁律六的显式例外**

> **⚠️ 2026-09-23 修正**：本条原来只说"改为每批一次"，**没有声明它是「例外」**。
> 而 `execution-contract.md` 的**铁律六**写的是「**【必须】** seam 重读：
> **每章**边界重读 `05-创作台账.md` 五段后再动笔」。两条**硬碰硬**，后果有三个：
>
> 1. 读铁律六的 Agent → 每章重读（贵，但"合规"）；
> 2. 读本文件的 Agent → 每批重读（省，但按铁律六算"违规"）；
> 3. **Phase 4 会抽查台账"最近重读章号"是否推进**（`EC:150`）——
>    而 low 模式下它**每批才推进一次**，存在**被判"缺痕"的风险**（假报警）。

**所以本条的性质是：low 模式的「第四条例外」**（前三条见 Phase 3 铁律的例外清单），
并且**必须同步 Phase 4 的检查口径**——否则两个阶段会互相判违规：

```bash
# Phase 4 查痕时，按 costMode 分档（不要用同一把尺子量两种模式）
标准模式（standard）：05-创作台账.md 的「最近重读章号」应推进到**本批末章**且每章都有 seam 记录
低费用模式（low）：  同上推进到**本批末章**即可；**允许章级 seam 记录缺省**（它按批做）
                     —— 判定依据是"本批末章对齐"，不是"每章一行"
```

**规则本身不变**（仍是每批一次 seam 重读 + 台账回写）——变的是**它现在有了名分**：
一条"必须"级铁律被另一份文件豁免时，**必须显式写成例外**，否则两处规则会在长跑中互相判违规。

- 不每章重读 `05-创作台账.md` 五段全文。改为**每批（5–10 章）一次** seam 重读 + 台账回写。
- 圣经／大纲／人物档案**只在批次边界**看，不在每章质检时反复翻。
- **设定回流**（新词登记）随批次一起做，不每章一次。
- **批末必须补齐**：`05-创作台账.md` 推进"最近重读章号"到本批末章 + 三态标记回写 +
  **锚点滚动**（见 3.6/批末动作）——批末是这条例外的**兑现点**。

### 6.5 ★ 本书里的四个「3」——同形异义，别串用

全库检索发现**同一个数字 `3` 承担了四种完全不同的语义**。这不是数字漂移，
而是**同形异义**：一个 Agent 读到"3 章"必须先猜是哪一种，而其中**两个确实是同一个数、
另外两个纯属巧合**——后者最坏，因为会让人以为它们也有关联。

| 写法（建议这样说） | 指什么 | 出处 | 与谁同源 |
|---|---|---|---|
| **窗闸窗口（window=3）** | 跨章检测只看最近 3 章 | `low-cost-mode.md` 3.1 | **★ 与下一行是同一个数** |
| **领先上限（leadCap=3）** | 笔手最多领先磨手 3 章 | 3.5 | **★ 与上一行必须相等** |
| **连续三章同型** | 开场/章末连续 3 章同类别才报警 | `check_repetition.py` | 巧合（与上面无关） |
| **会话卫生：每 N 章换会话** | 见下方修正 | `token-efficiency.md` | 巧合 |

> **前两行为什么必须相等**：见 3.5 —— 「窗口 = 领先上限」⟺「发现缺陷时被污染的章还没定稿」
> ⟺「只向前修是安全的」。它们**不是两个可各调各的旋钮，是同一个数的两个约束**。
> **后两行的 3 只是恰好也是 3**——写的时候请用上表的完整说法（"连续三章同型"、"每 N 章换会话"），
> **不要只写"3 章"**。

**会话卫生的修正（另一个口径冲突）**：`token-efficiency.md` 纪律三写"每 **2–3 章**换一个新会话"，
而本文件按**批**（5–10 章）换。两者都没错——**因为会话策略本来就该随组织形式变**：

| 组织形式 | 谁在累积上下文 | 换会话的节奏 |
|---|---|---|
| **串行**（主编自写） | **主 Agent 自己**，每章线性累积 | **每 2–3 章**（纪律三的原始场景） |
| **链式流水线**（low 默认） | 子代理各自独立；**主编零正文**（每章只增一张交接卡） | **每批一次**（本文件 6.4） |

> **判据**：换会话的目的是**断掉上下文复利**。串行时复利涨得快，所以要勤换；
> 流水线里每个角色的上下文本来就近似常数，**勤换只是白白重读圣经/大纲**。
> 所以 low 模式取"每批一次"，**不是打折，是因为这个场景里复利本来就不存在**。

## 七、不可砍的三样（来自模型机制层的硬约束）

DeepSeek-V4.1-Flash 技术报告：**reasoning effort 档位是用"长度惩罚"训出来的**——
`low`（b=50）的奖励信号就是"**少想就奖**"；而写作的质量恰恰来自深思（挑词、权衡、回退）。

| 不可砍 | 为什么 | 依据 |
|---|---|---|
| **① reasoning effort** | 靠降 effort 省 token，省下的不是成本、**是思考本身**——模型会切到"记忆检索模式"，直接吐模板短语 | 报告 5.1.4（length-penalty 训 effort 档位）；2.4.2（Engram n-gram 查表） |
| **② 风格锚点 / 已知病灶的"内联"** | SWA Bounded Replay 使 prefix state 为**近似值**——**同一句规则放在不同位置不等价**。只在开头写一次 = 靠后的位置读不到它 | 报告 3.2.2 |
| **③ 不可 hack 的判据** | 本模式砍的是"调用次数 / 读文件量"，**不是"判据强度"**。指标只能当报警器；删除测试、对抗性读者这类"需要理解"的检查不能省 | 报告 5.1.3（模型会 reward hacking 可验证目标） |

> **一句话**：low 模式砍的是**"同样的检查做几次、每次带多重上下文"**，
> 绝不是**"想多深、检查多严"**。

## 八、调用预算与效果

**两种组织形态的预算形状不同**——串行时成本堆在主编身上，流水线时摊到各子代理身上：

| | 主编/章 | 笔手/章 | 磨手/章 | 合计 | 质检 | 组织形式 |
|---|---|---|---|---|---|---|
| **standard** | 10–18 | — | — | 10–18 | 全量（机械全跑 + 判断逐项 + 子技能） | 锚点章精写 |
| **low** | **2–3** | 2–3 | 3–4 | **6–9** | 机械**全跑**（0 token）+ 判断**合并成 1 次** | **链式流水线 + 批次** |

**关键差别不在这张表的合计，而在"主编那一列会不会随章数增长"**：

- 串行：主编上下文**线性累积**，写第 30 章时每轮要重发前 29 章的一切；
- 流水线：主编每章只增**一张交接卡（~800 字）**，且卡是文件、可随时重读滚掉
  → **活跃上下文近似常数**。同一条公式"上下文 × 轮数"里，
  这一项从"随章数平方增长"变成"线性"。

**low 的调用拆解**（6–9 次/章，流水线形态）：

```
机械质检（章闸 + 窗闸，一条命令，含交接卡校验）  1 次   ← 0 reasoning
判断合并（自评+配额+四项测试）                1 次
撰写初稿                                     1–2 次
一次批量改 + 复跑                              2 次
台账/设定回流（均摊到批次）                     0.2 次
子代理任务包装配（每章一次）                    1 次
余量                                         ~2 次
```

**>9 次 = 掉进微步循环，立即自查。**（`python scripts/audit_tokens.py --traces`）

**建议混合用法**：锚点章与关键转折章用 `standard` 精写定调，其余推进章用 `low` 批量跑。
**两章混用，质量和费用都兼顾。**
