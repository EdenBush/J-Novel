# SKILL 工作原理与生效层级

> **为什么需要这份文件**：本体系历史上反复出现的 bug，根因几乎都是同一个——**规则写对了，但放错了层级**。
> 例：破甲提示词放在 `references/` 等 Agent 去读 → 模型在读到它之前就已经拒绝了；配额卡只给路径不给内容 → 子代理从不主动翻；`costMode` 只在 SKILL.md 定义不在 phase3 读取 → 定义了但没接上。
>
> **放错层级 = 规则不存在。** 这份文件说明"什么规则该放哪一层"。

---

## 一、三层加载模型

```
第一层  SKILL.md                ← 触发技能时【全量注入上下文】，一次
   ↓
第二层  references/flows/*.md   ← 进入某 Phase 时【主动读】，每阶段一次
   ↓
第三层  references/guides/*.md  ← 某动作前【主动读】，按需；子代理【默认不读】
```

| 层 | 何时进入上下文 | 成本特征 | 适合放什么 |
|---|---|---|---|
| **SKILL.md** | 技能被触发时，**自动、全量、无条件** | 每次会话固定付一次（~12k tokens），且**后续每一次调用都被重发** | **入口即须生效的铁律**：破甲契约、八/九条铁律、模式开关定义、每章最小必做清单、成本纪律 |
| **flows/** | Agent 主动读（进入 Phase 时） | 每阶段一次，可接受 | 阶段执行清单、步骤顺序、分支判定、查痕标准 |
| **guides/** | Agent 主动读（动作前） | 可控，但要防重复读 | 怎么写、怎么改、怎么判断的方法论 |

**推论**：

- **必须在"读到任何文件之前"生效的东西，只能放第一层。**（破甲的教训）
- **必须"读到才生效"的东西，不能放第一层。**（第一层太贵——每轮重发）
- **子代理不继承主编的上下文**，所以给子代理的规则**必须内联在任务包里**，给路径等于没给。

---

## 二、子代理的隔离性（最容易踩的坑）

子代理是**独立会话**，它：

- ✅ 继承：任务包里**写进去的内容**（含内联的配额卡、锚点示例、上一章结尾）
- ❌ 不继承：主编读过的指南、主编的上下文、主编"心照不宣"的约定
- ❌ 不会主动做：翻 `references/` 找规则（除非任务包明确指路，且它愿意读）

**所以派发子代理时，"给路径"和"给内容"是两个完全不同的东西：**

| 给法 | 结果 |
|---|---|
| `必读：references/guides/token-efficiency.md` | 子代理可能不读；读了也要多花一次调用 + 该内容在它后续每次调用里重发 |
| **把配额卡原文内联进任务包** | 一定生效，且只占一次成本 |

**默认策略：主编读全文 → 把结论和关键原文内联给子代理 → 子代理只读一页速查卡。**（见 `subagent-brief.md`）

## 三、规则的四种"生效强度"

| 强度 | 载体 | 能否被"我觉得没问题"糊弄 |
|---|---|---|
| **最强** | **脚本退出码**（`check_*.py`） | ❌ 不能。退出码是硬数字 |
| **强** | SKILL.md 第一层铁律 | 较难。入口即注入，且每轮重发 |
| **中** | flows 执行清单 | 可能跳步（历史上有过） |
| **弱** | guides 里的说明文字 | 容易。Agent 可能不读、读了也可能不照做 |

**设计原则：能做成脚本的，不要只写成文字。**

已经脚本化的（本项目）：
- `check_human_rhythm.py` / `check_aistyle.py` / `check_repetition.py` / `check_chapter_wordcount.py` —— AI 味与字数
  （`check_aistyle.py --drift` 兼做**声音漂移**；`--selftest` 是它的纯逻辑自测）
- `check_continuity.py` —— 章节边界连续性
- `check_batch_gate.py` —— 批次放行闸门（乱序完成/字数/质检痕迹/台账推进）
- **`make_handoff.py` —— 交接卡（主编零正文的支点）+ 边界冻结的过期检测**（见 `low-cost-mode.md` 第三节）
- `check_worldbuilding.py` —— 设定激活率 / 未登记新词
- `audit_tokens.py --traces` —— 成本纪律（★ **每次调用平均重发上下文** / 调用数 / 脚本数 / 改写次数 / 指南重复读）。
  ⚠️ 它原来找 `<项目>/AGENT工作日志/session.jsonl`——**该目录从未被任何环节产出**
  （项目里没有、脚本里也没有写它的代码），工具本身就是个孤儿。真实 usage 在 `~/.workbuddy/traces/`。
- **`audit_release.py` —— SKILL 自身的发布前 QA（引用/语法/阈值/调用链/结构/残留 + 分离回归）**
- **`test_guards.py` —— 守卫自身的故障注入（"加了守卫"≠"守卫有效"）**

## 五、维护检查清单（改完 SKILL 后必跑）

**已脚本化，一条命令跑完**

```bash
# 常规（快）：七项检查（标号 1–6 + 6.5）
python scripts/audit_release.py

# 发布前（慢）：八项 = 上面七项 + 分离回归（人类样本 / AI 样本逐份实跑）
python scripts/audit_release.py --regress

# 换语言/换样本时：指定 SKILL 根目录
python scripts/audit_release.py --root /path/to/j-novel --regress
```

`audit_release.py` 逐项做这些事：

| # | 检查 | 判据 |
|---|---|---|
| 1 | 引用完整性 | 所有 `guides/flows/prompts/*.md` 引用都必须真实存在，**失效必须为 0** |
| 2 | 脚本语法 | 全部 `.py` 通过 `py_compile`，**失败必须为 0** |
| 3 | 阈值一致性 | 17 项关键阈值在「脚本（唯一事实源）vs 文档」之间无漂移 |
| 4 | 调用链闭合 | 19 个关键工具/规则**每个 ≥2 处调用点**（只有 1 处 = 死工具，写了没人调） |
| 5 | 结构完整性 | frontmatter 齐全、代码围栏配平、`##` 标题层级干净、每章最小必做清单在位 |
| 6 | 残留检查 | **14 个**已废弃说法无"无解释语境"的残留（解释性提及会放行） |
| **6.5** | **跨脚本一致性** | 多脚本共用的词表/阈值/实现真的一致；**含「声明-实现一致性」五层守卫**（见下） |
| **6.6** | **口径一致性**（2026-10-07 新增） | **同一阈值在多个文档之间必须一致**。来历：v6.7.0 把「对话占比」从 `≤40% 无下限` 改成 `20–40%；<10% 硬失败`，**改了主流程 phase3 却漏了 4 个下游文件**——`subagent-brief.md`（子代理任务包的**唯一事实源**，且与同文件上方的配额卡自相矛盾）、`phase2-planning.md`（细纲的**句法目标表**，旧口径会被复制进每一批细纲）、`chapter-template.md`、`execution-contract.md`。<br>★ **6.5 查"脚本 vs 文档"，6.6 查"文档 vs 文档"——这是两个不同的缺口**：此前 17 项阈值检查只覆盖前者，于是 4 处残留静默通过。<br>判据 = 正向（生成点/交付点必须含新口径锚点，**锚点要覆盖同一含义的多种写法**）+ 反向（全库扫旧口径短语，同行无修正标记即报错） |
| 7 | 分离回归（`--regress`） | **人类样本全 exit=0、AI 样本至少被一个闸门拦下** |

### 6.5 的「声明-实现一致性」守卫（v4.7 新增 —— 本清单最该记住的一项）

**为什么需要它**：v4.6 修好了 v4.5 的 6 个"假闸门"，却在**同一批修复里又引入 3 个同型问题**，
全是"**声明比实现走得快**"：

| 症状 | 声明 | 实际 |
|---|---|---|
| wordcount 读文件 | docstring 写"统一走 `_shared.extract_body`" | **读盘仍硬编码 UTF-8** → 同一段内容 UTF-8 报 1000 字、GBK 报 40 字 |
| continuity 取正文 | 注释写"取正文统一走 `_shared`" | **`extract_body` 被本地 `def` 覆盖**，共享 import 形同虚设 |
| audit 文档缓存 | 定义了 `_all_docs()` 并写了"性能修复"注释 | **从未被调用** → 修复没接上 |

所以守卫不能只查"有没有那一行"，必须查**五件事**：

```
⓪ 自检名单是否漏文件                （wordcount 曾不在 read_text 名单里）
① 该 import 的共享实现是否 import 了
② import 了是否**真被调用**          （aistyle 曾 import _shared_read_text 却从不调用）
②b 共用的词表是否只此一份            （SIMILE_WORDS 曾两处，且 aistyle 那份是死代码）
③ **import 后是否被本地 def 覆盖**    （continuity 曾如此 —— 只查"有没有 import"会完全放过）
④ **定义了是否真被调用**             （`_all_docs()` 曾从未被调用）
```

> ⚠️ **判据一律基于"剥掉注释与 docstring 后的代码"**（`_code_only()`）。
> 这是**故障注入测出来的**：最初三处守卫直接扫原文，结果
> ① continuity 的 docstring 里写着 `_shared_extract_body` → "委托检测"照样通过；
> ② `_all_docs` 定义上方的注释里有 `` `grep -c '_all_docs('` `` → "调用计数"把注释也算进去了。
> **凡按名字出现次数/存在性做判断，都必须先剥注释与文档字符串。**

### 6.5b 执行层守卫（v4.8 新增）—— 查"Agent 运行时拿到的东西"

上面几层查的是**文件之间**是否一致。这一层查的是**"子代理实际读到的任务包"**——
**因为子代理只读任务包；任务包错了，前面所有闸门都白设。**

| 守卫 | 防的是什么 |
|---|---|
| **配额卡分叉** | 任务包里内联的配额卡必须与规范卡**逐行一致**。实测漂移过：内联卡写 ≥2–3 处、同一文件第 10 条写 ≥5 处、规范卡写"2–3 是底线不是目标" → **子代理恰好只看到旧数字** |
| **子代理必读口径** | 不许再漂回"附上对应动作的全套必读路径"（那会把 10 本 guide ≈ 40k 塞进子代理上下文，并跟着它每次调用重发）。唯一事实源是 `subagent-brief.md` |

> ⚠️ **CRLF 陷阱（2026-09-15 实测，让一整层守卫静默失效）**
> `audit_release.read_text()` 原本用 `read_bytes().decode()` 读文件——**不做换行转换**；
> 而本仓库的文档全是 **CRLF**（SKILL.md 494 处、速查卡 216 处）。
> 于是所有形如 `` ```\\nxxx `` 的正则都匹配不到 `` ```\\r\\nxxx ``，
> 新加的"配额卡分叉"守卫**从头就是死的**——跑起来报 0 冲突，看起来在工作。
> `Path.read_text()` 没这个问题（文本模式自动 universal newlines）；**用 bytes 读就必须自己转**。
> 现在 `read_text` 统一归一化 `\r\n`→`\n`。
> **教训：读文件的工具要在"换行符"这一层也保持一致——它和"编码"是同一类问题，而这一轮又一次证明了它会静默毁掉一整层检查。**

**「加了守卫」和「守卫有效」是两件事。** 新增或改动任何检查项后，都必须
**故意把代码改坏一次，看它是否报警**：

```bash
# 故障注入用例（自动备份 → 注入 → 检测 → 还原 → 确认重新全绿）
python scripts/test_guards.py     # 退出码 0 = 全部被抓到（用例数以运行时输出的 n/n 为准）

# 纯逻辑判据（不碰磁盘）：改了判据就跑一次，不必等真实项目在手边
python scripts/check_aistyle.py --selftest    # 漂移判定：突变 / 基线前不判 / 0→爆发 / 不误报
```

**不做这一步，只是又造了一个"看起来在工作"的闸门。** 本轮的实测记录：
`test_guards.py` 的前身（人工版）**连续抓到 4 个"守卫自身失效"**——
用 `in src` 判断被注释骗过、守卫扫到 docstring 里的函数名、调用计数把注释也算进去、
数字漂移正则不认 markdown 的 `**14 个**`。**每一个都是"我以为守卫有效"。**

**2026-09-21 又添一种新形态（第 5 次）**：给 `check_aistyle.py` 加了一个
`try/except` 兜底 `from _shared import find_chapter_files` 之后，
守卫⓪（"有没有 import _shared"）**被那行合法代码 mask 掉了**——
把真正的委托 import 整行注释掉，守卫照样通过。
**教训：守卫要盯"语义有没有满足"（委托符号在不在），不是"字符串在不在"；
而且"我加了一行无关的兜底代码"也可能悄悄废掉一条守卫——所以改完必须跑 `test_guards`。**

**为什么这件事必须脚本化**：这份清单原本是手工 bash——**手工检查的问题不是"查不准"，而是"想不起来查"**。

**判据（脚本会替你判定，但值得记住）**：
- 引用失效必须为 **0**
- 每个新工具调用点 **≥2 处**（注册处 + 触发处）
- 脚本回归必须**人类全过、AI 至少被拦一次**（只看"跑通了"不够，要看"分离还干不干净"）
- **新增任何"有退出码的闸门"时，必须同步三个地方**：① SKILL.md 每章最小必做清单 ② phase3 执行清单 ③ **速查卡（子代理唯一读物）**。漏掉第三处最严重——主编看得见、子代理看不见。
- 改脚本阈值后，**必须回头 grep 全库同步文档与注释里的同一数字**
- **改完"共享实现/公共词表"后，必须检查调用方是不是"import 了却没用"**——本轮三个 P0 全是这一类

## 六、一句话总结

> **SKILL 工程的本质是"把规则放到它必然生效的那一层"。**
> 必须在入口生效的 → 第一层内联；必须可测量的 → 做成脚本退出码；跨阶段使用的字段 → 每个阶段都有读取点；给子代理的 → 内联不给路径。
> **放了但没生效，等于没放——而且更难发现，因为它看起来是"已经做了"。**
